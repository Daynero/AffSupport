# Session mutation ownership — T169 isolated work in progress

The installed SDK can remove a new session when an old `signOut` response arrives late. This was reproduced with real SDK public APIs and an entirely synthetic transport/storage; no network or provider mutation was involved. A provider-only generation check cannot protect SDK persistence. The product uses its public SDK APIs through a cooperative mutation lane instead of modifying private SDK methods or installed dependencies.

## Ownership and ordering

Every interactive SDK session writer in the current web product participates: password sign-in, OAuth initiation, ID-token sign-in, PKCE exchange, session handoff and logout. They use one exclusive same-origin Web Lock scoped to the public authentication project origin. Logout captures the original session and shared intent revision before retirement awaits, then re-reads both inside the lock. A newer intent revision, different actor or stable session ID means superseded; it must not invoke SDK logout. The stable session ID allows refresh-token rotation within one authenticated session. Legacy sessions without that ID use conservative refresh-credential equality; changed credentials skip destructive logout.

The lock remains held through the entire SDK mutation, including response handling and persistence removal. A new sign-in either commits first and makes the old logout skip, or commits after old logout removal and survives it. Lock acquisition is bounded at10seconds; that deadline never releases a mutation which already owns the lane. Missing Web Locks fail closed. Existing auth error UI handles refusal/timeout/rejected SDK promises, including handoff initialization. No credential, decoded token payload or project address is diagnostic payload.

Provider generation advances synchronously on SIGNED_IN, before queued profile loads and React rendering. It fences delayed retirement, analytics flushing and cleanup, including same-actor re-login. Scoped old-actor journal purge is safe; global remembered jobs, analytics identity and UI state must not be cleared after replacement identity is observed.

An OAuth intent can exist before a new session: an old logout would otherwise remove its PKCE verifier. Each coordinated sign-in writer first replaces one project-scoped opaque revision under the same lock. Google/provider preparation records that intent before its asynchronous external step or handoff redirect. Only the revision is persisted; the owner session remains in memory. Missing, unreadable or corrupt shared state fails closed with AUTH_SESSION_STATE_UNAVAILABLE. Provider sign-in generation also advances at local intent start, before an authenticated replacement exists.

## Diagnostics and remaining collector acceptance

Expected stages are old-actor retirement intent, server attempt acknowledgement, SDK lane requested/acquired, SDK outcome and browser auth-state settlement. Correlate SDK intent/outcome with one opaque attempt; never reuse server retirement confirmation as proof of SDK logout or native protected-key cleanup. The typed observer now emits requested, lane acquisition and one SDK terminal via expected-actor tracking. Closed AUTH_SESSION_MUTATION_CODES and exact code locations carry bounded failure causes, never provider error text. Flow/attempt IDs are lifted into the typed wire envelope. Actual ProductAnalytics producer output is read by the real CLI SQL against disposable in-process PostgreSQL; an actual guarded beta collector/ingestion check now accepted6/6events and the SELECT-only NEXT CLI verified failure, supersession and unknown terminal. Browser-only unauthenticated producers remain explicitly unsupported.

Loss of the old analytics identity during SDK logout can suppress its terminal. A missing terminal is unknown, not success or failure. Safe fallback evidence is the actor-scoped committed retirement receipt, original native journal records, and the currently authenticated session observed in acceptance. These prove different facts. They do not reconstruct an unobserved browser transition, and they do not authorize replaying a destructive mutation under a new actor. Browser-only session loss can be genuinely unobservable; retain an explicit capability blind spot.

## Verification and compatibility limits

Real SDK tests cover replacement sign-in before/after acquisition, two clients sharing storage and one lane, same-actor re-login, token rotation and legacy fallback. Deadline/error tests cover no SDK execution after an expired wait, release on failure, missing lock and invalid scope. Provider regressions cover delayed retirement/analytics/SDK-response boundaries and handoff failure UI. An AST architecture fence prevents enumerated interactive SDK writers from bypassing the lane.

Real SDK handoff/PKCE/ID-token, late old-actor refresh, pending OAuth verifier and shared-state privacy/refusal tests pass on synthetic transport. Four physical Chrome two-tab cases now also pass with the actual `session-mutations.ts`: replacement session before guarded logout, replacement OAuth intent, legacy writer replacement before the session check, and a queued mutation waiting for the held Web Lock. This browser harness uses synthetic SDK responses; it proves real browser locking/storage behavior, not actual Auth endpoint acceptance or a legacy mutation arriving after the session check. Its own state, tabs and generated page were removed. Proof: `t169-two-tab-locks-proof.json`.

Older tabs that do not participate in the lane, external SDK clients, and different origins remain outside the cooperative ordering guarantee. Inspection of installed `@supabase/auth-js`2.110.7 confirms `_signOut` still removes shared session storage after its awaited server request. This is source evidence of the compatibility risk, not a fresh runtime reproduction. Do not claim the late non-cooperating race is fixed. Actual Auth/two-tab integration and current full/release verification remain open.

The CLI capability account.session_logout treats absent terminals as incomplete observability, including when another attempt completed. Audit pairs actor plus attempt. Inspection of a colliding attempt with mixed or unknown actors does not select a terminal or claim a last-proven stage; actor metadata used for that guard is not emitted into event output. This does not fix or claim unrelated legacy capability inspection semantics.
