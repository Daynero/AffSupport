# Feature Specification: Масові запуски

**Branch**: `053-bulk-launches` | **Created**: 2026-11-13 | **Status**: Implemented and locally verified — release acceptance remains separate
**Input**: Owner requests polished Launch workspace, readable chronology/states, selection/delete/keyboard copy, immediate progressive results, saved configurations and optimized batch generation. Implementation stays isolated from main and the active release.

## User Scenarios & Testing

### US1 — Read and manage launches (P1)
As an operator I distinguish saved settings, queued, generating, ready, partial, failed and canceled launches without opening each card. I see creation time separately from the intended launch date. I select by checkbox, range, select-all or marquee and archive selected items through the existing retention confirmation. Cmd/Ctrl+C and Cmd/Ctrl+V copy selected configurations; text editing and native text selection retain their shortcuts.
Acceptance: mixed-state fixture has explicit labels and icons, stable chronological pagination, count of selection and visible primary batch action. A copied launch is a fresh draft, never copied generated resources. A duplicate notice expires and does not offer navigation to the already opened copy.

### US2 — Prepare and generate a batch (P1)
As an operator I save multiple configurations then generate the selected drafts in one action. Each item retains separate validation, request identity, progress, result and recovery. An invalid item does not block valid siblings. Repeated activation cannot submit the same item twice. Canceling a batch requests cancellation of its unfinished accepted generations through existing fences; completed results remain intact.
Acceptance: four saved configurations for one video, five variations each, are admitted through existing generation safeguards. Running/results are never regenerated by the bulk action. One authenticated command durably accepts valid selected items and records each refusal. Closing/reloading the browser cannot stop accepted work. Re-entry discovers the batch and actual generation progress automatically; transient observation loss needs no manual status action.

### US3 — See results while generation proceeds (P1)
As an operator I land on results after Generate is validated, see deterministic campaign names immediately and the catalog name as soon as its reservation exists. Pending links have explicit waiting placeholders and are not copyable. Existing result remains identifiable during regeneration. Copyable fields always show a copy affordance; successfully copied unchanged values retain a visible check and label.
Acceptance: pending, failed, partial and successful stages remain on results; clipboard refusal never records success; changing a value resets its copied mark; no temporary revision or ready URL is fabricated.

### US4 — Reuse expensive media preparation (P1)
As an operator I generate repeated-video configurations with shared source preparation and independent variation outputs. Compatible jobs are grouped, coordination is bounded and native work stays inside PowerGovernor. Source authorization and frozen settings remain per job. Different content/trim/output recipes cannot share prepared bodies incorrectly.
Acceptance: 4 × 5 equivalent-body requests perform one preparation; concurrent waiters share work. Cancellation of one consumer does not cancel siblings. Eviction cannot remove in-use material. Failed/unknown preparation never becomes a cache hit. Benchmarks distinguish cold preparation savings from already-warm individual generation.

## Requirements

- **FR-001** Explicit text/icon state for every card, creation timestamp and server chronological order with cursor tie-break; no color-only meaning.
- **FR-002** Checkbox, Shift range, Cmd/Ctrl+A, Escape, guarded Delete and Cmd/Ctrl+C/V on the list; preserve editable/portal/native selection behavior and permissions.
- **FR-003** Config-only duplication through existing idempotent API; transient receipt notice without redundant open action; retain uncertain request identity.
- **FR-004** Saved drafts can be selected and generated in one action; preflight each, bound admissions, retain per-item outcomes and do not regenerate existing results.
- **FR-005** Group compatible source jobs for cache locality; retain immutable per-launch settings/variation draws and server lease/resource authority.
- **FR-006** Batch cancellation is durable and idempotent, applies only to unfinished generations, preserves completed resources and pending cleanup fences. Exact selected-version CAS rejects edits racing admission. Actor/membership/security changes revoke execution authority without erasing receipts.
- **FR-007** Results open before long generation completes, campaign names appear immediately, authoritative catalog reservation replaces pending naming; links stay disabled until confirmed.
- **FR-008** Visible copy icon and persistent copied label/check tied to actual value and authorized actor/revision; clipboard failure is explicit.
- **FR-009** Card progress uses confirmed stages/counts, including partial outcomes; unknown progress stays indeterminate. No per-card polling.
- **FR-010** Reuse verified content and compatible preparation only; cancellation-aware sharing, bounded cache and safe consumer ownership.
- **FR-011** Typed diagnostics connect batch intent/dispatch and per-launch attempts to existing inspect/investigate evidence; missing signals are unknown, no names/URLs/paths/content in analytics.
- **FR-012** Reuse UI inventory and tokens; keyboard/focus, narrow view, both themes and reduced motion acceptance; keep release/main untouched.
- **FR-013** Unattended accepted batches continue independently of browser lifetime. Individual refusal, deleted source, cancellation, provider failure or unknown output cannot starve executable siblings. Transient transport failures retry with bounded backoff and persisted Retry-After. The existing workspace observation owner restores current progress automatically on return.
- **FR-014** One batch key and fixed child keys identify an immutable submission. Lost replies reconcile/replay only that identical command. Durable per-item accepted/pending/refused receipts are separate from projected generation state. Never manufacture completion, repeat an unknown provider side effect, or create a fresh attempt automatically after definitive failure.
- **FR-015** Batch size stays bounded at 100. Server/native leases and PowerGovernor govern concurrency. Fair paced per-set claims skip temporarily uncertain sets while preserving ownership. Native restart adopts only quiescent old-boot sets under fresh actor/installation/delegation/epoch authority after at least two minutes of silence; unknown uploads remain pending and do not block siblings.
- **FR-016** Closing a detail, browser, or switching views does not cancel already accepted work. No manual Check status button or background-work opt-in is required. Local video work waits honestly for an authorized available Soty executor; sleeping/offline machines are not represented as executing. Cancel remains an explicit durable action.
- **FR-017** A shared preparation producer's missing input or cancellation cannot invalidate independently verified surviving source copies. Rebuild from a surviving consumer; never cache failed outputs or bypass live source authority.

- **FR-018** Automatically enroll background work on the next eligible authenticated connection, including previously manually disabled installations. Keep actor/session/entitlement/membership fences, native single-flight and idempotent enrollment; never resurrect security-revoked credentials. Remove the toggle and prompts to enable it in Settings. Transient setup and legacy retry exhaustion recover automatically.
- **FR-019** Bulk captions show offer · social · ad account suffix · status. Copy/paste actions say Copy launches (count) / Paste as drafts (count). Cards reserve heading/facts/progress/footer space so ordinary content changes do not push neighbors; layout responds to available container width.
- **FR-020** Elapsed time belongs to the authoritative generation attempt, survives reopen/reconnect/stage changes, and never resets when an uncertain request is replayed. A confirmed new attempt resets the clock; scope changes cannot leak another launch’s time. Missing historical timestamps remain unknown.

- **FR-021** Desktop launch settings use one creative drop/click field with a computer/workspace choice, authorized selected preview and concise replacement. Essential counts/budget/audience/date/catalog controls are compact. Creative names have bounded input width; creative and URL share a desktop row with one visible URL label and aligned inline help. Long manual-budget lists retain bounded height and keyboard access; switching from an invalid automatic range must leave editable manual fields. The existing duration slider opens from a compact disclosure with the selected time/range always visible, and the R2 switch remains visible among main catalog settings; advanced details disclose on demand and invalid hidden fields reveal automatically. No full video download just to render a thumbnail. Notes are visually neutral until actual clipboard success, including previously colored notes.
- **FR-022** A completed catalog can be renamed from Launch results and the catalog manager through the same authoritative material operation. Confirmed current name appears consistently everywhere; result-only text overrides must not masquerade as a real rename. Lost replies, conflicts, permission loss and concurrent renames reconcile the same mutation identity.
- **FR-023** If a historical catalog name was embedded in a generated SUB/advertising link, renaming requires an explicit OK/Cancel explanation that existing links retain the old value. Use compact text that explains the old name will also remain visible below the new name. Keep the original bound name as a small noneditable annotation; do not rewrite immutable generated URLs. Authorized catalog search also matches previous names, without exposing aliases across teams/actors.

## Edge Cases

Changed draft between selection and admission, revoked edit permission, archived material, same source with changed bytes, no executor, double activation, uncertain save/generate reply, browser close, actor/team change, empty selection, stale list after Realtime, active publication after parent completion, clipboard denied, copied value changed, cache eviction while encoding, cancellation while waiting for shared preparation.

## Key Entities

Launch draft and generation remain authoritative aggregates. Batch submission is a durable actor/team-scoped immutable command over frozen selected IDs/versions, with accepted/pending/refused membership and existing durable generations. List summary exposes stage receipts without downloading full launch details per card. Prepared body is shared immutable intermediate content; final variation/catalog is never shared merely because the source matches.

## Success Criteria

- **SC-001** Mixed-state UI tests distinguish draft/queued/running/ready/attention/canceled and creation chronology; selection, copy and archive work with keyboard and pointer.
- **SC-002** Deferred generation fixture renders campaign preview before resolving the generation request; pending URLs cannot be copied and successful values retain a copied marker.
- **SC-003** Batch fixture covers four drafts × five variations, bounded admission, duplicate activation, invalid sibling, stale version, stop and scope loss with no duplicate accepted request.
- **SC-004** Media regression proves 20 compatible consumers use one expensive body preparation; incompatible recipes miss; aborted waiter exits promptly and in-use outputs survive eviction. A repeatable benchmark reports cold/warm conditions; no universal speed multiplier is claimed.
- **SC-005** Diagnostic regression covers success, refusal, unknown/missing terminal, interruption and cache-hit evidence through existing typed producer/sanitizer/CLI seams.
- **SC-006** Focused tests, static/design gates and `npm run verify` pass. Runtime/browser and release-only limitations are recorded precisely; no production deployment or release artifact mutation.

- **SC-007** Ten durably submitted launches with a deleted source, unknown upload, cancellation, browser closure and native restart allow every independent executable sibling to finish without duplicate output; DB and native fault tests prove fences.
- **SC-008** Existing disabled registration auto-enrolls once after authentication; two tabs and lost confirmation cannot revoke the newly enabled worker; logout and membership loss at each await deny stale completion.
- **SC-009** Browser fixtures at 320–1600px show no horizontal overflow or neighbor displacement when a reserved card’s title/status/progress changes; elapsed tests cover 7-minute reopen, lost metadata, pending replay and real attempt change.

- **SC-010** Desktop browser acceptance proves compact settings, click/computer/workspace/drop paths, selected preview, keyboard use, async scope fencing and auto-revealed invalid advanced fields. Notes become green only after confirmed copy. No mobile screenshots are delivered to the owner.
- **SC-011** Rename from results and manager changes the same provider/material name and both readbacks, preserves already encoded SUB/URL values, warns only for actual binding, retains searchable old names and survives lost replies/concurrent changes without duplicate effects or unauthorized access.

## Assumptions

The existing autosaved draft is the requested reusable configuration. Batch applies to explicitly selected saved drafts, up to one loaded page (100), not hidden filtered records. Definitive failures retain their cause; temporary uncertainty is automatically reconciled without a user status-check action. The owner explicitly superseded the initial session-local queue: acceptance is durable before success is shown, and browser closure is not a worker lifecycle event. Existing native caches already accelerate warm individual runs, so batch speed comes from removing duplicate cold work and overlapping bounded coordination. The complete accepted flow still depends on authorized provider/native availability.
