# Protection, failover and recovery contract

Primary private originals: R2 Standard **EU jurisdiction**. Independent recovery data: B2 **US East**, separate account/admin MFA, keys not stored in the R2 writer environment. Existing buckets have unknown jurisdiction until readback; never infer it from an `eeur` location hint. Existing public buckets continue until explicit validated relocation of links; regional protection claim applies only after all required backup dependencies pass.

## Protection state and independent metadata

`committed` means verified primary bytes + authoritative SQL commit, `protected` means exact immutable replica + current minimum lock retention + restorable metadata checkpoint containing that commit. Distinct user label «Збережено; резерв готується». Joint watermark is the oldest required object/metadata dependency, not maximum successful timestamp. Target ≤15min from committed_at under admitted healthy workload; oldest lag >15min blocks new durable writes/generations, alerts, and reconciles inflight completions as saved-unprotected. Never block revocation, cancel or export to meet this gate.

Worker consumes transactional outbox, streams R2 generation into B2, verifies full digest/length, records exact B2 version identity and lock readback, then protects metadata. All business mutations affecting recoverability (including RLS memberships, policy/cutover, aliases, keys-by-reference, quota/receipts and tombstones) must be covered. No “eventually export DB daily” substitute.

Launch metadata design: encrypted transactionally consistent portable snapshot of required application schemas, auth identity/authorization state and schema/version configuration at most every5min, upload+verify completion budget ≤5min; append-only protected mutation/tombstone/cutover journal exported ≤1min for inter-snapshot replay. A snapshot uses dedicated operational backup principal and approved supported Supabase export method, **never analytics credentials**. Benchmark snapshot size/load on isolated schema/data fixtures and validate provider support before production enablement. If bounded full snapshots cannot meet target, implement and qualify transactional change capture before launch rather than weakening the target silently. This is deliberately a qualification gate; no claim of existing managed-WAL access. Portable export excludes application file blobs already in version manifests; encrypted auth backup is recovery data, never analytics/report content.

Each exported snapshot is one database REPEATABLE READ consistent boundary (supported exported snapshot shared with all export readers), including auth/security tables and actual operation receipts visible in that snapshot. Protected means that specific commit receipt is included, not that its ID is below a maximum sequence or timestamp. Concurrent transactions can commit in reverse allocated-ID order; aborted transactions never enter the snapshot. The journal does not advance the protected watermark beyond a fully verified snapshot in v1. Replay for operator recovery is allowed only when a transaction-atomic, gap-free commit boundary is proven; otherwise restore the complete snapshot and fail closed for uncertain later rights. Tests cover inverted commit order, rollback, multi-row mutation, source export failure and auth revocation during capture.

Avoid storing a new full dump every5min for31days: deduplicate immutable metadata chunks within the backup account, with stable partition identity and encrypted chunk reuse plus small immutable snapshot manifests. A chunk is retained through the latest referencing manifest; GC traces all retained manifests, never only the latest. Changed data/history and manifests still cost money. No cross-tenant dedup endpoint or deterministic public encryption; dedup references remain internal, encryption uses managed per-chunk random keys. Benchmark full consistent export CPU/read load; chunk reuse reduces stored bytes, not source query cost. Metadata bytes/requests/CPU and independent transfer-network costs enter the qualification model. A nominal 1GB fresh dump every5min otherwise retains8,640GB over30d, an explicitly rejected default.

Snapshot manifest pins the exported snapshot identity, schemas, object references, policy epochs, auth restoration procedure and integrity hashes. A restore point is publishable only when all required referenced object replicas are `replica_verified` (full hash/length/lock proof independent of metadata). After snapshot manifest/closure verification, the corresponding operations become jointly `protected`. Order is replica_verified → snapshot_verified → protected, never a circular requirement for joint protection before the snapshot exists. Historical purged/tombstoned versions in audit metadata do not become live blob dependencies or get resurrected. Concurrent objects may lag without making an older complete checkpoint invalid; UI shows real recoverable-through age. DB corruption detection can require an older known-good checkpoint and therefore an older RPO, explicitly reported. Supabase PITR is useful additionally, not independent portable recovery.

All current backup object versions receive rolling lock extension to now+31d at least daily, alert before remaining <30d. On retirement stop extension only after tombstone has independent proof; preserve max(current lock, retirement+30d). A dedicated retention-only principal cannot shorten locks/delete/read content. Same principle protects metadata snapshots/journals (rotate snapshots, keep restore points and dependent objects consistent for30–31d). Root account compromise/provider administration remain residual risks; offline recovery MFA/keys and restore drills reduce them, not eliminate them.

## Failure matrix

| Failure                                              | Path                                                                                                                   | Target / explicit limit                                                                                                                                  |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R2 transient5xx/timeout, DB/auth/gateway healthy     | authorize current request; retry max1 then exact verified B2 generation                                                | circuit breaker converges ≤5min; protected read p95 ≤10s; no fallback for auth403, true404, revoked/tombstoned objects                                   |
| Cloudflare Worker/Pages/DNS outage, Supabase healthy | predeployed independent read API/frontend on separate host, separate DNS recovery hostname/TLS/static assets, B2 bytes | operator declaration to read-ready ≤60min; no seamless same-domain promise; public catalogs need independent feed URL or preconfigured external fallback |
| Supabase auth/DB unavailable                         | deny authenticated access whose current authorization cannot be checked; incident page remains independently available | restore verified metadata+objects into isolated supported DB/auth, reconcile revocation journal, ≤24h qualified launch volume                            |
| primary credential compromise or mass deletion       | revoke primary credential, preserve immutable B2, restore into clean environment                                       | test backup non-deletability by ordinary writer; elapsed restoration measured, not assumed                                                               |
| B2 outage/replication failure                        | R2 reads remain; labels degraded; no new durable writes beyond15min protection budget                                  | user knows recoverability lag; existing safe reads/security actions continue                                                                             |
| corrupt object found during read/restore             | quarantine replica/version, report checksum error, seek another verified copy                                          | never return stale version as latest; irrecoverable explicit                                                                                             |

The independent recovery service is prebuilt/redeployed on each release, config parity checked, not installed for the first time during incident. Its provisioning needs independently administered DNS/TLS, pinned artefacts, standalone status page, secrets vault access, real auth redirect/CORS allowlist and the current revision of authorization logic. An endpoint on the same Cloudflare zone is not independent enough. Soty existing public catalog delivery on Cloudflare may pause; universal external-feed failover cannot be promised without each consumer's alternate URL support.

## Restore and failback

1. Declare incident with evidence, disable mutating admissions and fence background leases; record immutable incident/epoch in independent control journal. DB outage means no write gateway can grant a new lease.
2. Select restorable checkpoint and compatible schema/app release. Restore into isolated environment; validate manifests/checksums and every FK/canonical linkage, quotas, cutover receipt, deny/tombstone watermarks.
3. Auth restore is fail-closed: all previous sessions and download grants invalidated; reauthentication via qualified restored auth with rotated signing keys and independent access to identity provider. If latest revocations cannot be proven, keep affected spaces blocked until owner revalidates access; do not trust old memberships just because login works. Password/identity recovery and Google sign-in outage are tested dependencies, not assumed portable auth.
4. For recovery UI with restored DB, require approved checkpoint + replay through known incident boundary or explicitly restrict affected writes/reads. Never replay a purge that would delete currently protected recovery data. Manual review captures uncertain revocations/ownership/grants.
5. Enable read-only mode only after security and reference checks. Reveal restore point age and unavailable recent generations. A shared schema restore without object manifest verification is not success.
6. Once primary healthy, compare generation/policy/ledger and both replica sets; user updates have remained paused, so no bidirectional merge. Re-enable primary writer in a new monotonically increasing epoch, fence all old jobs/tickets, then leave read-only standby. Manual cutback avoids oscillation.

Drills quarterly and before first launch/major recovery change. Initial fixture1TB/100k objects, plus current Scale1TB/20people/20spaces and the largest actually offered add-on envelope (up to10TB/80people/50spaces/1m objects): quantify object listing/copy/read speed, bytes moved, digest checks, RPO/RTO, transfer allowance and billed requests. Metadata restore/read availability does not require copying every B2 byte back to R2; full repatriation ETA is reported separately. No production destructive drill without a separately explicit authorized scope.

Snapshot boundary semantics use PostgreSQL's supported exported-snapshot mechanism; provider privileges/export tool compatibility still require a sandbox proof. Reference: [PostgreSQL snapshot synchronization](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION). This does not claim managed Supabase WAL or auth signing keys are automatically portable.

## Snapshot publication versus garbage collection

Before building a manifest, pin every dependency in a leased build record. Before publication verify/extend each reused chunk and key-reference retention through manifest expiry; atomically publish the manifest generation and convert builder pins into retained references. GC must use a generation fence and recheck live/building references plus lock expiry immediately before deletion. Unknown manifest-publication outcome is reconciled before releasing pins. Aborted builder pins expire only after its lease/unknown outcome is resolved. Key material retention follows the latest referencing manifest and stays outside primary provider failure scope. Tests cover expiring-chunk reuse during GC, manifest response loss, failed builder, lost encryption-key reference and concurrent tombstone creation.
