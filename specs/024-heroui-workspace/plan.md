# Implementation Plan: The team workspace on HeroUI

**Branch**: `024-heroui-workspace` | **Date**: 2026-09-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/024-heroui-workspace/spec.md`

## Summary

Re-lay the team workspace on HeroUI v3 (React Aria + Tailwind v4), themed from Soty's existing
token layer, and — while every screen is being touched — fix the flows those screens were
forcing. The load-bearing decisions are in [research.md](./research.md):

- The component inventory keeps its public API and its marker classes; only its insides become
  HeroUI (D5). That makes the migration reviewable screen by screen, keeps the "one role, one
  appearance" test working, and hands the new look to the screens outside the workspace for free.
- Soty's `tokens.css` drives the library, not the reverse (D2), so the design gate keeps its
  premise and the exemption list stays empty.
- The token fence moves to where values can now be written — a new check on utilities in TSX
  (D6) — because Tailwind v4's Vite plugin never writes a stylesheet into the source tree.
- One registry defines what can be done to a material, and every surface renders from it (D9).
  That is what makes the owner's example — catalog a video from inside the task that carries it —
  a small change rather than a large one.
- The task editor gets one save model: autosave (D10).

**Primary Dependencies**: React 19.2.7, Vite 8.1.5, `@heroui/react` 3.2.5, `@heroui/styles`
3.2.5, `tailwindcss` 4.3.1, `@tailwindcss/vite` 4.3.1, `react-aria` 3.52.1,
`react-aria-components` 1.21.1, `@react-aria/i18n` 3.13.1, `@react-aria/ssr` 3.10.1,
`@react-aria/utils` 3.34.1, `@internationalized/date` 3.12.4, `lucide-react` 1.37 (kept)

**Storage**: none new. No migration, no edge function, no RPC, no shared-contract change.

**Testing**: vitest (central `tests/`, `*.test.ts(x)`, jsdom docblock for DOM), single-fork on
this machine; the gate scripts under `scripts/`; hand-walked visual verification on the beta.

**Target Platform**: browser, Cloudflare Pages; the app also runs inside the packaged desktop
shell, which loads the same bundle.

**Project Type**: web application in an npm-workspaces monorepo; this feature touches
`apps/web` only.

**Performance Goals**: first-load weight measured before and after and stated (D7); no
transition of a layout-forcing property; a 500-row folder stays usable.

**Constraints**: web-only deployable — nothing under `apps/agent`, `packaging`,
`packages/shared/src`, `packages/shared/package.json` or `config/production.env` may change, or
the release gate refuses the deploy. Prettier is non-negotiable (`printWidth: 100`, single
quotes, no trailing comma, `arrowParens: avoid`). This machine runs one heavy process at a time.

**Scale/Scope**: 146 files / 32,060 lines under `apps/web/src/team/`; 13 inventory files / 2,856
lines; 25,929 lines of CSS of which 3,529 are team-dedicated; 128 modules importing the
inventory; 104 raw buttons, 34 raw inputs, 11 raw selects to remove.

## Complexity Tracking

| Violation                                                                                                                                       | Why needed                                                                                                                                                                                                                                      | Simpler alternative rejected because                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Principle VI: a styling library and a utility layer replace "one global stylesheet"                                                             | The owner chose HeroUI to get a complete, accessible, beautiful component set instead of maintaining 45 bespoke controls and five hand-rolled roving-focus implementations. The library cannot be themed or composed without its utility layer. | Keeping the bespoke system: the audit's numbers (104 raw buttons, two calendars, two menu implementations, two dialog implementations, two `Button` generations) are what "keep maintaining it" has produced in one cycle. Vendoring only HeroUI's CSS: its components are tailwind-variants functions, so the CSS without the components is not the library. |
| A second component generation exists during the migration (inventory adapters over HeroUI, while un-migrated screens still use the old classes) | Layer order (D4) makes each screen's migration a deletion. A flag day across 128 modules is not reviewable.                                                                                                                                     | A single atomic rewrite: the previous migration's finding S1 is that the phased floor inverted the cost in the project's favour; repeating it is the cheaper path, not the more complex one.                                                                                                                                                                  |
| The compression queue is lifted into a provider                                                                                                 | A task must be able to compress an attachment without the explorer being mounted (FR-012, FR-019).                                                                                                                                              | Leaving it in `ExplorerShell`: it is the single reason a whole class of actions cannot be offered anywhere else, and the same lift was already made for batches by `LibraryProcessingProvider`.                                                                                                                                                               |
