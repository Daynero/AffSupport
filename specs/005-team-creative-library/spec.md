поверх Google Drive з Finds і Library, масовим завантаженням, автоматичним визначенням мови,
керованою локальною обробкою, спільними результатами, розподілом jobs між Local Agents,
простими tasks із універсальним progress, швидким поширенням Drive-посилань і розділеною
статистикою внеску команди. Уточнення: транскрипт є прив'язаним до відео текстовим
sidecar-документом і рухається або видаляється разом із ним; відеокартка відкриває й копіює
кешований текст або пропонує транскрибування. Tasks живуть в окремому просторі, підтримують
необмежену кількість посилальних media-вкладень через пошук чи drag-and-drop з дерева,
плиткові preview, створення task прямо з asset і календарний фільтр."

## Контекст і межа інкременту

Ця функція розширює наявний командний медіапростір із підключеним Google Drive, членством,
ролями, дозволами, каталогом і файловими операціями, визначеними у feature 001. Вона також
використовує наявну командну галерею та безпечний перегляд лендінгів із feature 004.

Soty залишається легким робочим шаром над зрозумілим Google Drive, а не створює окрему
віртуальну файлову систему чи великий project manager. Цільовий наскрізний сценарій:

Upload → Organize → Finds → Library → Task → Work → Result

Окремий керований сценарій збагачення бібліотеки:

Process Library → distributed Local Agents → shared results

## Clarifications

### Session 2026-08-14

- Q: Який закритий набір значень має структурний сегмент Type, що створює папки Drive? → A:
  Video / Image / Archive / Transcript / Landing / Other — канонічний material-category набір із
  шести значень; Type визначається автоматично. Файл поза конкретними категоріями отримує catch-all
  Other, а контрольований Unknown (за FR-022) застосовується лише за відсутньої категорії.
- Q: У якому форматі зберігати канонічні transcript- і translation-sidecars у Drive? → A:
  Простий UTF-8 текст (.txt) без часових міток; картка показує й копіює саме цей текст, а
  language code лишається в детермінованому імені файлу.
- Q: Як вирішувати колізію, коли дві різні назви Offer нормалізуються в одне безпечне ім'я
  папки Drive? → A: За поточної нормалізації (case/whitespace-fold) справді різні офери не
  колізують; лише регістрові/пробільні варіанти того самого оферу свідомо ділять одну канонічну
  папку. Перший display-value зберігається, тихої заміни немає; окремий суфікс не потрібен.
  (Уточнення 2026-08-15: попередня відповідь про стабільний суфікс скасована — премиса колізії
  різних оферів не справджується за фактичної нормалізації.)
- Q: Як обробляти rate limits / квоти Google Drive під час масових завантажень і розподіленої
  обробки? → A: Без спеціального throttling — покладатися на resumable-сесії та поелементні
  повтори; відмова через квоту показується як поелементна помилка, придатна до безпечного
  повтору, а пачка не подається як повністю успішна.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Масово додати та організувати матеріали (Priority: P1) 🎯 MVP

Учасник завантажує велику змішану пачку креативів, лендингів та інших матеріалів, один раз
обирає для всієї пачки Finds або Library, офер, GEO та, за бажанням, мову. Soty одразу
показує завантажені assets, створює базові представлення та розміщує їх у зрозумілих папках
Google Drive. Якщо мову задано вручну, це рішення має безумовний пріоритет; якщо ні, Soty
намагається визначити її локально й чесно залишає Unknown за недостатньої впевненості.

**Why this priority**: Без швидкого пакетного входу команда знову витрачатиме час на
завантаження й тегування кожного файла окремо, а Creative Library не матиме практичної
цінності.

**Independent Test**: Вибрати щонайменше 100 змішаних матеріалів, один раз задати Finds,
офер і GEO, залишити мову для автоматичного визначення та підтвердити, що кожен успішно
завантажений asset з'являється без окремої форми, має правдивий стан обробки й лежить у
відповідному зрозумілому шляху Drive.

**Acceptance Scenarios**:

1. **Given** учасник із дозволом на завантаження, **When** він обирає пачку матеріалів і
   задає спільні параметри, **Then** ці параметри застосовуються до всієї пачки без
   пофайлового тегування.
2. **Given** мову явно задано перед завантаженням, **When** пачка прийнята, **Then**
   автоматичне визначення мови для цих assets не запускається й ручне значення не
   перезаписується.
3. **Given** мову не задано, **When** Soty має достатній мовний сигнал, **Then** asset
   отримує визначену мову; за недостатнього сигналу він отримує Unknown без мовчазного
   припущення.
4. **Given** bytes окремого asset уже успішно збережені, **When** решта пачки ще
   завантажується або проходить легку обробку, **Then** готовий asset уже доступний у
   Finds/Library із правдивими проміжними станами.
5. **Given** учасник відкриває підключений Google Drive напряму, **When** він переходить
   шляхом Stage / Offer / Language / Type, **Then** знаходить ті самі матеріали без
   необхідності знати внутрішню модель Soty.

### User Story 2 - Відібрати Finds до робочої Library (Priority: P1)

Учасник переглядає сирі знахідки, вибирає одну або багато корисних і одним простим action
переносить їх до Library. Фізичні assets переміщуються між відповідними папками Google
Drive без копій. За потреби учасник так само повертає матеріал до Finds.

**Why this priority**: Розділення великої сирої маси від відібраного робочого фонду є
центральною організаційною моделлю Creative Library.

**Independent Test**: Додати 20 assets до Finds, вибрати довільні 5, перенести їх до
Library, повернути 1 назад і підтвердити в Soty та напряму в Drive, що існує рівно по одному
фізичному asset, а шляхи й metadata узгоджені.

**Acceptance Scenarios**:

1. **Given** один або кілька assets у Finds, **When** уповноважений учасник обирає
   «Move to Library», **Then** вони зникають із Finds, з'являються в Library і фізично
   переміщуються до відповідної Library-папки Drive без створення копій.
2. **Given** asset у Library, **When** учасник обирає повернення до Finds, **Then** той самий
   фізичний asset повертається до відповідної Finds-папки зі збереженими metadata та
   результатами.
3. **Given** користувач змінює structural tag, **When** зміна підтверджена, **Then** asset і
   його пов'язані sidecar-результати переміщуються як одна логічна група до нового
   канонічного шляху.
4. **Given** переміщення в Drive не вдалося, **When** Soty отримує відмову або конфлікт,
   **Then** asset не показується в новому Stage як успішно переміщений, а користувач бачить
   придатний до безпечного повтору стан.

### User Story 3 - Запустити Process Library у зручний час (Priority: P2)

Учасник із дозволом на обробку сам запускає Process Library, коли готовий навантажити
комп'ютер. До старту Soty сканує доступні assets і показує, скільки саме відсутніх робіт
знайдено: повних транскрипцій, перекладів, оптимізацій лендингів та інших підтримуваних
operations. Повторний запуск безпечний і добирає лише те, чого ще бракує.

**Why this priority**: Важка робота має створювати спільну цінність, але не повинна
неочікувано навантажувати пристрої або дублювати вже готові результати.

**Independent Test**: Підготувати Library із відео без транскриптів, одним уже
транскрибованим відео, лендингом без оптимізації та готовим лендингом; відкрити Process
Library, перевірити точні counts, запустити й повторити після завершення — другий запуск не
створює вже виконаних operations повторно.

**Acceptance Scenarios**:

1. **Given** Library із різними пропущеними результатами, **When** учасник відкриває
   Process Library, **Then** він до запуску бачить кількість jobs за кожним типом operation.
2. **Given** учасник не підтвердив старт, **When** scan завершено, **Then** жодна важка
   operation не запускається.
3. **Given** відео без повної транскрипції, **When** processing успішно завершується,
   **Then** команда отримує оригінальний транскрипт і переклад мовою інтерфейсу учасника,
   а обидва варіанти доступні з картки з дією Copy.
4. **Given** підтримуваний неоптимізований лендинг, **When** processing успішно
   завершується, **Then** збережено робочий оптимізований результат із коректними media
   links і явним походженням від оригіналу.
5. **Given** потрібна operation уже має чинний готовий результат для поточної версії
   джерела, **When** Process Library запускають повторно, **Then** ця operation не входить
   до черги й не виконується повторно.
6. **Given** інтерфейсна мова збігається з мовою оригіналу, **When** транскрипція готова,
   **Then** один оригінальний текст використовується для обох режимів перегляду без
   беззмістовного дублювання перекладу.
7. **Given** транскрипція відео успішно завершилася, **When** результат стає доступним
   команді, **Then** існує один чинний текстовий sidecar-документ, явно прив'язаний до
   конкретного відео та його версії, а картка відкриває його кешований текст без повторної
   важкої обробки.
8. **Given** відео має чинні transcript-sidecars, **When** відео переміщують, видаляють
   відновлюваним способом або відновлюють, **Then** усі його чинні текстові sidecars
   проходять ту саму lifecycle-дію як одна логічна група; частковий результат не показується
   як успішний.
9. **Given** картка відео, **When** чинний кешований текст існує, **Then** видно окремі дії
   «Переглянути текст» і «Скопіювати текст»; коли тексту немає або він застарів, замість них
   доступна дія запуску транскрибування, а Copy не показується.

### User Story 4 - Спільно обробляти Library кількома комп'ютерами (Priority: P2)

Кілька учасників одночасно запускають Process Library, а їхні Local Agents забирають різні
відсутні operations. Активна робота тимчасово закріплена лише за конкретною operation.
Якщо комп'ютер зупинився, поставлений на pause, завис або втратив зв'язок, робота швидко
повертається до спільної черги. Перший чинний результат стає командним, а запізнілий
дублікат не перезаписує його.

**Why this priority**: Розподіл скорочує загальний час обробки та не дозволяє одному
пристрою назавжди заблокувати Library.

**Independent Test**: Запустити три Local Agents на черзі зі 100 operations, примусово
зупинити один під час роботи та створити контрольовану race condition для однієї operation;
перевірити перерозподіл, рівно один готовий результат і стан Skipped — already completed для
запізнілої спроби.

**Acceptance Scenarios**:

1. **Given** кілька активних Local Agents, **When** вони одночасно запускають processing,
   **Then** доступні jobs розподіляються між ними без блокування всього asset.
2. **Given** Agent підтримує активну operation, **When** його heartbeat надходить,
   **Then** тимчасове закріплення продовжується тільки для цієї operation.
3. **Given** heartbeat припинився, **When** короткий строк закріплення сплив,
   **Then** operation автоматично знову доступна іншому Agent.
4. **Given** два Agents отримали результат через race condition, **When** перший чинний
   результат уже прийнято, **Then** другий не перезаписує його та завершується як
   Skipped — already completed.
5. **Given** один teammate уже завершив operation, **When** інший відкриває asset або
   Process Library, **Then** він одразу бачить спільний результат і його комп'ютер не
   повторює цю роботу.

### User Story 5 - Працювати з media у зручному просторі tasks (Priority: P2)

Учасник відкриває окремий простір tasks, створює task із нуля або прямо з креативу чи
лендинга, прикріплює будь-яку кількість доступних media пошуком або перетягуванням із
лівого дерева, призначає виконавця, додає коротку note і рухає task через To do,
In progress та Done. Вкладення лишаються у своїх Drive-папках і показуються плитками з
малими правдивими preview. Прогрес доступний прямо на картці як універсальна дискретна
шкала: 0–100 за замовчуванням або власний максимум для конкретної task, а календар і
швидкі пресети дозволяють показати tasks за потрібну дату.

**Why this priority**: Це з'єднує Library з реальною командною роботою, не перетворюючи
Soty на важкий project manager.

**Independent Test**: Створити task із asset, додати ще кілька media пошуком і одним
multi-drag із дерева, підтвердити відсутність фізичного переміщення, плиткові preview та
кадр відео на позначці 1 секунда. Призначити teammate, встановити Max = 9 і progress = 6,
перевести task у Done та підтвердити, що лишається 6/9; окремо створити task без ручної
зміни та підтвердити автоматичні 9/9. Перевірити вибір конкретної дати й пресети Сьогодні,
Вчора та За весь час.

**Acceptance Scenarios**:

1. **Given** учасник переглядає asset, **When** він створює task, **Then** asset
   прикріплюється автоматично, нова task одразу відкривається, а task можна призначити собі
   або іншому активному учаснику.
2. **Given** уже створена task, **When** учасник шукає доступні media й обирає одне або
   кілька, **Then** усі вибрані media додаються як вкладення без переміщення чи копіювання у
   Drive і без фіксованого продуктового ліміту кількості.
3. **Given** у task-просторі відкрите ліве дерево дозволених матеріалів, **When** учасник
   перетягує один або багато assets у task, **Then** кожен унікальний asset прикріплюється
   один раз, а початкове розташування й metadata не змінюються.
4. **Given** task має вкладені video, image/static і landing assets, **When** task
   відображається, **Then** вкладення показуються компактною плитковою сіткою з малими
   правдивими preview або явним unavailable-станом; video preview використовує кадр на
   1-й секунді, а не перший кадр.
5. **Given** нова task зі статусом To do, **When** вона створена, **Then** її прогрес має
   Max = 100, Value = 0 і ще не вважається вручну встановленим.
6. **Given** task без ручної зміни progress, **When** її переводять у Done, **Then** Value
   автоматично стає рівним Max.
7. **Given** користувач хоча б раз явно змінив progress, **When** status надалі змінюється,
   **Then** Soty не перезаписує вручну встановлене значення.
8. **Given** Max = 9 і Value = 6, **When** task показується на картці, **Then** видно 6/9,
   дискретний slider і зелену завершену та червону незавершену частини.
9. **Given** у task-просторі є tasks за різні дні, **When** учасник обирає дату в календарі
   або натискає Сьогодні, Вчора чи За весь час, **Then** показуються лише tasks, створені у
   відповідну локальну календарну дату, або всі tasks для останнього пресета.

### User Story 6 - Швидко передати Drive-посилання (Priority: P3)

Учасник копіює з картки asset саме його Google Drive URL. Якщо доступ за посиланням уже
відкритий, URL копіюється одразу. Якщо доступ закритий, Soty пропонує відкрити його та може
запам'ятати безпечний вибір цього користувача для цієї команди. Жоден файл не стає
публічним до фактичної дії Share/Copy link.

**Why this priority**: Команда може передати матеріал дизайнеру або teammate без
скачування та повторного завантаження, зберігаючи контроль над зміною доступу.

**Independent Test**: Перевірити public і restricted assets, погодитися на відкриття
доступу з Remember my choice, повторити для другого restricted asset, скинути preference в
Settings і підтвердити, що жоден нешерений asset не змінив permissions.

**Acceptance Scenarios**:

1. **Given** Anyone with the link уже активний, **When** учасник натискає Copy link,
   **Then** копіюється фактичний Google Drive URL без зайвого підтвердження.
2. **Given** доступ закритий і учасник може ним керувати, **When** він натискає Copy link,
   **Then** Soty пропонує Allow anyone with the link і необов'язкове Remember my choice.
3. **Given** учасник погодився та запам'ятав вибір, **When** він надалі копіює restricted
   asset у тій самій команді, **Then** Soty перевіряє поточні permissions, за потреби
   відкриває link access і копіює URL без повторного prompt.
4. **Given** користувач скинув preference або не погодився, **When** він завершує дію,
   **Then** закритий доступ не змінюється без нового явного дозволу.

### User Story 7 - Бачити окремий внесок автоматики й людей (Priority: P4)

Soty вже під час цього інкременту фіксує, хто виконав локальні processing jobs і хто
виконав людські командні дії. Ці дві категорії не змішуються в один performance score.
Майбутній необов'язковий екран Busy Bees зможе показати легкі achievements, не заважаючи
основній роботі.

**Why this priority**: Дані потрібно збирати з правильною семантикою від початку, навіть
якщо декоративний UI з'явиться пізніше.

**Independent Test**: Виконати одним учасником транскрипцію через Local Agent, іншим —
відбір Finds і завершення task; перевірити, що внески відображені у двох окремих категоріях
і жодна подія не містить матеріалів, транскриптів або приватних шляхів.

**Acceptance Scenarios**:

1. **Given** Local Agent успішно завершив operation, **When** внесок зафіксовано, **Then**
   він належить до Local Processing і пов'язаний з actor та Agent без оцінювання людської
   продуктивності.
2. **Given** учасник додав asset, відібрав find або завершив task, **When** внесок
   зафіксовано, **Then** він належить до Human Activity, а не до processing counts.
3. **Given** дані внеску доступні для майбутнього Busy Bees, **When** обчислюються прості
   achievements, **Then** вони не створюють валюту, магазин або обов'язковий leaderboard.

### Edge Cases

- Порожня або частково невдала upload-пачка не створює порожніх матеріалів; успішні файли
  лишаються доступними, а помилки показуються по конкретних елементах.
- Rate limit або перевищення квоти Google Drive під час масового завантаження чи розподіленої
  обробки не потребує окремого throttling: Soty покладається на resumable-сесії та поелементні
  повтори, показує відмову через квоту як поелементну помилку, придатну до безпечного повтору,
  і не подає пачку чи operation як успішну.
- Однакові назви в цільовій Drive-папці ніколи не призводять до тихої заміни; застосовується
  наявний явний вибір конфлікту з feature 001.
- Невідомий offer, language або type отримує контрольоване Unknown-розміщення, щоб asset
  залишався видимим і придатним до подальшого виправлення.
- GEO залишається окремим контрольованим metadata-полем і не додає ще один рівень папок;
  це не змішує значення GEO та language.
- Якщо ручну мову встановлено, поки автоматичне визначення ще тривало, пізній автоматичний
  результат відкидається.
- Для відео без достатнього мовлення на першому короткому фрагменті Soty перевіряє ще один
  короткий фрагмент; тиша, шум або неоднозначне багатомовне мовлення завершуються Unknown.
- HTML без достатнього читабельного тексту не класифікується за випадковими атрибутами,
  filenames або media; language залишається Unknown.
- Asset з'являється в Finds/Library навіть тоді, коли thumbnail, preview або language ще
  готуються; кожен незавершений результат має окремий правдивий стан.
- Відсутній, paused, застарілий або offline Local Agent не запускає важку роботу в іншому
  середовищі непомітно для користувача; jobs лишаються або повертаються до черги.
- Зміна bytes або версії джерела робить залежні результати неактуальними, але не стирає
  історію й не інвалідовує незалежні operations.
- Якщо asset переміщено під час processing, результат прив'язується до стабільної
  ідентичності та чинної версії asset, а не записується до старого шляху.
- Якщо task assignee видалений із команди, task лишається видимою уповноваженим учасникам і
  переходить у стан без активного assignee.
- Повторне прикріплення того самого asset до однієї task не створює дубль; один multi-drag
  може містити довільну кількість дозволених елементів, а недоступні елементи відхиляються
  окремо без втрати успішних вкладень.
- Переміщення або перейменування прикріпленого asset не розриває task-вкладення; якщо asset
  видалено чи доступ втрачено, task лишається, а плитка показує правдивий unavailable-стан.
- Для відео коротшого за одну секунду preview використовує останній доступний кадр; для
  відео тривалістю щонайменше секунду перший кадр не може підмінити кадр із позначки 1 с.
- Якщо cached transcript належить попередній версії відео, картка не видає його за чинний:
  View/Copy замінюються на явний stale-стан і дію повторного транскрибування.
- Якщо Max зменшують нижче поточного Value, Soty не обрізає progress мовчки, а вимагає
  явно вибрати допустиме нове Value або скасувати зміну.
- Перехід із Done назад до іншого status не зменшує progress автоматично; status ніколи не
  виводиться з progress без явної дії користувача.
- Користувач без дозволу змінювати Drive sharing може скопіювати вже доступний public URL,
  але не може відкрити restricted asset для Anyone with the link.
- Втрата можливості змінити Drive permission після Remember my choice завершується
  правдивою відмовою; preference не обходить актуальну перевірку дозволів.
- Папка, landing package і його sidecar-файли переміщуються як одна логічна група або
  лишаються в попередньому узгодженому стані; часткове переміщення не показується як успіх.

## Requirements _(mandatory)_

### Functional Requirements

#### Канонічне сховище та структура

- **FR-001**: Soty MUST використовувати наявний командний простір, членство, дозволи та
  активну Google Drive кореневу папку з feature 001 як передумову цієї функції.
- **FR-002**: Google Drive MUST залишатися канонічним фізичним сховищем усіх assets і
  пов'язаних файлових результатів; Soty MUST NOT створювати паралельну віртуальну файлову
  ієрархію.
- **FR-003**: Канонічний фізичний шлях asset MUST мати не більше чотирьох structural
  сегментів під коренем команди в порядку Stage / Offer / Language / Type.
- **FR-003a**: Канонічну папку Offer визначає нормалізований ключ, нечутливий до регістру та
  зайвих пробілів; варіанти тієї самої назви Offer за регістром/пробілами MUST розділяти одну
  канонічну папку. Перший канонічний display-value MUST зберігатися, а наступні варіанти
  MUST NOT тихо його замінювати. Дві справді різні назви Offer дають різні ключі й різні папки,
  тож окремий суфікс розрізнення не потрібен.
- **FR-004**: Stage MUST підтримувати рівно два робочі значення цього інкременту: Finds і
  Library.
- **FR-004a**: Type MUST бути закритим системним набором із шести канонічних material-category
  значень: Video, Image, Archive, Transcript, Landing і Other. Тип визначається автоматично; файл,
  що не належить до жодної конкретної категорії, отримує catch-all значення Other, тоді як
  контрольований Unknown (розміщення з FR-022) застосовується лише коли категорії ще немає
  (наприклад, до класифікації). Другорядні теги лишаються metadata й MUST NOT створювати
  Type-значень або папок.
- **FR-005**: Doctor, UGC, Good Hook, Competitor та інші другорядні теги MUST зберігатися як
  metadata Soty й MUST NOT автоматично створювати Drive-папки.
- **FR-006**: GEO MUST залишатися окремим контрольованим metadata-полем відповідно до
  feature 001 і MUST NOT додавати п'ятий структурний рівень.
- **FR-007**: Підтверджена зміна Stage, Offer, Language або Type MUST фізично переміщувати
  asset та його sidecars до нового канонічного шляху.
- **FR-008**: Structural move MUST зберігати стабільну ідентичність asset, metadata,
  provenance, tasks і готові results та MUST NOT створювати копію джерела.
- **FR-009**: Soty MUST узгоджувати дозволені зовнішні переміщення й перейменування в Drive
  з каталогом, не створюючи другого логічного asset для того самого фізичного об'єкта.
- **FR-010**: Кожне створення, переміщення, sharing або processing-запис MUST повторно
  перевіряти актуальні Soty permissions і можливості підключеного Drive.

#### Bulk Upload, Finds і Library

- **FR-011**: Учасник із дозволом на завантаження MUST мати змогу вибрати щонайменше 100
  змішаних підтримуваних assets в одній upload-пачці в межах опублікованих file-size
  обмежень.
- **FR-012**: Перед стартом upload Soty MUST дозволяти один раз задати для всієї пачки
  Destination, Offer/Vertical, GEO і Language або Auto detect.
- **FR-013**: Явно задане batch-значення MUST застосовуватися до кожного asset пачки, якщо
  користувач не виправить конкретний asset пізніше.
- **FR-014**: Soty MUST показувати загальний прогрес пачки й окремий результат кожного asset
  та MUST NOT подавати частково невдалу пачку як повністю успішну.
- **FR-015**: Кожен успішно збережений asset MUST ставати доступним у вибраному Stage, не
  очікуючи завершення решти пачки.
- **FR-016**: Finds MUST приймати велику кількість сирих матеріалів без обов'язкового
  пофайлового заповнення другорядних metadata.
- **FR-017**: Наявність asset у Finds MUST NOT означати його відбір, заплановане
  використання або створення task.
- **FR-018**: Уповноважений учасник MUST мати змогу одним bulk action перемістити один або
  кілька assets із Finds до Library.
- **FR-019**: Уповноважений учасник MUST мати змогу повернути один або кілька assets із
  Library до Finds.
- **FR-020**: Переходи Finds ↔ Library MUST переміщувати наявні фізичні assets у Drive без
  створення дублікатів.
- **FR-021**: Після upload учасник із дозволом керувати metadata MUST мати змогу виправити
  Offer, GEO, Language, Type і другорядні tags; structural зміни MUST виконувати FR-007.
- **FR-022**: Невідоме structural значення MUST мати явний контрольований варіант Unknown,
  який зберігає asset видимим для подальшого виправлення.
- **FR-023**: Конфлікт, відмова або обрив structural move MUST залишати Soty й Drive в
  останньому узгодженому стані або показувати явний стан відновлення; хибний успіх
  заборонений.

#### Автоматичне визначення й легка обробка

- **FR-024**: Якщо Language задано вручну до або під час upload, Soty MUST не запускати або
  зупинити автоматичне визначення та MUST відкидати пізній автоматичний результат.
- **FR-025**: Для лендинга без заданої Language Soty MUST визначати основну мову з
  доступного читабельного HTML/текстового вмісту локальним негенеративним способом.
- **FR-026**: Для відео без заданої Language Soty MUST спочатку аналізувати приблизно перші
  5–8 секунд доступного мовлення локально, без транскрибування всього ролика.
- **FR-027**: Якщо перший короткий фрагмент не містить достатнього мовлення, Soty MUST
  автоматично перевірити ще один короткий фрагмент з іншої частини відео.
- **FR-028**: За недостатньої впевненості language detection MUST завершуватися значенням
  Unknown, а не найімовірнішим непідтвердженим значенням.
- **FR-029**: Автоматично визначена Language MUST бути видимою й доступною для ручного
  виправлення; ручне виправлення надалі має пріоритет.
- **FR-030**: Після upload Soty MUST автоматично зібрати базові metadata та створити
  thumbnail для підтримуваного creative без запуску повної важкої processing-черги.
- **FR-031**: Для підтримуваного лендинга Soty MUST знайти entry page і поставити створення
  первинного preview в негайну легку обробку, незалежну від Process Library.
- **FR-032**: Asset MUST бути показаний у Finds/Library до завершення thumbnail, language
  або preview з окремим правдивим станом кожної незавершеної operation.
- **FR-033**: Повна транскрипція, переклад повного тексту й оптимізація landing media MUST
  NOT запускатися автоматично лише через upload.

#### Process Library і спільні results

- **FR-034**: Soty MUST надавати явну дію Process Library лише учаснику з актуальним
  дозволом на processing.
- **FR-035**: Перед підтвердженням старту Soty MUST просканувати доступні assets і показати
  counts відсутніх jobs щонайменше для transcription, translation та landing optimization.
- **FR-036**: Scan MUST виключати operations із чинним готовим результатом для поточної
  версії джерела й потрібного цільового варіанта.
- **FR-037**: Повторне натискання Process Library MUST бути безпечним та додавати тільки
  відсутню або явно неуспішну роботу без дублювання готових results.
- **FR-038**: Кожна processing operation MUST мати окремий стан щонайменше pending, leased,
  running, ready, failed, cancelled, stale і skipped.
- **FR-039**: Ідентичність operation MUST включати стабільний asset, версію джерела, вид
  operation і, де потрібно, цільову мову або варіант результату.
- **FR-040**: Повна video transcription MUST зберігати текст мовою оригіналу.
- **FR-041**: Для активної мови інтерфейсу Process Library MUST створювати відсутній
  переклад повного транскрипту; переклади для різних target languages є окремими спільними
  operations.
- **FR-042**: Оригінальний транскрипт і переклади MUST фізично зберігатися поряд із asset у
  Drive як прості текстові UTF-8 документи (.txt) без часових міток, під детермінованими,
  відмінними іменами, що містять відповідний language code.
- **FR-042a**: Кожен оригінальний transcript-документ MUST мати явний зв'язок із одним
  source-video та конкретною source version; для однієї чинної версії відео Soty MUST
  визначати не більше одного канонічного оригінального transcript-sidecar.
- **FR-042b**: Успішне переміщення, відновлюване видалення або відновлення source-video MUST
  застосовувати ту саму lifecycle-дію до всіх його чинних transcript і translation
  sidecars. Групова дія MUST завершуватися правдивим узгодженим станом або явним станом
  відновлення та MUST NOT показувати частковий результат як успіх.
- **FR-042c**: Переміщення source-video без зміни bytes MUST зберігати чинність cached text
  і sidecar-зв'язків; зміна source version MUST позначати попередній cached text як stale до
  створення нового чинного результату.
- **FR-043**: Картка відео MUST дозволяти перемикати Original і доступні переклади та
  копіювати показаний текст однією явною дією.
- **FR-043a**: Якщо чинний original transcript-sidecar має кешований текст, картка відео
  MUST показувати дію «Переглянути текст», яка відкриває цей cached text без запуску нової
  heavy operation.
- **FR-043b**: Якщо показаний cached text готовий, картка відео MUST показувати окрему дію
  «Скопіювати текст», що копіює саме поточний видимий original або translation variant.
- **FR-043c**: Якщо чинного cached text немає або він stale, картка відео MUST замість Copy
  показувати дію запуску transcription; Copy MUST бути недоступним до готового тексту.
- **FR-044**: Готовий result одного teammate MUST бути доступний усім уповноваженим
  учасникам і MUST запобігати повторній тій самій важкій operation на інших комп'ютерах.
- **FR-045**: Landing optimization MUST оптимізувати підтримувані зображення, відео й інші
  важкі media, оновити залежні links та перевірити, що результат лишається робочим.
- **FR-046**: Оптимізований лендинг MUST за замовчуванням зберігатися як окремий похідний
  material із provenance та без неявного перезапису оригіналу.
- **FR-047**: Чинний preview MUST NOT генеруватися повторно під час Process Library без
  зміни source version, preset або явної потреби відновлення.
- **FR-048**: Зміна source version MUST позначати залежні results stale і повертати лише
  потрібні operations до майбутнього scan, не видаляючи audit/history.

#### Розподілена локальна обробка

- **FR-049**: Кілька сумісних Local Agents однієї команди MUST мати змогу одночасно
  забирати різні доступні operations.
- **FR-050**: Тимчасове закріплення MUST застосовуватися до конкретної operation, а не до
  всього asset або конкретного користувача назавжди.
- **FR-051**: Активний Agent MUST регулярно підтверджувати продовження закріплення, а
  відсутність підтвердження MUST робити operation доступною іншому Agent після короткого
  обмеженого timeout.
- **FR-052**: Pause, shutdown, crash, втрата живлення або зв'язку MUST NOT залишати
  operation заблокованою після завершення timeout.
- **FR-053**: Перед фінальним прийняттям result Soty MUST повторно перевірити чинну source
  version, потребу operation, дозвіл і відсутність уже готового чинного result.
- **FR-054**: Для конкурентних чинних results MUST діяти правило first valid result wins;
  пізніший result MUST NOT перезаписувати прийнятий і MUST завершуватися як skipped.
- **FR-055**: Невдала, скасована або прострочена спроба MUST бути придатною до безпечного
  повтору без видавання часткового artifact за готовий.
- **FR-056**: Користувач MUST бачити локальний прогрес, pause/cancel result і причину
  skipped/failed operation без показу секретів або приватних filesystem paths.

#### Легкі Tasks і Universal Progress

- **FR-057**: Уповноважений учасник MUST мати змогу створити task безпосередньо з creative
  або landing, і вибраний asset MUST прикріплюватися автоматично.
- **FR-057a**: Tasks MUST мати окремий зручний team-scoped простір, відокремлений від
  Finds/Library, але доступний із командного workspace не більш ніж за одну основну дію.
- **FR-057b**: Після створення task уповноважений учасник MUST мати змогу знайти через
  permission-filtered пошук і прикріпити одну або багато доступних media; Soty MUST NOT
  встановлювати фіксований продуктовий максимум вкладень, а повторний вибір того самого
  asset MUST бути ідемпотентним.
- **FR-057c**: Task-простір MUST показувати доступну файлову ієрархію ліворуч і дозволяти
  перетягнути з неї до task один або багато assets за одну дію з окремим результатом для
  кожного недоступного елемента.
- **FR-057d**: Task attachment MUST бути посиланням на стабільну ідентичність material і
  MUST NOT переміщувати, копіювати або змінювати Drive-файл, його metadata чи каталогове
  розташування.
- **FR-057e**: Усі task attachments MUST відображатися компактними плитками з назвою,
  категорією та малим правдивим preview для підтримуваних landing, static/image і video;
  непідтримуваний або недоступний preview MUST мати явний fallback без false-ready стану.
- **FR-057f**: Video attachment preview MUST показувати кадр на часовій позначці 1 секунда,
  а не перший кадр; для коротшого відео допускається останній доступний кадр.
- **FR-057g**: Asset card MUST мати видиму keyboard-accessible дію Create Task; вона MUST
  створити й одразу відкрити нову task з уже прикріпленим asset без залежності від
  контекстного меню правої кнопки.
- **FR-057h**: Task-простір MUST фільтрувати tasks за локальною календарною датою створення
  через date picker і швидкі пресети Сьогодні, Вчора та За весь час; активний фільтр MUST
  бути видимим і не змінювати самі tasks.
- **FR-058**: Task MUST підтримувати одного активного assignee з вибором себе або іншого
  активного учасника команди та коротку description/note.
- **FR-059**: Базовий workflow task MUST містити To do, In progress і Done без обов'язкових
  спринтів, епіків, залежностей чи інших project-management механік.
- **FR-060**: Нова task у To do MUST мати Max = 100, Value = 0 і ознаку, що progress ще не
  змінювався вручну.
- **FR-061**: Картка task MUST показувати поточне Value над компактним дискретним slider;
  завершена частина шкали має бути зеленою, а незавершена — червоною.
- **FR-062**: Учасник із дозволом редагувати task MUST мати змогу встановити для неї
  власний додатний цілий Max від 1 до 10 000 та цілий Value від 0 до Max.
- **FR-063**: Після першої явної зміни Value Soty MUST назавжди позначити progress цієї task
  як вручну керований, навіть якщо вибране значення дорівнює поточному.
- **FR-064**: Перехід task у Done MUST автоматично встановити Value = Max лише тоді, коли
  progress ще жодного разу не змінювався вручну.
- **FR-065**: Зміна status після ручного progress MUST NOT змінювати Value; зміна progress
  MUST NOT автоматично змінювати status.
- **FR-066**: Зменшення Max нижче Value MUST вимагати явного вибору нового допустимого
  Value або скасування; мовчазне обрізання заборонено.
- **FR-067**: Видалення або деактивація assignee MUST зберігати task та її історію й
  переводити її до стану без активного assignee.
- **FR-068**: Create Task, зміна status і коригування progress MUST бути доступні з
  відповідної asset/task card не більш ніж за 1–2 основні дії.

#### Quick Share через Google Drive

- **FR-069**: Asset card MUST надавати Copy link, Open in Drive і дозволений Download.
- **FR-070**: Copy link MUST працювати з фактичним Google Drive URL саме вибраного asset, а
  не з внутрішнім Soty URL.
- **FR-071**: Під час кожного Copy link Soty MUST перевіряти поточний link-access state.
- **FR-072**: Якщо Anyone with the link уже активний, Soty MUST скопіювати URL без зміни
  permissions.
- **FR-073**: Якщо access закритий, Soty MUST запропонувати Allow anyone with the link та
  окреме необов'язкове Remember my choice до будь-якої зміни permission.
- **FR-074**: Remembered choice MUST бути scoped до користувача й команди, MUST лише
  пропускати повторний prompt і MUST NOT обходити актуальні Soty/Drive permission checks.
- **FR-075**: Після remembered approval майбутній Copy link MUST за потреби відкрити link
  access тільки вибраного asset і скопіювати URL.
- **FR-076**: Користувач MUST мати змогу переглянути та скинути remembered choice у
  Settings.
- **FR-077**: Soty MUST NOT автоматично відкривати sharing для всієї Library, папки,
  upload-пачки або asset, для якого користувач не виконав Copy link/Share.
- **FR-078**: Користувач без дозволу змінювати sharing MUST NOT відкрити restricted access;
  відмова MUST залишити permission незмінним і не повідомляти хибне Copied.

#### Team Activity / Busy Bees

- **FR-079**: Для кожної успішної локальної processing operation Soty MUST зафіксувати
  actor, Local Agent, вид operation, час і outcome без вмісту asset.
- **FR-080**: Soty MUST окремо фіксувати Human Activity щонайменше для доданих assets,
  вибраних Finds і завершених tasks.
- **FR-081**: Local Processing contribution і Human Activity MUST залишатися окремими
  категоріями та MUST NOT зводитися до одного performance score.
- **FR-082**: Contribution records MUST NOT містити транскрипти, landing content, filenames,
  приватні Drive/filesystem paths, share URLs, access tokens або інші секрети.
- **FR-083**: Майбутній Busy Bees UI MAY показувати компактні необов'язкові achievements на
  основі окремих counts, але MUST NOT додавати валюту, магазин або нав'язливий leaderboard.
- **FR-084**: Відсутність Busy Bees UI в першому delivery increment MUST NOT блокувати
  коректний збір і подальше агрегування contribution records.

#### Наскрізні UX-обмеження

- **FR-085**: Ручне рішення користувача MUST мати пріоритет над автоматично визначеним
  значенням у всіх конфліктах цієї функції.
- **FR-086**: Soty MUST виконувати language detection і детерміновану організацію локально
  та MUST NOT надсилати вміст asset до зовнішнього генеративного сервісу для цих задач.
- **FR-087**: Важка processing-робота MUST запускатися лише після явної дії користувача;
  легкі post-upload operations із FR-030–FR-032 є єдиним автоматичним винятком.
- **FR-088**: Move to Finds/Library, Create Task, зміна status/progress, Copy link, Open in
  Drive і Download MUST бути доступні з asset/task card або поточного selection не більш
  ніж за 1–2 основні дії, крім одноразового permission prompt для restricted sharing.

### Межі функції

**Входить до цього feature**:

- Канонічна чотирирівнева Drive-організація Finds/Library.
- Bulk Upload зі спільними параметрами та локальним визначенням мови.
- Легка post-upload обробка й негайний landing preview.
- Явний Process Library, спільні results і розподілена обробка Local Agents.
- Повні транскрипти, target-language переклади та оптимізовані landing results.
- Прив'язані до відео transcript-sidecars із груповим move/trash/restore та cached
  View/Copy/Transcribe actions.
- Окремий простір легких tasks із multi-attachments, пошуком, drag-and-drop, плитковими
  preview, календарним фільтром, статусами й універсальним progress.
- Quick Share фактичного Google Drive URL з permission-on-demand.
- Розділені contribution records для майбутнього Busy Bees.

**Не входить до цього feature**:

- Заміна Google Drive власною файловою системою або підтримка іншого cloud storage.
- Повноцінний project manager: спринти, епіки, залежності, складні workflow, тайм-трекінг,
  бюджети чи ресурсне планування.
- Автоматичний запуск важкої обробки після кожного upload.
- Хмарне генеративне AI-класифікування для задач, які надійно вирішуються локально.
- Автоматичне відкриття public access для всієї Library або анонімний Soty-портал.
- Валюти, магазини, змішаний performance score або обов'язковий leaderboard.
- Повний Busy Bees UI; цей інкремент гарантує його коректну data foundation.

### Key Entities

- **Team Space**: Наявний командний контекст із членством, дозволами й одним активним
  Google Drive root.
- **Asset**: Стабільно ідентифікований creative, landing, media file або package з поточною
  source version, physical Drive location, category та доступністю.
- **Structural Placement**: Stage, Offer, Language і Type (Type ∈ Video | Image | Archive |
  Transcript | Landing | Other, інакше Unknown), що разом визначають канонічний Drive path asset.
- **Asset Metadata**: Окремі керовані атрибути GEO та другорядні tags, які не створюють
  додаткових папок.
- **Upload Batch**: Група вибраних assets зі спільними параметрами, загальним progress та
  окремим outcome кожного елемента.
- **Processing Operation**: Ідемпотентна потреба, визначена asset, source version,
  operation kind і target variant, зі станом та чинним result.
- **Job Attempt**: Конкретна спроба Local Agent виконати operation з тимчасовим
  закріпленням, heartbeat, actor, progress та outcome.
- **Processing Result**: Спільний чинний artifact або metadata-result із provenance,
  language/preset variant та source version.
- **Task**: Легка одиниця командної роботи з нулем або багатьма посилальними media-
  вкладеннями, assignee, note, status, датою створення та progress scale.
- **Task Attachment**: Ідемпотентний зв'язок task зі стабільним командним material, який
  не змінює фізичне розташування asset і зберігається після його move/rename.
- **Task Progress**: Цілі Max і Value та незворотна ознака, чи користувач уже керував
  progress вручну.
- **Share Preference**: Скидуваний вибір конкретного користувача в конкретній команді щодо
  автоматичного permission-on-demand під час майбутніх Copy link.
- **Contribution Record**: Безконтентна подія Local Processing або Human Activity, що
  зберігає категорію, actor, час, action kind та outcome.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: У модерованому тесті щонайменше 18 із 20 нових учасників без допомоги
  завантажують 100 змішаних assets до Finds, задавши Offer і GEO рівно один раз, без
  відкриття пофайлових форм.
- **SC-002**: Для контрольного набору з 500 uploads, corrections і переходів
  Finds ↔ Library у 100% успішних операцій Soty та прямий перегляд Drive показують один
  фізичний asset у правильному Stage / Offer / Language / Type path; немає дублікатів,
  загублених sidecars або хибного успіху.
- **SC-003**: Після успішного збереження bytes щонайменше 95% assets з'являються в
  Finds/Library з базовими metadata або правдивим проміжним станом не пізніше ніж за
  3 секунди; первинний preview 95% підтримуваних лендингів стає доступним або показує
  типізовану причину очікування не пізніше ніж за 15 секунд за доступного Local Agent.
- **SC-004**: На версійованому наборі щонайменше з 20 чітких одномовних landing/video
  прикладів для кожної підтримуваної language щонайменше 95% отримують правильне значення;
  на окремому наборі з 50 тихих, шумних або неоднозначних прикладів 50 із 50 не отримують
  впевненої неправильної language та завершуються Unknown.
- **SC-005**: У 100% тестів із вручну заданою або виправленою Language автоматичний
  результат не запускається або не перезаписує ручне значення, включно з пізнім
  завершенням конкурентного detection.
- **SC-006**: Для Library з 10 000 assets повторний scan Process Library показує однакові
  counts за незмінних даних, виключає 100% чинних ready operations і не створює жодного
  другого result після трьох послідовних запусків.
- **SC-007**: У контрольному запуску 1 000 operations на трьох Local Agents кожна operation
  має не більше одного прийнятого ready result; 100% jobs з примусово зупиненого Agent
  повертаються до доступної черги не пізніше ніж за 2 хвилини, а жоден пізній result не
  перезаписує перший чинний.
- **SC-008**: Учасник без Local Agent відкриває 100% готових транскриптів, перекладів та
  оптимізованих results, створених teammate, без повторного локального processing; для
  stale або відсутнього result немає хибного стану ready.
- **SC-009**: Щонайменше 18 із 20 учасників без підказок створюють task із asset,
  додають щонайменше десять різних media одним multi-drag і пошуком, призначають teammate,
  задають custom progress, переводять status і знаходять task через потрібну дату не пізніше
  ніж за 90 секунд; у 100% перевірок ручне значення не перезаписується status automation.
- **SC-010**: Для public asset Copy link завершується однією основною дією; після
  remembered approval restricted asset тієї самої команди відкривається on-demand і URL
  копіюється однією основною дією у 100% дозволених перевірок.
- **SC-011**: У 100% security acceptance tests Copy link не змінює permission іншого asset,
  folder або Library, не обходить відкликаний дозвіл і не повідомляє Copied після
  невдалої зміни access.
- **SC-012**: У контрольному наборі contribution events 100% processing jobs і human
  actions потрапляють до різних категорій, а жодна подія не містить content, filename,
  private path, Drive URL або secret.
- **SC-013**: Щонайменше 18 із 20 учасників, які бачать лише Google Drive без Soty,
  знаходять заданий asset через Stage / Offer / Language / Type не пізніше ніж за
  60 секунд.
- **SC-014**: У 100 перевірках task із 1–100 вкладеннями створення, search attach,
  multi-drag, повторне прикріплення, move і rename не змінюють кількість чи розташування
  фізичних Drive-файлів; кожен унікальний дозволений asset має рівно одну плитку, а дата-
  фільтри не пропускають task з іншої локальної календарної дати.
- **SC-015**: У 100% перевірок video тривалістю щонайменше одну секунду thumbnail не
  використовує початковий кадр, а View/Copy не запускають повторну transcription. У 100%
  move/trash/restore перевірок video та його чинні transcript-sidecars сходяться до одного
  узгодженого lifecycle-стану без false success.

## Assumptions

- Feature 001 уже надає команди, членство, ролі, permission checks, одну активну Google
  Drive root, каталог, metadata, базові file operations та processing permission.
- Feature 004 уже надає командну галерею й безпечний landing preview; цей feature розширює,
  а не дублює їх.
- Перший release використовує рівно чотири physical structural segments:
  Stage / Offer / Language / Type. GEO зберігається окремо як контрольоване metadata, щоб
  не поглиблювати Drive та не змішувати країну з мовою.
- Offer лишається team-defined value, але його physical folder representation має бути
  однозначним і безпечним; канонічний ключ папки нечутливий до регістру та пробілів, тож
  варіанти однієї назви ділять одну папку без тихої заміни display-value, а справді різні
  офери мають різні папки.
- Sidecar transcripts і translation files є частиною логічної asset-групи та слідують за
  джерелом під час будь-якого дозволеного move, recoverable trash і restore; операції над
  групою зберігають історію й допускають явне відновлення після зовнішнього partial failure.
- Task attachments є посиланнями на наявні materials, а не копіями. У першому інкременті
  для них немає штучного продуктового максимуму; практичні paging/performance limits не
  змінюють семантику «прикріпити скільки потрібно».
- Task create/update/attach використовує наявний командний дозвіл `edit`, а читання tasks і
  їхніх вкладень — `view`; прихований material не можна знайти чи прикріпити через task UI.
- Календар task-простору інтерпретує дату створення у локальній часовій зоні поточного
  користувача; пресети Сьогодні та Вчора використовують ту саму зону.
- Для preview відео тривалістю щонайменше секунду канонічна позначка — 1.0 с; для коротших
  файлів використовується останній доступний кадр без повідомлення false-ready.
- Переклад створюється для активної interface language учасника, який запускає scan; інша
  target language додається пізніше як окрема відсутня operation й стає спільною.
- Якщо interface language збігається з original language, окремий тотожний translation
  artifact не створюється.
- Custom task Max обмежено цілим діапазоном 1–10 000 для придатного discrete control; це не
  визначає семантику шкали й не змушує команду використовувати відсотки.
- Remember my choice для sharing зберігається на рівні user + team, а не глобально для всіх
  команд, і ніколи не замінює актуальну перевірку permission.
- Heavy processing вимагає сумісного Local Agent; якщо жодного немає, Library і готові
  shared results залишаються доступними, а нові jobs мають правдивий waiting state.
- Source version є частиною чинності processing result; переміщення без зміни bytes не
  робить result stale, а зміна source content робить.
- Усі основні дії дотримуються наявних team permissions і conflict rules feature 001.
- Перший delivery збирає Busy Bees data foundation; окремий декоративний екран та
  achievements можуть бути заплановані наступним інкрементом.
