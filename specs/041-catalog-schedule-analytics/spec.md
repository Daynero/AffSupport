# Catalog schedule analytics

**Status**: Closed — implemented and verified locally, 2026-10-20.

## Outcome

The owner can request a visual report for a rolling week, another supported period, or a single user and immediately compare schedule popularity, daily trends and confirmed changes such as daily → hourly. Reports are generated by the existing read-only analytics CLI as JSON and an optional self-contained local HTML artifact. No analytics dashboard is added to customer workflows.

## Evidence and counting

- Authoritative transaction-backed history captures committed interval, civil schedule and five update options across individual, legacy, bulk, creation and undo writers. Failed/rolled-back/no-op writes do not become selections; scheduled execution and next-due advancement do not become preference changes.
- Record opaque actor/team/catalog IDs, bounded settings and server timestamps only. Never collect catalog names, URLs, content, provider data or credentials. System/unknown actors remain separate from users.
- The first observation of an existing catalog is a baseline, not a historical selection or its creation date. Historical preferences before observation are unknown. A new first observation is also distinguished from a change.
- Current popularity counts active catalogs as of the requested end instant. Selection popularity counts confirmed interval transitions in the window and distinct actors separately. One actor can select several intervals and appears once per interval in distinct-user counts.
- Normalize equivalent elapsed intervals for comparisons, retain raw interval keys and distinguish calendar cadence from clock/weekday edits. Per-user timelines retain separate catalog tracks rather than inventing one preference for a shared workspace.
- Include disable/re-enable, custom hours, time/weekday settings, option adoption, first/latest observed settings states, transitions and daily trends. State denominators, UTC day boundaries, unknown attribution and bounded timeline truncation.

## Diagnostic coverage

Reuse correlated catalog_manager browser flows for attempted, confirmed, failed, cancelled and visible edits. The durable journal proves commit but cannot prove UI visibility or capture unsaved intent. Reports must expose collection start, actor gaps, unavailable schema and truncated evidence; absence before observation is never a zero. Read-only diagnosis and capability inventory document both sources.

## Acceptance

1. Fixture users who move daily → hourly → off produce ordered per-catalog tracks, correct transition counts and distinct actor denominators.
2. Bulk and legacy writes are visible, one atomic schedule edit produces one final state, rollback/no-op/worker due advancement produce no change event.
3. Baseline, null actor, archived/deleted catalogs, carry-in state, as-of cutoff, equivalent intervals, boolean-only edits and scope filtering are tested.
4. Population aggregates are not silently capped; user/timeline limits are explicit. A repeat with the same as-of instant is stable.
5. HTML runs offline, escapes data, has accessible chart/table labels and shows honest empty/partial coverage. Charts explain their units and global versus per-user scope.
6. Beta integration is additive; no production mutation or historical fabrication.
