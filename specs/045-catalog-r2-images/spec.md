# Feature Specification: Публічні зображення каталогу в R2 Standard

**Feature Branch**: не створювалась; специфікація незалежна від поточної гілки

**Created**: 2026-10-27

**Status**: Draft — власник обрав R2 Standard, лише картинки; уточнено імпорт і підказку; готовий до планування

**Input**: Підготувати перехід білих зображень у налаштуваннях каталогу на Cloudflare R2 Standard після порівняння альтернатив. Оцінити 50 користувачів × 15 нових каталогів щодня; повторне використання зображень; 100 товарів і одне відео в каталозі; перезшивання/завантаження та оновлення кожні 12 годин. У кошторисі старі каталоги накопичуються й продовжують оновлюватися навіть після типових 7 днів використання.

**Owner decision, 2026-10-27**: Цілимось у R2 Standard тільки для картинок. У налаштуваннях каталогу Soty можна вказати папку Google Drive або перетягнути локальні зображення. Дія «Проаналізувати й завантажити» розбирає назви, розподіляє картинки за чинним словником і публікує їх; надалі продукт використовує компактний словник посилань та відповідностей. Потрібне людське пояснення, чому використовується одяг і які параметри міксуються, та прихований за посиланням із копіюванням промпт для агента: квадратні картинки 1:1, лише одяг, без брендів, із правильними назвами. Це уточнення специфікації, не запит на реалізацію. Подальше уточнення: звичайні картинки без розпізнаваних назв теж завантажуються й вибираються випадково без зіставлення; це потрібно пояснити в підказці.

## User Scenarios & Testing _(mandatory)_

### User Story 1 — Один раз опублікувати вибрані картинки (Priority: P1)

Учасник із чинним правом керувати налаштуваннями вибирає папку підключеного Google Drive або перетягує локальні файли в секцію картинок. Після натискання «Проаналізувати й завантажити» Soty розпізнає тип одягу та колір із назв, розподіляє придатні картинки й готує публічні копії. Власний комп'ютер із запущеним агентом для цього не потрібен. Сам вибір джерела ще не публікує байти.

**Why this priority**: стабільне джерело картинок для зовнішнього читача — основна цінність переходу.

**Independent Test**: вибрати контрольний набір картинок; перевірити готовність та отримання їхніх байтів за публічними посиланнями із незалежного неавторизованого клієнта.

**Acceptance Scenarios**:

1. **Given** доступне вибране зображення, **When** завершується його публікація, **Then** воно має готову публічну копію, правильний тип і підтверджені байти; URL не потребує входу або короткочасного токена.
2. **Given** ту саму версію вибрано повторно або одночасно двома учасниками, **When** вони зберігають джерела, **Then** не виникає двох логічних публічних копій цієї версії у просторі.
3. **Given** одна картинка недоступна, **When** інші опубліковані, **Then** показано частковий результат; несправна картинка не видається за готову й не підставляється в новий каталог.
4. **Given** учасник може переглядати, але не публікувати/вивантажувати матеріал, **When** він намагається підготувати публічну копію, **Then** операцію відхилено без публікації байтів.
5. **Given** у папці або серед dropped-файлів є `hoodie_black_001.jpg`, `tank-top_sage_001.png` та `IMG_2031.png`, **When** натиснуто «Проаналізувати й завантажити», **Then** перші два файли потрапляють у правильні групи типу/кольору, останній після перевірки байтів завантажується як «Без класифікації — випадковий вибір», без вигаданого типу/кольору.
6. **Given** локальні файли вибрано, **When** користувач ще не запустив дію або прибрав файл із черги, **Then** він не опублікований; drop має рівноцінний вибір файлів для клавіатури й сенсорного пристрою.
7. **Given** імпорт частково завершений і вкладку закрито, **When** користувач повертається, **Then** готові записи доступні без локальних оригіналів; незавершені локальні файли потрібно вибрати повторно, а повтор не дублює вже готові версії.

### User Story 2 — Створювати й оновлювати каталоги без повторних upload (Priority: P1)

Створення каталогу та фонове оновлення розставляють готові посилання з пулу. Сто товарів і багато каталогів можуть посилатися на ту саму версію зображення; їхня кількість не множить кількість upload.

**Why this priority**: витрати та надійність залежать від повторного використання незмінного результату.

**Independent Test**: створити два каталоги по 100 товарів із того самого контрольного пулу й двічі їх оновити; порівняти посилання та кількість опублікованих копій.

**Acceptance Scenarios**:

1. **Given** готовий пул, **When** створено кілька каталогів, **Then** кожне використання тієї самої картинки має той самий URL без повторного upload і без потреби робити оригінал Drive публічним для нового каталогу.
2. **Given** джерела не змінилися, **When** приходить 12-годинне оновлення, **Then** вибір картинок може змінитися за чинними правилами, але незмінні версії повторно не публікуються.
3. **Given** оновлення потребує непідготовленої версії, **When** підготовка не вдалася, **Then** чинний каталог зберігає попередній працездатний результат; відсутні картинки не стають успішним оновленням.
4. **Given** зовнішній читач відкриває згенерований каталог, **When** читає картинку без авторизації Soty/Drive, **Then** отримує саме потрібне зображення; успіх публікації не позначає підтверджений імпорт зовнішньою платформою.
5. **Given** словник містить лише чорне худі й білу футболку, **When** формуються товари та тексти, **Then** фактичні тип/колір кожного посилання зберігаються; не виникає уявної групи «біле худі» лише через змішування окремих списків типів і кольорів.

### User Story 3 — Перейти без пошкодження старих каталогів (Priority: P1)

Власник простору бачить стан підготовки поточного пулу. Нові каталоги переходять на готові посилання, а існуючі — під час успішного оновлення. Невдале перенесення, зміна джерел або вимкнення нового запису не ламають уже видані посилання.

**Why this priority**: старі каталоги використовуються незалежно від відкритого Soty, а їхній фактичний строк життя невідомий.

**Independent Test**: підготувати legacy-каталог, частково перервати перенесення, повторити й оновити каталог; перевірити до/після з обох зовнішніх посилань.

**Acceptance Scenarios**:

1. **Given** старий каталог із Drive URL, **When** підготовка частково неуспішна, **Then** старі посилання залишаються доступні, а каталог не переписано неповним набором.
2. **Given** усі вибрані для оновлення версії готові, **When** новий результат записано й перевірено, **Then** зафіксовано нові посилання та окремо підтверджено доступність результату каталогу.
3. **Given** джерело змінено або прибрано з пулу, **When** нові каталоги використовують поточні налаштування, **Then** посилання в раніше виданих каталогах не змінюють байтів і не видаляються автоматично.
4. **Given** вимкнено нову публікацію, **When** користувач читає раніше виданий R2 URL, **Then** читання продовжує працювати; вимкнення не є видаленням копій.

### User Story 4 — Розуміти витрати й причину несправності (Priority: P1)

Власник отримує від агента пояснення невдалої підготовки/оновлення та оцінку обсягу, повторного використання й фонової активності. Оцінка явно відокремлює припущені витрати від виміряних показників провайдера.

**Why this priority**: сотні тисяч старих каталогів можуть продовжувати роботу, а успішний upload сам по собі не доводить працездатність фіда.

**Independent Test**: контрольні успіхи, відмова публікації, невідомий результат upload, затримка діагностики та вимкнений збір; пояснення формується через наявний read-only інструментарій.

**Acceptance Scenarios**:

1. **Given** відома невдача, **When** агент досліджує користувача/операцію, **Then** показує останню доведену стадію, причину, evidence та безпечний спосіб повтору, не відкриваючи dashboard вручну.
2. **Given** облік cache/origin або billing недоступний, **When** агент оцінює витрати, **Then** позначає відповідні параметри невідомими, показує діапазон і не називає оцінку фактичним рахунком.
3. **Given** каталоги старші 7 днів, **When** власник отримує звіт, **Then** вони входять у накопичення й активні оновлення, якщо реально не призупинені; вік сам по собі не виключає їх із знаменника.

### User Story 5 — Підготувати картинки за зрозумілою підказкою (Priority: P1)

Біля імпорту людина читає коротке пояснення: каталог працює з одягом; тип і колір картинки узгоджуються з товаром, а назви/описи та інші параметри додають варіанти. Посилання «Скопіювати промпт» одним натисканням копіює інструкцію для агента, який створить квадратні картинки без брендів і правильно назве окремі файли. Довгий текст промпту не займає місце на екрані.

**Why this priority**: правильне джерело та назви потрібні до імпорту; сам upload не робить довільні фото придатними для каталогу.

**Independent Test**: прочитати підказку, скопіювати промпт мишею та клавіатурою, отримати контрольні файли за його правилами й проаналізувати їх обома шляхами імпорту.

**Acceptance Scenarios**:

1. **Given** відкрита секція картинок, **When** користувач читає підказку, **Then** розуміє, чому рекомендований одяг, що змінюється в каталозі, що звичайні картинки вибираються випадково без зіставлення, та бачить приклад `hoodie_black_001.jpg` без читання технічної документації.
2. **Given** посилання «Скопіювати промпт», **When** його активовано мишею або клавіатурою, **Then** у clipboard потрапляє повний чинний промпт, а інтерфейс коротко підтверджує копіювання; зображення чи зовнішній AI-запит не запускаються.
3. **Given** clipboard недоступний, **When** копіювання не вдалося, **Then** немає хибного підтвердження; промпт можна відкрити в доступному для ручного копіювання вигляді.
4. **Given** промпт використано для контрольного набору, **When** перевіряються назви, **Then** усі дозволені комбінації одягу/кольору однозначно розпізнаються, а рекомендації формату 1:1, відсутності брендів та одного предмета на файл доступні користувачеві.

### Edge Cases

- Перекриття папок, повторний вибір файла, однакові байти в різних файлах, конкурентні підготовки й повтор після втрати відповіді.
- Джерело змінюється між вибором, завантаженням і підтвердженням; нові байти не повинні отримати ідентичність старої версії.
- Папка отримує нові картинки після збереження налаштувань; вони не готові автоматично лише через появу в індексі.
- Відкликаний доступ, відключений Drive, видалене джерело, порожній/частковий пул, чужий простір або втрата права публікації під час виконання.
- Провайдер прийняв байти, але відповідь втрачено; перед повтором необхідно визначити, чи результат уже існує.
- Каталог уже записаний, але підтвердження не отримано; не створювати новий каталог/нові копії навмання.
- Правильна metadata-відповідь, але публічний GET повертає HTML, інший MIME або інші байти; це невдала перевірка.
- Пошкоджене, анімоване чи завелике зображення; неконтрольовані зовнішні адреси не перетворюються на довільний завантажувач.
- Незалежні кеші можуть продовжувати показувати старі байти після явного аварійного відкликання; діагностика не обіцяє видалення всіх зовнішніх копій.
- Старий клієнт і новий сервер, відсутній локальний агент, скасування, падіння виконавця, повтор із тим самим наміром, відкладені сигнали.
- Дві різні картинки з однаковим ім'ям; один вміст із різними іменами/суперечливими групами; назви без типу/кольору, з двома кольорами або двома типами; регістр, дефіси, підкреслення й порядкові номери.
- У drop є відео, HTML, папка чи файл неправдивого типу; локальні байти зникли після перезавантаження вкладки; папка Drive змінюється під час аналізу. Локальні папки як drop не входять до MVP; пояснюється вибір файлів або папки Drive.
- Промпт випадково пропонує токен, який одна частина продукту читає інакше; машинний словник, підказка та промпт мають проходити спільну перевірку сумісності.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Обране власником сховище публічних копій білих зображень каталогу — **Cloudflare R2 Standard**. Порівняння альтернатив і сценарна вартість зберігаються в [research.md](./research.md); відеохостинг залишається поза обсягом реалізації.
- **FR-002**: У секції картинок налаштувань каталогу підтримати вибір файлів/папки підключеного Google Drive та імпорт локальних зображень через drag-and-drop з рівноцінним файловим вибором. Зберегти чинні права керування налаштуваннями. Підготовка не потребує запущеного локального агента.
- **FR-003**: Публікація дозволена лише з правом керувати картинками та явно запущеною дією публікації. Для Drive додатково перевіряються права на джерело та його публічне поширення; для локальних файлів — право учасника публікувати їх у цьому просторі. Фоновий виконавець використовує чинну обмежену авторизацію простору. Самого права перегляду недостатньо. Втрата доступу до незавершеної публікації блокує її завершення.
- **FR-004**: Одна незмінна версія картинки має одну логічну публічну копію в межах простору. Дублікати/конкурентні спроби не множать копії. Дедуплікація між незалежними просторами не входить до MVP і не повинна розкривати наявність чужих файлів.
- **FR-005**: Підготовка має розрізняти вибір, аналіз назви та придатності, класифікацію, отримання джерела, перевірку вмісту, публікацію, перевірку публічних байтів, прив'язку до словника, готовність, частковий результат, відмову, скасування та переривання. Готовність медіа виставляється після незалежного публічного читання та перевірки байтів; класифікація окремо має стан matched або unclassified, який не блокує придатну звичайну картинку.
- **FR-006**: Посилання мають бути стабільними, публічно читаними без входу й короткочасних токенів, придатними для зовнішнього фіда. Жодних секретів, імен користувачів, назв файлів або адрес електронної пошти в публічній ідентичності. Самостійне вгадування сусідніх ідентифікаторів не має відкривати перелік матеріалів.
- **FR-007**: Незмінні картинки повторно використовуються у будь-якій кількості рядків/каталогів без нового upload. Оновлення фіда не запускає публікацію всього пулу; випадкові параметри URL не мають руйнувати повторне використання та кеш для незмінних байтів.
- **FR-008**: Зміна байтів утворює нову версію та нове посилання. Просте перейменування/переміщення незмінного дозволеного джерела не вимагає нової копії. Старе посилання ніколи не починає повертати іншу картинку.
- **FR-009**: Каталог використовує тільки підтверджені версії. Якщо запланована картинка не готова, результат не позначається успішним: підготовка або повторюється в обмежених межах, або повертає явну дію для користувача. Збереження старого працездатного каталогу має пріоритет над заміною неповним результатом. Частковий пул не скорочується мовчки. Якщо нова картинка потребує неоднозначної зміни тексту при вимкненому оновленні текстів, зберегти старий каталог і пояснити потребу виправити текст або дозволити його оновлення, без прихованої регенерації.
- **FR-010**: Перенесення чинного пулу та новий імпорт мають бути відновлюваними з прогресом і результатом для кожного джерела. Аналіз папки фіксує вибірку поточного запуску; повторний аналіз додає нові/змінені елементи без повторної публікації незмінних. Нові елементи папки не стають готовими лише через появу в індексі. Безперервна синхронізація папки та новий фоновий розклад імпорту не входять до обсягу. Повтор після переривання використовує вже підтверджений результат.
- **FR-011**: Нові каталоги використовують нові готові посилання. Існуючі переходять тільки після успішного оновлення та перевірки результату. Перенесення не змінює старі каталоги, permissions Drive або користувацькі файли наперед і не відкликає legacy-доступ, потрібний старим посиланням.
- **FR-012**: Прибирання джерела з пулу припиняє його новий вибір, але не видаляє копії, на які можуть посилатися видані каталоги. Вік 7 днів не є доказом непотрібності. Автоматичне видалення опублікованих копій та зупинка розкладів за віком не входять до цього MVP.
- **FR-013**: Непідтверджені тимчасові результати мають обмежений строк життя — до 24 годин після останньої активної спроби. Перед очищенням потрібно довести відсутність активної спроби/виданого посилання; невідомий стан відкладає видалення й стає діагностичною знахідкою. Успішно опубліковані результати не очищуються цим правилом.
- **FR-014**: Після невідомого результату публікації система спочатку перевіряє наявність і відповідність результату. Повтор використовує той самий намір; фонові retries обмежені трьома автоматичними спробами на версію, далі — явна відкладена/помилкова дія. Втрата відповіді не доводить невдачу.
- **FR-015**: Зберегти можливість вимкнути нову публікацію та поступово повертати попередній шлях для нових операцій без видалення вже виданих R2-посилань. Старий клієнт не має позначити незавершений новий шлях успішним або обійти права.
- **FR-016**: Секрети сховища залишаються лише в довіреному серверному контурі. Публічна доставка відокремлена від авторизованого запису; середовища production/beta/dev ізольовані. Невідомі типи/розміри, пошкоджені байти та джерела поза дозволеним простором відхиляються до готовності.
- **FR-017**: Початкова область форматів — статичні PNG/JPEG/WEBP до 50 MB на джерело, із коректною орієнтацією. Перевірка охоплює фактичний розмір, тип/структуру контейнера, розміри кадру, відсутність анімації та відповідність опублікованих байтів. Повний decode всіх кодеків і візуальне підтвердження назви не обіцяються; ці межі явно відображаються в readiness/діагностиці. Непідтримувані поточні елементи залишаються явно legacy/unsupported та не перекодовуються мовчки. Придатність опублікованих форматів для фактичного зовнішнього імпортера має пройти приймальну перевірку; неперевірена сумісність не є готовністю до релізу.
- **FR-018**: Перед увімкненням публікації користувачеві зрозуміло, що вибрані картинки отримають публічні копії. Опис приватності та правило відсутності серверних медіа мають отримати точний вузький виняток для цих копій, їхнього призначення, утримання й відкликання. Відео, приватні previews та картинки ре-стітчу цим винятком не охоплюються.
- **FR-019**: Агентний звіт витрат показує окремо кількість копій/версій, повторне використання, обсяг, записи, origin-читання, cache hit ratio, накопичені/активні каталоги та оновлення, наскільки це спостережувано. Відсутні provider-метрики позначаються невідомими. Оцінки мають дату тарифу, період, допущення й знаменники; вони не є фактичним billing.
- **FR-020**: У кошторисі обов'язкові 1/3/6/12-й місяці без видалення старих каталогів, image-only reuse, відео тільки при створенні, відео кожні 12 годин з останньою версією та з усіма версіями, сценарії кешу й окремо запропонований строк активних оновлень. Сто товарів не множать одне відео на сто без явного припущення читача.
- **FR-021**: Підготовка та діагностика обмежують паралельність, пам'ять, retries і обсяг даних; не завантажують весь пул у пам'ять на кожен каталог. Точні ресурсні ліміти та load acceptance визначаються планом на контрольному навантаженні 50 × 15 каталогів/день.
- **FR-022**: Видалення простору та явне відкликання публікації мають охоплювати нові копії й залишати очищені докази результату; завдання очищення переживає видалення запису простору. Видалення акаунта відкликає незавершені дозволи цього учасника й очищає його персональні зв'язки; готові командні копії залишаються власністю простору після передавання прав. Чинний власник спочатку передає/видаляє простір за наявними правилами. Перед відкликанням пояснюється вплив на старі каталоги; зовнішні кеші/вже скачані копії не вважаються гарантовано знищеними. Звичайне видалення джерела або учасника не є неявним відкликанням усіх публікацій простору.
- **FR-023**: Основна дія має назву **«Проаналізувати й завантажити»**. Вибір папки чи drop готує чергу без публікації; дія виконує аналіз назв, розподіл і upload придатних файлів як одну операцію з видимими стадіями. Друге обов'язкове підтвердження upload не додається. Підсумок явно показує готові, повторно використані, нерозпізнані й невдалі файли.
- **FR-024**: Для matched-відповідності потрібні розпізнані тип одягу та один колір із чинного словника назв. Дозволені канонічні токени, приклади й формат `<тип>_<колір>_<номер>.<розширення>` описані в [image-guide.md](./image-guide.md). Невідомі, неповні або неоднозначні назви не отримують вигадану категорію: придатні картинки публікуються як unclassified та вибираються випадково без зіставлення з товаром. Підсумок і підказка пояснюють цей режим та правильне іменування. Це аналіз назви, не AI-розпізнавання вмісту.
- **FR-025**: Після імпорту робочий пул — компактний словник готових URL та їхніх відповідностей: тип, колір, версія, стан і службова прив'язка до публікації/простору. Для matched-записів вибір і генерація назв/описів використовують наявні пари тип+колір, без перемноження в неіснуючі комбінації. unclassified-картинки вибираються випадково без обіцянки відповідності. У змішаному пулі лише matched-записи мають гарантію зіставлення; відсутність classified-набору не блокує каталог із придатними звичайними картинками. Повторне читання всіх оригіналів або розбір назв при кожному каталозі не потрібні. Soty не утримує другу постійну бібліотеку байтів у браузері, на агенті або в іншому серверному сховищі; тимчасові буфери/передачі обмежені. Точне місце зберігання спільного словника визначає план, а не метафора «локально».
- **FR-026**: Саме ім'я файла не доводить ідентичність байтів: однакові назви різного вмісту не зливаються, а однакові байти з суперечливими типами/кольорами не підмінюють чинну відповідність мовчки. Підсумок аналізу вказує конфлікт і не додає суперечливий запис до готового пулу.
- **FR-027**: Під імпортом показати короткий людський текст із [image-guide.md](./image-guide.md): чому рекомендований одяг, як правильно названі картинки поєднуються з типом/кольором, які параметри варіюються та приклад назви. Обов'язково пояснити: звичайні картинки без розпізнаваних назв теж можна додати, але вони вибиратимуться випадково без логіки відповідності назві та кольору товару. Матеріал/крій/візерунок не видаються за факти, розпізнані з фото або чинним парсером назви.
- **FR-028**: Повний промпт із [image-guide.md](./image-guide.md) прихований за текстовою дією **«Скопіювати промпт»**: одне натискання копіює текст і показує коротке «Промпт скопійовано». Посилання доступне клавіатурою та допоміжним технологіям. Якщо clipboard не спрацював, показується доступний текст для ручного копіювання без хибного success. Зовнішня генерація автоматично не запускається; сам промпт не містить даних простору.
- **FR-029**: Промпт вимагає окремий квадратний файл 1:1 для кожної картинки, один цілий предмет одягу, чисте біле тло, природний колір, відсутність людей, брендів, логотипів, написів, watermark, колажів та аксесуарів. Він містить сумісні списки типів/кольорів і правила іменування, приклади та самоперевірку. Рекомендований розмір 1024×1024 і JPEG або PNG; інші підтримувані імпортером джерела не відхиляються лише через інше співвідношення сторін.
- **FR-030**: Підказка, промпт і словник класифікації мають бути узгоджені: усі комбінації рекомендованих токенів типу/кольору перевіряються чинними точками розбору та новим аналізатором. Якщо словник змінено, тексти й приймальні приклади оновлюються разом. UI використовує наявні компоненти й правила [DESIGN.md](../../docs/DESIGN.md), без великого постійного блоку промпту.

### Analytics & Diagnostic Coverage _(mandatory)_

Вимоги [031](../031-platform-autoanalytics/spec.md) поширюються на всі наведені journeys. Завдання реалізації повинні перевіряти повний шлях до read-only діагностики, а не тільки факт створення події.

- **AD-001 — Кореляція.** Намір підготовки/перенесення, кожна спроба публікації, джерело/версія в межах простору та створення/оновлення каталогу мають корельовані неприватні ідентифікатори. Автоматичний чи ручний повтор отримує окрему спробу з тим самим батьківським наміром; чужі простори/версії не змішуються.
- **AD-002 — Стадії та outcomes.** Докази охоплюють вибір джерела (Drive/local) → запуск дії → авторизація → аналіз/класифікація → визначення версії → отримання → перевірка → reuse або upload → публічне підтвердження → запис словника → прив'язка до каталогу → запис каталогу → перевірка доступного каталогу → terminal. Для background вказуються причина запуску, очікування залежності, затримка, остання доведена стадія та факт повтору. Upload success окремий від готового URL, успішного каталогу та підтвердженого зовнішнього імпорту.
- **AD-003 — Причини.** Стабільні закриті причини розрізняють права, відсутнє/змінене джерело, формат/розмір, неповний пул, недоступний провайдер, rate limit, timeout, невідомий результат запису, невідповідність байтів, недоступне публічне посилання, помилку прив'язки/каталогу, скасування, переривання та відновлення. Нові коди покриваються code map та перевіркою її повноти.
- **AD-004 — Агентний інтерфейс.** Наявні `investigate`, `inspect`, `journey`, `audit` та доречний каталоговий звіт мають пояснювати новий шлях через чинний read-only CLI. Розширення діагностики включає capability inventory, source freshness, delivery lag, missing joins, delayed/lost terminals, partial/truncated reads та unsupported producers. Не потрібні ad-hoc SQL або ручний dashboard.
- **AD-005 — Межі приватності.** Лише очищені IDs, стани, нормалізовані коди, bounded size/time/count buckets та агрегати. Без байтів/вмісту, назв/шляхів, оригінальних або signed URLs, секретів, provider payloads і глобального content hash, який дозволяє зіставляти чужі файли. Експорт діагностики повторно перевіряє очищення.
- **AD-006 — Сліпі зони.** Успішний публічний GET доводить доступність у точці перевірки, але не прийняття картинки Meta, не використання конкретним кінцевим користувачем і не глобальний cache hit ratio. Без незалежного дозволеного підтвердження це `insufficient`/`unsupported`, не «успіх доставки». Статус billing без provider evidence — estimate/unknown. Дозволена fallback evidence: контрольний фід, зовнішнє анонімне читання й очищені агреговані метрики.
- **AD-007 — Приймальна матриця.** Синтетичні success/reuse, source changed, forbidden, provider unavailable, accepted-but-response-lost, public verification failed, catalog write failed, cancel/crash/retry, cleanup race, old client, late/missing events, unavailable billing та disabled analytics мають давати правильний product outcome і віддалений діагноз. Втрата діагностики не блокує роботу продукту; її відсутність залишається видимою. Перевірити чинні macOS/Windows клієнти, серверний шлях без агента та ізольовану packaged beta відповідно до обраного плану релізу.
- **AD-008 — Нові межі.** Розрізняти невідомий тип, невідомий/неоднозначний колір, конфлікт відповідності, непридатний dropped-файл, втрату локального джерела після reload, частковий результат і невдалий запис словника після вдалого upload. unclassified/random — нормальний успішний режим, а не failure upload. Копіювання промпту має окремі intent/success/failed/manual-fallback outcomes із версією промпту; текст промпту, імена й вміст clipboard не збираються. Відсутність upload після копіювання не означає помилку генерації: зовнішній агент неспостережуваний.
- **AD-009 — Додаткове приймання.** Обидва способи імпорту, 32×24 сумісних імен, sparse-пул із двома фактичними парами, конфлікти імен/вмісту, повторне вибирання local після reload та відмова clipboard перевіряються через product outcome і агентний read-only діагноз. Звичайний та змішаний пул і нормальний успішний random-режим перевіряються окремо. Сліпі зони зовнішньої генерації та візуальної правдивості назви лишаються явними.

### Key Entities _(include if feature involves data)_

- **Джерело імпорту**: вибрана папка/файл Drive або локальний файл, права, вибірка та стан доступності в поточній спробі.
- **Запис словника**: готове посилання, matched-пара тип+колір або unclassified без вигаданих значень, версія, стан і зв'язок із простором/публікацією; без постійної локальної копії байтів.
- **Правило назв / версія промпту**: сумісні канонічні типи й кольори, схема назви, приклади та текст для копіювання.
- **Версія зображення**: незмінний вміст джерела, придатність і зв'язок із простором; відрізняється від перейменування.
- **Публікація**: готова або незавершена копія версії, публічна ідентичність, перевірка, часові межі та стан відкликання.
- **Спроба підготовки**: намір, спроба, стадії, результат, нормалізована причина, reuse та доказ відновлення.
- **Видане використання**: зв'язок версії з успішним результатом каталогу; підстава захистити копію від випадкового очищення.
- **Оцінка витрат**: часовий горизонт, накопичення, параметри media/read/cache, тарифна дата, спостережуваність і розклад вартості.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Для контрольного пулу зі 100 придатних зображень 100% готових версій доступні незалежному неавторизованому читачу з правильним вмістом; жодна неперевірена версія не має статусу готовності.
- **SC-002**: Створення 100 каталогів по 100 товарів та 10 раундів оновлення з незмінного готового пулу дають **0 додаткових публікацій байтів** після початкової підготовки; одна версія зберігає однакове посилання у всіх використаннях.
- **SC-003**: У всіх контрольних конкурентних повторах і втратах відповіді є не більше однієї логічної публікації версії; повтор не створює зайвий каталог, а невідомий outcome явно залишається невідомим до звірки.
- **SC-004**: У 100% сценаріїв неповної підготовки/невдалого оновлення попередній працездатний каталог і його зображення зберігаються. При зміні байтів старе посилання повертає стару версію; звичайне прибирання з пулу не руйнує видані посилання.
- **SC-005**: У контрольній матриці всі заборонені публікації між учасниками/просторами відхиляються до готовності; у діагностиці та публічних ідентифікаторах 0 заборонених приватних значень.
- **SC-006**: Для всіх ін'єктованих невдач агентний звіт протягом 2 хвилин після доступності доказів правильно називає останню доведену стадію та причину або конкретну сліпу зону. Жодного непідтвердженого зовнішнього імпорту чи фактичного рахунку не оголошено доведеним.
- **SC-007**: Кошторис відтворюється локально з явних параметрів для 50 користувачів, 15 каталогів/день і всіх сценаріїв FR-020; накопичення дає 22 500/270 000 каталогів на кінець 1-го/12-го місяців без вигаданого видалення на 7-й день.
- **SC-008**: Усі контрольні journeys налаштування та підготовки працюють без локального агента; вимкнення нової публікації не припиняє читання жодного раніше виданого посилання.
- **SC-009**: До production-перенесення контрольний зовнішній імпортер успішно отримує всі підтримувані формати з нового медіадомену; результат перевірки зафіксовано окремо від звичайного публічного GET. Відсутність такої перевірки означає недостатню готовність.
- **SC-010**: Усі 768 рекомендованих комбінацій 32 типів × 24 кольорів однозначно розпізнаються в однакові тип/колір; невідомі та неоднозначні назви не стають matched-записами, але придатні картинки стають готовими unclassified-записами для випадкового вибору.
- **SC-011**: Імпорт того самого контрольного набору через Drive та local дає однакові відповідності й придатні URL; повтор не множить публікації. Після втрати локальних джерел готовий словник лишається придатним до створення каталогів.
- **SC-012**: В усіх контрольних способах активації посилання повний промпт копіюється за одну дію або чесно відкривається ручне копіювання; жодне копіювання не запускає зовнішню генерацію і не надсилає в діагностику текст чи clipboard.
- **SC-013**: У sparse-пулі «чорне худі + біла футболка» 100% створених/оновлених рядків зберігають фактичний тип і колір обраного зображення; словник не містить вигаданих пар. Невизначений старий текст при вимкненому його оновленні дає явну причину й збереження старого каталогу, без вгадування. Для готового пулу наступні каталоги не потребують доступу до оригінальних файлів лише заради класифікації/посилань.

- **SC-014**: Пул лише зі звичайних придатних картинок без розпізнаваних назв успішно імпортується й використовується для випадкового вибору. У змішаних пулах matching застосовується лише до matched-записів; підказка пояснює різницю.

## Assumptions

- «Білі зображення» — картинки товарів у налаштуваннях каталогу: одяг на білому тлі, не обов'язково білий за кольором. Відео та початкові/фінальні кадри ре-стітчу залишаються поза обсягом. Оригінали користувача залишаються на його комп'ютері/Drive; Soty не переносить локальний drop додатково в Drive.
- R2 Standard підтверджено власником для цієї специфікації; перенесення та реалізація ще не виконувались.
- «Локально словничок» описує компактне представлення пулу всередині Soty, не вимогу тримати єдину копію словника на одному комп'ютері; спільний простір має залишитися працездатним для інших учасників і фонових каталогів.
- «1 на 1» у промпті означає квадратне співвідношення сторін 1:1 та один предмет на окрему картинку. Автоматично доводити відповідність візуального вмісту назві поза обсягом: аналіз спирається на правильно підготовлені назви.
- Одне відео використовується всіма 100 товарами каталогу; 100 MB/відео, 0.2 MB/картинка і 500 картинок/користувача — явні сценарні припущення, не виміряна статистика. Калькулятор дозволяє їх змінити.
- Немає видалення каталогів і зупинки їхніх розкладів за віком у базовому кошторисі. Пропозиція паузи після 7 днів розрахована окремо та потребує наступного продуктового рішення.
- Зображення можуть зберігатися довше за життя каталогу. MVP не обіцяє автоматично знати, чи зовнішній каталог ще використовується; консервативне утримання має явну ціну.
- Чинні довільні fallback-посилання залишаються legacy зовнішніми адресами; система не починає безконтрольно копіювати їхній вміст. Їхній хостинг не покритий гарантіями нового сховища.
- Залежності: доступ до джерел простору, серверна авторизація, production-медіадомен, доступне сховище, наявний створювач/оновлювач каталогів, read-only діагностика та підтвердження зовнішнього імпортера.
- Ресурсна реалізація, контракти сумісності й спосіб релізу визначаються наступним планом. Нова спекa не дозволяє обходити beta/production gates або кваліфікувати зміни серверних функцій як суто web mini release.
- Поза обсягом MVP: перенос відео/приватних previews/ре-стітч картинок, серверне перекодування медіа, генерація картинок усередині Soty, AI-аналіз вмісту, новий парсер матеріалу/крою/візерунка з назв, імпорт локальних папок drop, платні трансформації, нова система планування, автопауза, архівування/видалення виданих каталогів за строком, загальна дедуплікація між просторами та фактичні production-операції.

### Catalog management at collection scale (2026-10-28)

- Storage occupied and available capacity are visible in the image section and its collapsed summary; the quota is owner-wide. Stale capacity is explicitly marked. Deletion never optimistically credits bytes.
- A named Manage images action opens a complete bounded library read. ### Weekly replacement of names and descriptions (2026-10-28)

The names section separates its actions from the introductory text with token-based spacing and wrapping. An explicit weekly switch and editable integer count (1–1000, default 200) save a server schedule. It starts disabled. Enabling schedules the first run seven days later; changing an enabled count preserves its next due time. The interface reports only confirmed next/last times, protects unsaved drafts, and says that the complete saved text list is replaced. Existing catalogs keep their own content until their normal update.

The existing catalog scheduler wakes independently of catalog update work, and executes a bounded text worker before the Drive OAuth gate. The manual and automatic paths share the same generator and image classification inputs. A durable lease and configuration/content revision fences prevent stale workers from committing over a changed configuration or intervening manual edits. The old pool survives failed generation/validation/insertion. Replacement, draw reset and committed receipt are one transaction. A replayed committed run is read-only. Failed attempts use bounded retry backoff; abandoned leases can be reclaimed. Disabling cancels the current lease. Deleting the configuring account does not block account deletion and permission checks fail closed.

Diagnostics: content-free configured/claimed/lease_recovered/committed/failed/cancelled journal rows correlate by run and team IDs. Stable error codes distinguish read, validation, save, conflict and permission failures. The read-only `catalog-texts <team-id|run-id>` CLI reports current settings, period-bounded run evidence, source coverage and truncation. Historical as-of omits mutable current settings. Capture health does not prove worker deployment, secret delivery, browser visibility or changes in existing catalogs: these remain explicit blind spots until an actual run receipt or downstream evidence exists.

Acceptance: UI spacing, persisted toggle/count/default, no immediate replacement on save, rejected counts, read-only roles, protected drafts, partial/unknown save feedback; SQL permissions, atomic failure, replay, stale lease/config/manual-content fencing, account deletion and capture health; worker exact count, image inputs and lost reply; shared generator regression; full disposable database migration gate before incremental local-beta application.
