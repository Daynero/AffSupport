# Порядок ручної beta-прийомки

Цей документ описує майбутнє виконання. Браузери, beta reset та навантаження під час написання специфікації не запускалися.

## 1. Зафіксувати кандидата

1. Прочитати `docs/BETA.md`, `docs/PRODUCTION.md`, цю специфікацію і scope.md.
2. Записати `git rev-parse HEAD`, `git status --short`, базовий tag, міграції, версії macOS/Safari/Chrome/агента. Зберегти manifest незакомічених файлів з хешами для дослідного прогону. Для остаточної прийомки потрібен чистий commit; сторонню роботу не видаляти й не комітити автоматично.
3. Перевірити Node 22 та `npm run beta:doctor`. Не читати/публікувати секрети конфігурації у звіті.
4. Після нових міграцій потрібен `npm run beta:reset`: він стирає resettable beta-дані, тому виконувати лише на виділеному тестовому стенді після збереження потрібних fixtures. `beta:up` сам міграції не застосовує.
5. Запустити `npm run beta:up`. Перевірити локальну web-адресу `http://127.0.0.1:5175`, agent `43140`, локальний Supabase `54321`, health runtime й актуальність схеми. Dev auth має бути вимкнено; beta використовує окремий ключ entitlement.

## 2. Відкрити два Safari та один Chrome

Використати два **окремі профілі Safari**: `Soty Beta Owner` та `Soty Beta Member`. У кожному відкрити окреме вікно з `http://127.0.0.1:5175`. У Chrome створити профіль `Soty Beta Viewer` та відкрити ту саму адресу. Не заміняти профілі звичайними вкладками: вони ділять сесію. Якщо версія Safari не підтримує профілі, потрібен інший ізольований контекст/користувач ОС; ізоляцію довести SET-001, інакше SET BLOCKED.

| Вікно    | Особа                         | Роль у W1                     | Призначення                         |
| -------- | ----------------------------- | ----------------------------- | ----------------------------------- |
| Safari A | owner-a, звичайний користувач | owner                         | Створення, тарифні екрани, учасники |
| Safari B | member-b                      | editor; потім admin/overrides | Зміни й гонки                       |
| Chrome C | viewer-c                      | viewer; потім обмін ролями    | Read-only та спостерігач            |

Додаткові тестові особи: S — Soty admin у четвертому окремому контексті для видачі тарифів; X — неучасник. Вбудований `beta@soty.local` є адміністратором Soty, тому **не використовувати його як платного власника A**: його власний простір обходить тариф. Для W2 використати іншого звичайного власника, а також окремим fixture перевірити два простори A.

Основна трійка спочатку відкриває один W1, щоб порівнювати результат однієї дії. W2 потрібен для ізоляції. Підписати вікна/профілі й перед кожною ризиковою дією перевіряти поточного користувача та назву простору. Паролі fixtures зберігати локально, не у звіті.

Один Mac з одним агентом не дорівнює трьом незалежним робочим станціям. Спочатку з’ясувати фактичний контракт pairing, виконати SET-006; для багатопристроєвого upload/download/process та Windows потрібні окремі тестові агенти/машини. Не послаблювати авторизацію агента для зручності тестів.

## 3. Fixtures та керований час

- W1: активний Лід, три звичайні місця; W2: інша команда з власними даними. Для варіантів — Соло, Соло+1, Лід+місця, pending grant, legacy та internal-admin workspace.
- Старе правило вимкнути для основної тарифної серії; окрему legacy серію виконати явно. Порожній/активний/призупинений/відновлений стани повинні мати однаковий контрольний набір даних.
- Використати тестові матеріали: коротке відео зі звуком, body зі зміщеним audio, зображення, landing, вкладені папки, файл без доступу, shortcut, кириличні/довгі назви. Підготувати manifest очікуваних кількостей і контрольних сум; ніяких реальних клієнтських матеріалів.
- Додати завдання з вкладеннями, рекламні акаунти й витрати за різні дні, каталоги з різними інтервалами, transcript та, якщо включено, launches з різними revisions.
- Drive налаштувати як тестову інтеграцію за `docs/BETA.md`, тільки з окремими тестовими папками й тестовим Google client. Немає Drive — залежні кейси BLOCKED, а не PASS.
- Для D−3/D−1/D/D+1…D+4 потрібен безпечний локальний clock/fixture механізм, який охоплює серверну перевірку, scheduler і клієнт. Зміна лише годинника браузера не тестує строк. Не змінювати глобальний годинник робочого Mac. Якщо такого механізму немає, додати підготовче завдання й позначити граничні сценарії BLOCKED до його реалізації.
- Fault fixtures для 429/cursor/lease/acceptance timeout повинні працювати лише в beta. Для серверної відмови використовувати тестовий harness з реальною особою й її правами, не привілейований ключ. Відсутній harness — явна передумова планування, не привід писати ручний production SQL.
- Запрошення копіювати з UI, не надсилати. Прямі зовнішні повідомлення тарифів/нагадувань потребують capture/безпечного адаптера без delivery credentials. Локальний поштовий catcher сам по собі не перехоплює прямий сторонній HTTP email.

## 4. Послідовність

1. SET → TEAM → ACL: перевірити стенд та захист.
2. TARIFF → LIFE → RO: тарифи, час, призупинення, повернення доступу.
3. SYNC: активний простір; потім повторити критичні фази під час відкликання прав/тарифу.
4. REG → LAUNCH: усе, що потрапило у scope кандидата.
5. OBS та capacity-plan: діагностика, idle, навантаження, recovery, backup.
6. Поміняти ролі між Safari й Chrome та повторити критичні створення/запрошення/відкликання/несплату/sync. Перевірити звичайні режими Safari tracking prevention, cookies і блокування loopback без глобального вимкнення захисту.
7. Виправлення → конкретний регресійний тест → повтор кейсу та залежних груп. Після зміни кандидата повторити P0 smoke й оновити докази.
8. Для фінального чистого SHA: `npm run verify`, `npm run verify:release`; пакована beta за `docs/BETA.md`: `npm run beta:down`, `npm run beta:package`, `npm run beta:verify`. Важкі локальні команди послідовно; release-команди згідно з канонічним runbook. Не вважати автоматичний короткий runtime smoke заміною всього ручного каталогу.
9. Заповнити execution-report.md. Production лише окремою процедурою з G0 та sandbox acceptance за `docs/PRODUCTION.md`.

## 5. Докази та діагностика

На початку/кінці групи записати час UTC, build, fixture, учасників під псевдонімами й дозволені correlation IDs. Screenshot до/після у трьох вікнах доводить видимість; діагностичний JSON доводить серверний стан. Не зберігати необроблений HAR з токенами або користувацьким контентом. Неперевірене автоматично лишається NOT RUN.

Штатні команди (спершу довести тестову ціль через безпечну конфігурацію, не друкуючи DSN):

```bash
npm run analytics -- investigate <test-email> --json
npm run analytics -- inspect <run-or-flow-id> --json
npm run analytics -- journal <test-installation-id> --json
npm run analytics -- sync <test-team-id> --json
npm run analytics -- connection --period today --json
npm run analytics -- team-workspace --period today --json
npm run analytics -- audit --period today --json
npm run analytics -- database-retention --json
npm run analytics -- database-health --json
```

Для повторного розслідування додати `--as-of <UTC instant>` до часових команд. Це фіксує кінець вікна подій, але не перетворює поточні database gauges на історичний знімок. Зберігати самі ресурсні знімки та час. Якщо `ANALYTICS_DATABASE_URL is not set`, виконати одноразове налаштування `docs/ANALYTICS_CLI.md`; не обходити CLI ручним SQL.

Повні `database-health --management`/`database-tables` сканування — лише за потреби, не частий polling. Продакшен-знімок має окрему позначку і ніколи не змішується з beta-навантаженням. Збирання JSON може вимагати прибрати npm banner, зберігши незмінений envelope `{ok, command, period, data}` та помилки.

Уточнення прийомки: після поновлення застосовуються тільки актуальні права; додати snapshot/restart до оплати та негативні agent credential audience перевірки. Hosted runtime readiness, native browser latency probes і EvidenceAdoption виконуються за contracts/acceptance-tooling.md; старі докази не перейменовуються під новий SHA.
