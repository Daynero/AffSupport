# Feature Specification: Агент сам розслідує проблему будь-якого користувача і веде до виправлення

**Feature Branch**: `033-agent-user-investigation` (від `031-platform-autoanalytics`)

**Created**: 2026-10-10

**Status**: Draft — ready for planning; рішення прийняті автономно за дорученням власника

**Input**: Власник: «По подіях очікую максимальну автоматизацію, щоб при потребі агент міг детально вивчити будь-якого юзера і його проблему сам по логах і виправити помилки». Рішення щодо хвостів 031 (сортування блокнота, `team_preview_completed`, коди помилок) делеговано агенту.

## Що вже є і чого бракує (після 031/032)

Є: події з `run_id`/`flow_id`, `tool_ready`, `error_occurred`, link-події, `audit`, `inspect <id>`, `journey <email>`, `connection`, `sync`, журнал агента **лише на комп'ютері користувача** і support-bundle, який користувач має скопіювати сам.

Бракує для автономного розслідування:

1. **Журнал агента недосяжний.** Усе, що агент знає про spawn/exit, picker, drop, entitlement, shutdown, лежить локально. Розробник-агент не бачить цього без участі користувача.
2. **Немає однієї точки входу.** Щоб розібрати скаргу, агент-розробник має сам скласти 5–7 команд і з'єднати їх вручну.
3. **Коди помилок `unknown`** для транскрибації, стітчера, landing і оцінки: агент повертає текст, а не код. Fingerprint не вказує, де в коді шукати.
4. **Немає мапи «fingerprint → місце в коді».** Агент-розробник не знає, з якого файлу починати виправлення.
5. **`team_preview_completed` без продюсера**, хоча на неї спирається метрика SC-009.

## User Scenarios & Testing _(mandatory)_

### User Story 1 — Одна команда розслідування (Priority: P1)

Власник каже «у user@x не працює транскрибація». Агент-розробник виконує одну read-only команду і отримує повну картину: хто користувач (білди, платформа, браузер, походження сторінки), що він робив (сесії, інструменти), де зламалось (невдалі прогони з ланцюжками стадій), що в той момент відбувалося на його комп'ютері (журнал агента навколо збою), стан зв'язку, синхронізація просторів, сліпі зони, і ранжований перелік висновків з доказами та місцями в коді.

**Independent Test**: на PGlite-наборі з користувачем, у якого є невдала транскрибація, розрив зв'язку і записи журналу агента, команда повертає висновок «транскрибація впала на стадії X з кодом Y; агент у той момент записав Z; ймовірне місце — файл F».

**Acceptance Scenarios**:

1. **Given** користувач із невдалим прогоном, **When** `investigate <email>`, **Then** результат містить прогін, його ланцюжок, terminal, код, fingerprint, записи журналу агента в межах ±2 хв, і посилання на файли коду з мапи fingerprint.
2. **Given** користувач без подій за період, **When** `investigate`, **Then** результат «недостатньо даних» із переліком сліпих зон (старий білд, вимкнена аналітика, немає журналу), а не «проблем немає».
3. **Given** `investigate <run_id>` або `<installation_id>`, **Then** команда приймає будь-який із цих ідентифікаторів.
4. **Given** вихід команди, **Then** у ньому немає email, токенів, шляхів, назв файлів користувача.

### User Story 2 — Журнал агента доходить до бази сам (Priority: P1)

Без участі користувача безпечна вибірка журналу агента (лише категорії, коди, числа, закриті значення) регулярно потрапляє в базу і зв'язується з користувачем, інсталяцією та запуском агента.

**Acceptance Scenarios**:

1. **Given** підключений агент і користувач увійшов, **When** стається збій інструмента, розрив зв'язку, невдала готовність інструмента, старт сесії або ховання вкладки, **Then** веб пересилає нові записи журналу з останнього пересланого `seq`.
2. **Given** запис із шляхом або токеном (якщо обійшов захист агента), **When** він доходить до бази, **Then** сервер його відкидає; у базу потрапляють лише записи, що пройшли серверну перевірку.
3. **Given** перезапуск агента, **Then** нумерація `seq` нова, але записи не дублюються (унікальність `agent_instance_id + seq`).
4. **Given** аналітика вимкнена (бета/dev), **Then** пересилання вимкнене.

### User Story 3 — Помилки вказують на код (Priority: P1)

Кожна помилка кожного інструмента має стабільний код від агента, а кожен fingerprint — запис у мапі з файлами, де цей код виникає, і коротким описом, що перевірити.

**Acceptance Scenarios**:

1. **Given** невдала транскрибація, стітч, landing-оптимізація чи оцінка, **Then** `error_code ≠ unknown`, коли агент знає причину.
2. **Given** будь-який код у закритих списках агента, **Then** мапа має для нього файли; тест падає, якщо код без запису в мапі.

### User Story 4 — Цикл «розслідування → виправлення» (Priority: P2)

AGENTS.md містить runbook: скарга → `investigate` → факти/гіпотези → відтворення тестом → виправлення → регресія → перевірка ефекту через `audit`/`investigate` після релізу. Агент-розробник не питає власника, де шукати.

## Requirements _(mandatory)_

- **FR-001**: Таблиця `public.agent_journal_records` (user_id, installation_id, agent_instance_id, seq, recorded_at, received_at, category, code, props jsonb) з RLS: insert лише власних через RPC, select для admin і `wishly_analytics_ro`; унікальність `(agent_instance_id, seq)`.
- **FR-002**: RPC `ingest_agent_journal(p_records jsonb)` (security definer): ≤ 200 записів за виклик; кожен валідований: category із закритого списку агента, code `^[a-z][a-z0-9_]{1,63}$`, props ≤ 16 ключів, значення — скінченні числа, булеві або рядки ≤ 64 символів без `/`, `\`, `://`, `token`, `bearer`, `@`; відкинуті — повертаються з причиною; дублікати — no-op.
- **FR-003**: Веб пересилає записи журналу (`/api/diagnostics?since=`) на тригерах: успішне підключення, `error_occurred`, `link_recovered`, `tool_ready` failure, ховання вкладки; не частіше ніж раз на 30 с; курсор `seq` на `agent_instance_id` у `localStorage`; лише коли аналітика ввімкнена й користувач увійшов; ≤ 200 записів за раз.
- **FR-004**: Retention журналу — 30 днів (purge у тій самій щоденній задачі retention 031).
- **FR-005**: CLI `investigate <email|installation_id|run_id|flow_id> [--period] [--as-of] [--json]`: ідентичність (без email у виході), білди, платформа агента й браузера, походження сторінки; сесії; інструменти; невдалі й незавершені прогони з ланцюжками (`inspect`); link-історія; кластери помилок користувача; журнал агента в вікні ±2 хв навколо кожного збою; sync-jobs просторів, де користувач власник; сліпі зони; ранжовані `findings` (`fact | hypothesis | insufficient`, докази, `code_locations`, `next_step`). Read-only, детерміновано з `--as-of`.
- **FR-006**: CLI `journal <email|installation_id|agent_instance_id>` — записи журналу агента за період.
- **FR-007**: Закриті списки кодів помилок агента для транскрибації, стітчера, landing-оптимізації й оцінки (як `COMPRESSION_ERROR_CODES`) — у shared; агент виставляє код у стані job-а; веб передає його в `error_occurred`.
- **FR-008**: `scripts/analytics/code-map.ts`: для кожного `<tool>:<stage>:<code>` і кожної категорії/коду журналу — файли та підказка; тест: кожен код із закритих списків і кожен код журналу має запис.
- **FR-009**: Продюсер `team_preview_completed` у командному перегляді матеріалу (успіх/помилка відкриття прев'ю) з `attempt_id`.
- **FR-010**: AGENTS.md — runbook розслідування і виправлення; таблиця «питання → команда» з `investigate`/`journal`.
- **FR-011**: Приватність: жодного вмісту, шляхів, назв файлів, email у журналі, подіях і виході CLI; тести-сторожі на кожному шарі (агент, веб-пересилання, RPC, CLI).

## Success Criteria _(mandatory)_

- **SC-001**: На контрольному наборі (невдала транскрибація, розрив зв'язку, збій picker-а, застарілий агент, користувач без подій) `investigate` дає правильну стадію, код і файл у 100% випадків із даними, і «недостатньо даних» з названою сліпою зоною в решті.
- **SC-002**: Журнал агента для збою доступний у базі без дій користувача; запис із забороненим значенням не потрапляє в базу (тест RPC).
- **SC-003**: Для нових збоїв транскрибації, стітчера, landing і оцінки `error_code = unknown` лише коли агент справді не знає причини.
- **SC-004**: `audit` показує 0 `declared_but_never_emitted`.
- **SC-005**: `npm run verify` зелений.

## Assumptions

- Пересилання журналу — це аналітика з тим самим вимикачем, що й події; бета/dev не пересилають.
- 30 днів зберігання журналу достатньо для розслідування скарг; агрегати не потрібні.
- Агент-розробник має доступ до `ANALYTICS_DATABASE_URL` (read-only); писати в production він не може і не повинен.
