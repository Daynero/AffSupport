## Reuse boundaries and mandatory architectural decisions

1. **Identity remains stable.** For “migrate this space”, retain `team_id`, material UUIDs, catalogs, tasks, launches, account/finance history, role grants and audit attribution. Introduce `storage_backend`, immutable object/version identity, provider locations and migration mapping. Do not use an R2 key as a business primary key. Material-to-parent relations need material UUIDs for R2 folders while preserving old provider IDs in legacy mappings.
2. **Empty new space is separate.** Fresh R2 creation produces a new team UUID and an immutable “fresh” origin choice. It never becomes an import target for a former Drive space. A later migration claims a separate reserved migration slot and preserves the old team's business identity, even if its storage destination is provisioned separately. User-facing “another space” must not imply silently cloning membership/billing/history.
3. **One operation seam.** Add storage-provider dispatch behind typed workspace operation/transfer contracts, migrate business call sites in bounded groups, and keep `drive-ops` compatibility routes during the supported old-agent window. Reject unsafe/unsupported old-client writes server-side rather than relying on hidden UI.
4. **One source of quota truth.** Define account allocation + per-workspace attribution and a reservation ledger that covers concurrent multipart uploads, process output, imports and migration. Commit/release reservations idempotently. All existing R2 publication uses must link into accounting, not be billed once by the old ledger and again by a new file row.
5. **Private originals, explicit public publication.** Existing public catalog image/video buckets cannot host general private workspace originals. Same-content reuse must never inherit a public ACL implicitly. Public serving and backup copies are physical costs; customer logical storage rules must be documented independently.
6. **Soty generates previews.** New version queues bounded derivative work, keeps originals downloadable, stores versioned thumbnails/posters, and reports unsupported/failed/pending explicitly. Use isolated rendering for documents/archives/HTML, resource ceilings and no ambient provider credentials. Avoid mandatory transcoding of every original: it changes both cost and acceptance latency.
7. **One authority per workspace generation.** Writes pin backend+generation and role/tariff revision. Freeze Soty writes for final migration reconciliation; drain/fence existing jobs and old agent tickets. External Drive editors cannot be frozen by Soty: detect subsequent revisions and either recopy before cutover or exclude post-cutover changes explicitly in UX. Never allow dual writers with “last response wins”.
8. **Rollback code is not reverse data migration.** Once R2 writes are accepted, deploying old web/native bytes must not restore Drive write authority. Maintain a compatibility layer and monotonic backend generation. Reverse migration is a distinct future operation, not automatic rollback.

## Existing R2 accounting hazards

The image quota amendment `20261206159000_catalog_image_storage_quota.sql` sets 100,000,000 bytes / 500 images per current owner scope and exposes `used_bytes`, `pending_deletion_bytes`, `reserved_bytes`, `library_bytes`, `retained_bytes`. Its comment explicitly preserves existing over-limit data and exact dedup. The video schema's initial defaults are 5,000,000,000 bytes/team and 2,147,483,648 bytes/object; its usage query includes `planned`, `uploading`, `verifying`, `ready`, `retiring`. These are **source defaults**, not a live configuration observation.

Migration must inventory current originals, public derivatives, shared global images, staging objects, retiring versions and references separately. A migrated original matching an existing public catalog video is not proof the public object can become the private original. Validate complete bytes/hash, ownership and authorization. Physical dedup should be intra-account only initially; global public pool stays platform overhead unless explicit existing commercial terms say otherwise. Keep retained immutable backup versions in platform cost accounting even when customer-visible logical bytes were freed. Deletion must await all material/catalog/launch/task references and backup retention policy; dropping an R2 use reference is not provider deletion.

## Migration traps to turn into explicit tasks

- **Google-native objects:** native Sheets/Docs are not ordinary blobs. Inventory MIME types, choose export formats, explain loss of live editing/formulas/external links, and preserve unsupported originals/metadata in an exception manifest. Catalog Sheets must be rendered as the compatible Soty feed, not blindly copied as a zero-byte material.
- **Shortcuts/external objects:** resolve only within permitted scope; detect cycles and shared targets; cannot silently import another owner's whole Drive. Preserve unresolved shortcut records with owner action.
- **Shared Drive and root changes:** membership, resource keys, deleted/moved roots and paginated scans can alter inventory. Baseline root identity, change tokens and scope; expired tokens require rescan with a new checkpoint.
- **Existing public URLs:** R2 image/video URLs and external catalog integrations need retention. Keep public object keys stable; do not delete legacy R2 buckets as “old Google storage”. A Google URL cannot be redirected by Soty DNS.
- **Long-lived catalog work:** foreground/native execution, scheduled update, automatic content and restitch variants need admission freeze and resumable generation fencing. An idle UI does not prove no writer is active.
- **Unknown outcomes:** provider accepted upload but SQL response lost must reconcile by immutable receipt+hash. Retry cannot allocate a second billed object or publish a different catalog generation.
- **Change after copy:** compare actual source revision and verified content against final manifest; “same name and size” is insufficient. Drive metadata version increments can occur without byte changes; existing `handler.ts` already distinguishes checksum-based content identity.
- **External Drive editing after cutover:** old Google content stays user-owned and untouched. Later external edits are not imported, and no periodic auto-sync should resurrect old authority.
- **Credential retirement:** keep only credentials required for nonmigrated maintenance and Google-URL bridges; remove from migrated ordinary work only after outstanding grants/jobs are fenced. Google login credentials and Drive tokens are separate.
- **Global provider outage:** R2+Cloudflare Worker+Cloudflare DNS can fail together. A second bucket alone does not provide an independent user path; the control plane, auth, DNS, secrets, public URL routing and metadata recovery all need explicit DR scope.

## Limits of this evidence

This source inventory does not establish deployed migration version, total storage bytes, bucket countries, backup policy, object counts, request costs, current credential scopes, production traffic or supported provider checksum APIs. Parent planning must attach read-only live CLI/provider evidence where available and make missing measurements explicit release prerequisites. No implementation readiness claim should infer these from filenames or hard-coded defaults.
