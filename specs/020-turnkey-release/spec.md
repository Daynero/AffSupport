# Feature Specification: Реліз під ключ на слабкій машині

**Feature Branch**: Не створюється; каталог специфікації незалежний від гілки.

**Created**: 2026-09-08

**Status**: Draft — ready for planning

**Input**: Автоматизувати повний реліз Soty без втручання власника, максимально зменшити участь ШІ; перед важкими або паралельними операціями чекати достатніх ресурсів слабкої машини. Доступи до ПК, сервісів, баз даних і ключів уже налаштовані.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Один запуск до перевіреного production (Priority: P1)

Власник або агент задає релізний намір один раз. Система самостійно проводить підготовку, перевірки, пакування двох платформ, публікацію, підписування, розгортання та перевірку доступного користувачам результату. Рутинні кроки не потребують нових повідомлень власника чи рішень моделі.

**Why this priority**: Перенесення координації в автоматичний процес усуває основне джерело повторного читання інструкцій, логів і ручного перенесення стану.

**Independent Test**: На ізольованих релізних призначеннях провести повний реліз із наперед заданими входами, без моделі після запуску; перевірити артефакти, походження та фінальні публічні результати.

**Acceptance Scenarios**:

1. **Given** готовий релізний намір і доступи, **When** реліз запущено, **Then** всі фази виконуються автоматично в дозволеному порядку й видають один підсумок з доказами завершення.
2. **Given** бракує кількох передумов, **When** виконується попередня перевірка, **Then** система повідомляє всі виявлені проблеми одним результатом до важких збірок і production-змін.
3. **Given** Windows build-only smoke не пройшов, **When** план доходить до публікації, **Then** tag і Release не створюються.
4. **Given** артефакти опубліковані, але live manifest ще старий, **When** перевіряється завершення, **Then** реліз залишається незавершеним і система очікує в межах установленого бюджету.

### User Story 2 - Машина залишається придатною до роботи (Priority: P1)

Перед кожною важкою операцією система перевіряє стан усієї машини, резервує доступні ресурси й чекає їх стабільного звільнення. Власник може продовжувати працювати; реліз не вбиває його процеси.

**Why this priority**: На слабкій машині одночасні компілятори, тести, архіватори та локальна база можуть спричиняти swap, перегрів і збої, які потім потребують дорогого розбору.

**Independent Test**: Подати контрольовану послідовність показників навантаження та запитів на роботу; перевірити заборону запуску, автоматичне очікування і допуск після стабілізації, без запуску реальних production-операцій.

**Acceptance Scenarios**:

1. **Given** пам’ять під тиском або CPU зайнятий, **When** готова збірка, **Then** вона переходить в очікування ресурсів без виклику ШІ.
2. **Given** показники коливаються навколо порога, **When** один вимір став прийнятним, **Then** важка операція не починається до повного стабільного вікна.
3. **Given** вже виконується важка локальна робота, **When** готова незалежна друга, **Then** у стандартному профілі вона чекає, включно з вкладеними збірками та тестами.
4. **Given** віддалена збірка виконується в CI, **When** локальні ресурси зайняті, **Then** її віддалене виконання та компактний моніторинг продовжуються; локальний важкий крок чекає.
5. **Given** навантаження зросло під час неподільного пакування, **When** його не можна безпечно призупинити, **Then** система не запускає нової важкої роботи, зберігає моніторинг і застосовує визначену для кроку політику завершення чи контрольованого переривання.

### User Story 3 - Продовження після переривання без повторної публікації (Priority: P1)

Після закриття чату, сну ПК, перезапуску процесу або тимчасової втрати мережі реліз продовжується зі збереженого і повторно перевіреного стану.

**Why this priority**: Повторне відтворення історії агентом витрачає контекст і створює ризик дублювання зовнішніх дій.

**Independent Test**: Перервати виконання до і після кожної зовнішньої зміни, відновити його та звірити кількість реальних дій і незмінність опублікованих артефактів.

**Acceptance Scenarios**:

1. **Given** CI запущено, але відповідь втрачена, **When** процес відновлено, **Then** він знаходить лише однозначно відповідний запуск і не створює другий навмання.
2. **Given** upload завершився до аварії, **When** реліз продовжується, **Then** існуючий asset перевіряється і не перезаписується.
3. **Given** змінився код або середовище, **When** завантажено старе свідчення успіху, **Then** залежні результати визнаються застарілими; опубліковані bytes залишаються незмінними.
4. **Given** два процеси запускають реліз для одного призначення, **When** другий намагається виконати зміни, **Then** він отримує стан уже активного релізу й не виконує конкурентних записів.

### User Story 4 - ШІ потрібний лише для нестандартного збою (Priority: P2)

Агент отримує компактне завдання з конкретною помилкою, коли автоматичний процес вичерпав дозволені способи відновлення. Звичайний прогрес, тривале очікування та успішні команди не запускають модель.

**Why this priority**: Кількість рішень ШІ та обсяг переданих логів повинні зменшитися вимірювано.

**Independent Test**: Змоделювати успіх, повторювані мережеві помилки та детерміноване падіння тесту; підрахувати звернення до моделі та обсяг переданих діагностичних даних.

**Acceptance Scenarios**:

1. **Given** штатний реліз, **When** проходять усі кроки, **Then** автоматичний процес не потребує жодного виклику моделі.
2. **Given** тимчасова мережева помилка, **When** наступна дозволена спроба успішна, **Then** ШІ не залучається.
3. **Given** стабільно падає конкретний тест, **When** класифіковано збій, **Then** видається один діагностичний пакет з його оригінальною помилкою, доказами та дозволеним місцем продовження.
4. **Given** виправлення змінило SHA після публікації, **When** агент повертає результат, **Then** він не може продовжити старий реліз з новими binaries під старою версією.

### User Story 5 - Реліз включає заздалегідь описані зміни сервісів (Priority: P2)

Якщо версія потребує змін бази чи серверних функцій, вони входять до єдиного релізного наміру з порядком виконання, перевірками сумісності й відновлення. Наявність доступів дозволяє виконати ці кроки без ручного перенесення команд.

**Why this priority**: Пакування клієнта не забезпечує реліз під ключ, якщо необхідні серверні залежності залишилися ручними.

**Independent Test**: На ізольованій базі провести реліз із наперед визначеною міграцією та функцією; повторити відновлення після втраченої відповіді й перевірити відсутність подвійних змін.

**Acceptance Scenarios**:

1. **Given** реліз не містить серверних змін, **When** він виконується, **Then** жодних записів до production-бази не відбувається.
2. **Given** визначені сумісні серверні зміни, **When** їхні передумови виконані, **Then** вони застосовуються в заданому порядку з перевіркою фактичного стану перед залежним deploy.
3. **Given** знайдено невідому міграцію чи інший цільовий проєкт, **When** перевіряється план, **Then** зміни не виконуються і формується конкретний блокер.

### Edge Cases

- Брудна робоча копія, сторонні файли, конфлікт гілок або віддалена гілка просунулася після freeze.
- Повторний запуск з тією самою версією, tag на іншому SHA, asset з іншою сумою, частково опублікований Release.
- Стара beta-перевірка, beta bundle у спільному каталозі production-збірки, зниклий або змінений portable input.
- Прострочена сесія, заблоковане сховище ключів, недоступна база, rate limit, неоднозначний результат upload чи dispatch.
- Сон ПК, відсутність мережі, завислий дочірній процес, пошкоджений журнал, старе блокування при ще живому процесі.
- Брак диска перед архівацією, невідомі показники температури, тривалий swap, зміна доступної пам’яті після допуску.
- Локальна beta/dev-програма виконує роботу; сторонній build стартував після перевірки ресурсів.
- Реліз опублікований частково, а наступний крок потребує зміни коду; публікація не скасовується автоматично.
- Manifest-only commit потребує нового beta-свідчення, але не перебудови вже опублікованих production-артефактів.
- Скасування під час непереривної зовнішньої зміни: стан спочатку звіряється, залежні дії не запускаються.

## Requirements _(mandatory)_

### Functional Requirements

#### Межі та релізний намір

- **FR-001**: Система MUST приймати один релізний намір: цільовий репозиторій і середовище, вихідний commit, версію або явне правило її підвищення, release notes або правило їх детермінованого формування, платформи, серверні зміни та профіль ресурсів. Усі вибрані значення фіксуються до публікації.
- **FR-002**: Один запуск MUST дозволяти всі наперед визначені штатні дії релізу без повторних підтверджень власника. Відсутність доступу чи невизначена зміна поза наміром є блокером, а не підставою вигадувати нові дії.
- **FR-003**: Система MUST мати режими попередньої перевірки без зовнішніх записів, запуску, читання стану, продовження та контрольованого скасування. Режим перевірки MUST показувати послідовність і заплановані зовнішні зміни.
- **FR-004**: Автоматизація MUST виконувати канонічний двоплатформний runbook з `docs/PRODUCTION.md`. При впровадженні runner і runbook MUST описувати один процес; додаткова ручна альтернативна процедура не створюється. Зменшення кількості збірок не дозволяє пропускати обов’язкові гейти.

#### Повний порядок виконання

- **FR-005**: До важких робіт preflight MUST перевірити походження коду, стан гілок, конфлікти версії/tag/assets, доступи до потрібних сервісів, локальні інструменти, налаштовані ключі, схвалені portable inputs поза вихідними каталогами, beta isolation, доступність потрібної локальної бази, порти, диск і ресурсний профіль. Усі незалежні виявлені помилки повертаються разом без значень секретів.
- **FR-006**: Підготовка MUST використовувати визначений commit і відокремлену чисту релізну робочу копію, якщо основна копія містить сторонню роботу. Система MUST NOT автоматично включати сторонні зміни, скидати їх або довільно розв’язувати конфлікти. Потрібні зміни версії та release notes формуються детерміновано в межах релізного наміру.
- **FR-007**: Freeze MUST завершити необхідні перевірки, зафіксувати release SHA, забезпечити його присутність у `main` і `beta` та створити чистий packaged-beta verification саме для цього SHA. Просування гілок MUST NOT затирати конкурентну історію. Production-контракти перевіряються на production output, не на залишеному beta bundle.
- **FR-008**: Пакування MUST створити macOS-артефакти з release SHA, перевірити їх контрольні суми й дочекатися успішного Windows build-only smoke для того самого SHA до створення tag/Release. Віддалений запуск MUST бути однозначно пов’язаний з релізом, режимом і SHA, а не вибраний просто як останній.
- **FR-009**: Публікація MUST створити tag/Release на release SHA, завершити upload macOS asset і використати лише канонічний Windows publish workflow для опублікованого installer. Його smoke та відновлення production public key зберігаються; приватний production entitlement key не передається в CI.
- **FR-010**: Система MUST перевірити фактично опубліковані bytes обох платформ, підписати manifest їхніми точними digest, перевірити підпис і release-контракти та створити окремий manifest commit. Цей commit MUST містити лише дозволену зміну підписаного manifest.
- **FR-011**: Перед web deploy manifest SHA MUST бути на `main` і `beta` та пройти власну чисту packaged-beta перевірку. Production binaries MUST NOT перебудовуватися через manifest-only commit.
- **FR-012**: Успіх MUST вимагати одночасно: недрафтовий Release; обидва assets uploaded з очікуваними digest; tag на release SHA; `main` і `beta` на manifest SHA на момент фінальної перевірки; live manifest з правильною версією, підписом і обома digest; доступний очікуваний web release; підтверджені серверні зміни, якщо вони входили в намір; чиста релізна робоча копія. Невідповідність MUST залишати реліз незавершеним.

#### Допуск за ресурсами слабкої машини

- **FR-013**: Кожен крок MUST мати клас навантаження, оцінку потрібної пам’яті та тимчасового диска, властивість безпечного переривання і часовий бюджет. До важких належать збірки, тести, локальна база з тестами, пакування, архівація, великі копіювання та перевірки великих артефактів.
- **FR-014**: Стандартний профіль слабкої машини MUST дозволяти щонайбільше одну важку локальну операцію та послідовне виконання її важких підоперацій. Низький пріоритет є обов’язковим, але не вважається обмеженням CPU. Паралельність тестів і компіляторів MUST також підпорядковуватися профілю.
- **FR-015**: Перед кожним важким запуском і перед додаванням паралельної локальної роботи система MUST перевіряти загальне завантаження CPU, доступну пам’ять і memory pressure, тенденцію swap, доступний диск та доступний термальний статус. Виміри MUST враховувати сторонні процеси, а рішення — сумарні резерви вже допущених робіт.
- **FR-016**: Початковий профіль MUST вимагати 30 секунд стабільно прийнятних вимірів з інтервалом 5 секунд: CPU не вище 50% усієї машини; нормальний memory pressure; доступна пам’ять не нижче оцінки наступної роботи плюс резерв максимум із 1 GiB та 15% фізичної пам’яті; вільний диск не нижче оцінки тимчасових даних плюс 5 GiB; swap не зростає більш ніж на 128 MiB за це вікно; немає повідомлення про серйозний або критичний термальний стан. Пороги MUST бути налаштовуваними й зафіксованими в записі релізу. Це початкові правила допуску, а не обіцянка пікового споживання.
- **FR-017**: Невідомі оцінки важкого кроку MUST замінюватися консервативним профілем, явно визначеним до виконання; невідоме значення не дорівнює нулю. Недоступна температура MUST позначатися як невідома з продовженням у послідовному профілі за рештою сигналів. Відсутність достовірних CPU, пам’яті або диска MUST забороняти новий важкий запуск і викликати повтор вимірювання.
- **FR-018**: Невиконані ресурсні умови MUST переводити крок у `waiting_resources` із причиною та часом наступного виміру. Очікування MUST автоматично продовжуватися без ШІ, не витрачати бюджет виконання кроку і не вважатися помилкою лише через тривалість. Може діяти лише явно заданий власником загальний deadline релізу.
- **FR-019**: Після допуску моніторинг MUST тривати. При погіршенні стану система MUST припинити нові важкі запуски, зменшити керовану паралельність там, де це підтримується, та застосувати заздалегідь визначену політику кроку. Система MUST NOT довільно suspend/kill сторонні процеси або зайняту Soty Dev/Beta; непереривні зовнішні зміни спочатку доводяться до відомого стану.
- **FR-020**: Віддалені CI-роботи MUST NOT займати локальний важкий слот лише через очікування. Їх запуск і перекриття локальними роботами дозволені тільки за залежностями канонічного порядку. Локальні downloads, розпакування та hash-перевірки MUST мати власний ресурсний допуск.
- **FR-021**: Після кожної важкої роботи наступна MUST знову пройти стабільне вікно; фіксована сліпа пауза не замінює вимірювання. Періоди сну ПК, ресурсного очікування та фактичного виконання MUST обліковуватися окремо; кожен виконуваний крок має скінченний timeout і визначену політику щодо своїх дочірніх процесів.

#### Стан, повтори та незмінність

- **FR-022**: Система MUST зберігати стійкий журнал до і після кожного кроку та зовнішньої зміни: намір, ідентичність входів, спроби, час, стан, посилання на докази та наступний дозволений крок. Закриття чату MUST не зупиняти runner; після зупинки ОС MUST бути можливе продовження без реконструкції історії моделлю.
- **FR-023**: Повторне використання успіху MUST спиратися на перевірені SHA, середовище, конфігурацію без секретів, ідентичність інструментів/входів і потрібні digest. Запис «done» сам по собі недостатній. Зміна залежності MUST інвалідувати лише залежні неопубліковані результати; обов’язкові exact-SHA beta та платформні smoke не замінюються кешем іншого commit.
- **FR-024**: Для одного релізного призначення MUST існувати один власник виконання. Відновлення MUST перевірити, чи попередній процес і його діти ще активні, та звірити зовнішній стан перед зняттям старого блокування або повтором дій.
- **FR-025**: Тимчасові мережеві збої MUST отримувати обмежені повтори з наростаючими інтервалами, варіацією затримки та дотриманням rate-limit відповідей. Стандарт — до п’яти спроб і 15 хвилин на одну операцію. Очікування активного CI є окремим станом з бюджетом відповідного workflow, не серією помилок.
- **FR-026**: Після невідомого результату dispatch, upload, commit/push, deploy чи міграції система MUST спочатку встановити фактичний результат за ідентичністю операції. Якщо відповідність неоднозначна, MUST зупинити залежні зміни з діагностикою, а не виконувати сліпий повтор.
- **FR-027**: Детерміновані помилки тестів, підписів, digest, конфлікти версії чи історії MUST NOT запускати автоматичний цикл rebuild/retry. Заборонені переміщення tag, заміна published assets і зміна зафіксованої версії. Виправлення коду після публікації потребує нового релізного наміру; проблема спостереження не є причиною нової збірки.
- **FR-028**: Скасування MUST забороняти нові кроки, контрольовано завершувати тільки власні процеси, звіряти незавершені зовнішні дії та зберігати місце продовження. Автоматичне видалення Release або відкат бази не є частиною скасування.

#### Доступи, база та секрети

- **FR-029**: Наявні доступи MUST використовуватися без копіювання секретів у модельний контекст, журнал, артефакти чи відстежувані файли. Діагностичний вивід і збережені логи MUST очищатися від секретів до запису. Система MUST NOT генерувати чи замінювати production-ключі як спосіб виправлення доступу.
- **FR-030**: Серверні зміни MUST бути явним списком із вихідного commit: призначення, порядок, залежності, перевірки до/після, сумісність із попередньою опублікованою версією та стратегія відновлення. Без такого списку production-база залишається без записів; analytics CLI залишається тільки read-only.
- **FR-031**: Включені міграції та серверні функції MUST перевірятися в ізольованій beta до production; застосовуватися лише штатними засобами до перевіреного проєкту, з урахуванням уже виконаних змін. Новий ad-hoc SQL, скидання production-бази, автоматичні руйнівні міграції та імпровізовані відкати поза наміром заборонені. Для v1 допускаються автоматично лише зміни, сумісні з попереднім клієнтом протягом розгортання; решта блокують preflight.

#### Мінімальна участь ШІ та спостережуваність

- **FR-032**: Визначення наступного кроку, перенесення SHA/run ID, очікування, допустимі повтори, завантаження конфігурації, штатне підписування і фінальна звірка MUST виконуватися без моделі. Інтерфейс MUST дозволяти запустити реліз і перевірити підсумок без відкритого чату чи періодичних агентних tool calls.
- **FR-033**: Система MUST видавати короткі структуровані події тільки при зміні стану та зберігати повну очищену діагностику локально. Незмінні polling-відповіді MUST NOT передаватися агенту. Підсумок успіху — до 20 рядків і 8 KiB; пакет помилки — до 100 рядків і 16 KiB, із кодом збою, оригінальною помилкою, фазою, спробами, станом публікації, посиланнями на логи та умовою продовження.
- **FR-034**: Передача роботи ШІ MUST відбуватися один раз на унікальний невирішений збій після дозволених повторів. Однаковий стан не створює нових звернень. Повернення від ШІ не означає успіху: виправлений крок і всі інвалідовані залежності MUST знову пройти перевірки.
- **FR-035**: Кожен реліз MUST звітувати про фактичний час роботи, ресурсне очікування, CI-очікування, повтори, кількість звернень до ШІ, обсяг переданих йому даних та повторних важких робіт. Реальні токени обліковуються лише за доступними даними сесії; відсутні дані позначаються невідомими, не нульовими. До/після порівнюється на однаковому сценарії, окремо для успіху і збоїв.

#### Стани та детерміноване продовження

- **FR-036**: Статус MUST розрізняти щонайменше стани нижче. Кожне очікування має причину, наступну автоматичну дію та окремий облік часу. `blocked` MUST NOT маскувати успіх або запускати нову спробу без зміни відповідних передумов.

| Стан                | Значення                                              | Умова наступної дії                                      |
| ------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| `preflight`         | Перевіряються передумови й фіксується намір           | Усі обов’язкові передумови підтверджені                  |
| `ready`             | Залежності кроку виконані                             | Ресурсний допуск або початок легкої операції             |
| `waiting_resources` | Машина ще не готова                                   | Стабільне вікно прийнятних вимірів                       |
| `running`           | Виконується конкретна локальна або зовнішня дія       | Підтверджений результат, timeout або невідомий результат |
| `waiting_remote`    | Віддалений процес працює або результат ще поширюється | Фінальний статус чи вичерпання бюджету очікування        |

| `cancelling`        | Нові кроки зупинені, поточна дія звіряється           | Власні процеси завершені й зовнішній стан відомий        |
| `cancelled`         | Виконання зупинене з місцем продовження               | Явне продовження того самого наміру                      |
| `completed`         | Усі кінцеві умови перевірені                          | Термінальний стан цього виконання                        |

- **FR-037**: Залежні операції MUST дотримуватися наступної послідовності. Кожна важка локальна дія, включно з підготовкою робочої копії та локальної beta-бази, додатково проходить FR-013–FR-021. Таблиця визначає результати фаз, а не нові команди замість канонічного runbook.

| Фаза                    | Автоматична робота                                                                                            | Доказ для переходу далі                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |

| 10. Live acceptance     | Звірити всі умови FR-012, очистити лише власні тимчасові ресурси                                              | Один підсумок завершення та збережені докази                                |

- **FR-038**: Серверні кроки MUST мати явно визначену позицію перед першою залежною перевіркою чи публікацією. Якщо production readiness потребує нової серверної можливості, її сумісна зміна виконується після успішної beta-перевірки і перед цим readiness gate. Якщо залежність потрібна лише новому web, зміна виконується перед web deploy. В обох випадках стара опублікована версія MUST залишатися працездатною. Неможливість такого порядку блокує preflight; система не переставляє гейти навмання.
- **FR-039**: Ресурсні резерви MUST враховувати весь час життя власної локальної бази й інших довготривалих служб, а не лише їх запуск. Зупинка вже наявної чужої служби заради звільнення пам’яті заборонена. Власна непотрібна служба може бути завершена на визначеній межі фази; докази для відновлення зберігаються.
- **FR-040**: Після успіху або скасування система MUST видаляти лише однозначно власні тимчасові дані, які не потрібні для відновлення чи перевірки релізу. Журнал, очищені логи, перевірки та походження опублікованих артефактів MUST зберігатися щонайменше 30 днів за стандартною політикою; активний незавершений реліз не очищається автоматично. Дефіцит диска не дозволяє видаляти чужі файли чи published assets.

### Key Entities _(include if feature involves data)_

- **Релізний намір**: версія, джерело, призначення, дозволені зміни, notes, платформи й ресурсний профіль; незмінна основа одного релізу.
- **Виконання релізу**: ідентифікатор, власник, release SHA, manifest SHA, поточний стан, часові бюджети й підсумок.
- **Крок і спроба**: залежності, клас навантаження, входи, допуск, початок/кінець, результат, властивість переривання та повтору.
- **Свідчення перевірки**: ідентичність перевірених входів, гейт, SHA, середовище, результат і умови придатності для повторного використання.
- **Артефакт і публікація**: платформа, походження, розмір, digest, локальне/опубліковане розташування та стан завантаження.
- **Ресурсний профіль і вимір**: пороги, резерви, оцінки кроку, часовий ряд навантаження та причина очікування.
- **Зовнішня операція**: ціль, ідентичність запиту, віддалений run/deploy/migration ID, перевірений фактичний результат.
- **Діагностичний пакет**: унікальний збій, обмежений очищений контекст, докази й умова повернення до автоматичного виконання.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: У трьох послідовних контрольних релізах на готовому середовищі після одного запуску потрібно 0 ручних дій і 0 звернень до ШІ для координації; кожен проходить усі кінцеві умови FR-012.
- **SC-002**: Порівняно з зафіксованим ручним агентним проходом того самого сценарію обсяг переданої моделі операційної діагностики зменшується щонайменше на 90%. Якщо доступний облік токенів обох проходів, їхня фактична різниця звітується окремо без заяви про економію, яку не виміряли.
- **SC-003**: У всіх контрольних сценаріях перевантаження жодна нова важка робота не стартує до 30 секунд прийнятних вимірів; у стандартному профілі одночасно працює не більше однієї важкої локальної операції. Після стабілізації та звільнення залежностей запуск відбувається протягом наступних 10 секунд.
- **SC-004**: Після примусового переривання на кожній межі зовнішньої зміни відновлення не створює дублікатів публікацій, не підміняє assets/tag і не повторює міграцію з уже підтвердженим результатом.
- **SC-005**: Успішно завершені й повторно підтверджені важкі кроки з незмінними входами виконуються 0 додаткових разів через закриття чату, втрату відповіді чи помилку моніторингу. Обов’язкові окремі beta/production/platform перевірки не рахуються дублікатами.
- **SC-006**: У сценаріях тимчасової мережевої помилки в межах бюджету відновлення відбувається без ШІ; для одного детермінованого збою видається рівно один обмежений діагностичний пакет до появи нових даних.
- **SC-007**: Контрольні секрети, навмисно включені в тестові помилки, не потрапляють у збережені логи, підсумки чи контекст ШІ; неправильний проєкт, SHA, підпис і digest блокують усі залежні зміни у 100% відповідних сценаріїв.
- **SC-008**: На найслабшій підтримуваній машині, конфігурація якої фіксується перед прийманням, повний контрольний реліз не спричиняє завершення процесів через брак пам’яті; на всьому проході відкриття локального статусу відповідає за 2 секунди у щонайменше 95% вимірів. Час релізу та ресурсного очікування публікується окремо, без обіцянки прискорення ціною чутливості машини.

## Assumptions

- Основний локальний хост v1 — maintainer Mac з обмеженими ресурсами; Windows installer будується віддалено чинним workflow. Автоматизація на Windows як головному хості не входить до v1.
- Доступи та ключі вже налаштовані й можуть використовуватися без інтерактивного входу. Відновлення забутого пароля, MFA чи випуск нового production-ключа не автоматизуються цим релізним процесом.
- Стандартний сценарій — повний двоплатформний реліз. Окремі режими web-only, dev і beta-only не додаються цією специфікацією.
- Релізний намір поширюється на підготовлений commit. Автоматичне виправлення довільних продуктових дефектів, прийняття рішень про несумісні міграції та генерація довільних shell-команд моделлю не є обов’язками runner.
- Поточні exact-SHA beta gates, Windows build-only і publish smoke, ключові обмеження та незмінність published assets зберігаються. Оптимізація дубльованих build можлива лише за доказом однакових входів, середовища та покриття.
- Політика ресурсоощадності релізу охоплює процеси релізу; вона не змінює налаштування CPU бюджету користувацьких інструментів Soty і не створює другого незалежного механізму suspend для керованих ними дітей.
- Початкові пороги ресурсів є консервативними припущеннями; планування має визначити оцінки кожної важкої роботи та перевірити їх на найслабшій підтримуваній конфігурації. Неможливий для цієї конфігурації резерв має давати зрозумілу причину очікування, а не приховане послаблення порога.
- Джерела обмежень: `docs/PRODUCTION.md`, `docs/BETA.md`, `AGENTS.md`, `.specify/memory/constitution.md`, специфікації 006, 007, 008 і 009. Планування MUST явно врегулювати застарілі формулювання конституції про відповідність tag і web commit щодо чинної пари release SHA / manifest SHA через передбачений процес зміни документа; мовчазний обхід не допускається.
- Ця специфікація визначає вимоги. Вибір реалізації, точні команди, формат журналу, механізм запуску без чату та план тестування належать наступній фазі Spec Kit.

Ці уточнення конкретизують FR-004, FR-015–017, FR-024, FR-026, FR-031 та FR-034 без зміни їхніх ідентифікаторів.

- Запропонована поведінка candidate gates та двох SHA є умовною: до окремого узгодження конституції відповідні зміни чинних гейтів та реальна інтеграція не виконуються. Сумісні базові модулі й fixtures можуть розроблятися незалежно.
- Повний sandbox-прохід використовує єдину перевірену прив’язку всіх призначень, включно з URL артефактів, підписом, Windows та web/backend. Sandbox виконує ті самі змістовні гейти; production-призначення не можуть бути підмінені параметрами наміру.
- Перед першим важким кроком доступні всі обов’язкові ресурсні сигнали. Probe постачається готовим разом із runner; його відсутність чи невірна ідентичність блокує preflight, не запускає компіляцію за спрощеними правилами.
- Всі локальні релізи на одному ПК ділять один важкий слот. Вкладені дозволи мають одного власника, перевірену ідентичність процесу та покоління; втрата зв’язку не означає звільнення ресурсу.
- Налаштований фоновий міст до агента є необхідною частиною обробки нестандартних збоїв без чату. Тимчасова втрата зв’язку автоматично відновлюється без повторного запуску тієї самої ремонтної задачі. Недоступність агента не видається за успіх.
- Наявність версії міграції у remote history не доводить вміст її джерела. Потрібне попереднє підтвердження виконання або окремо встановлений baseline з достовірним походженням; невідома відповідність блокує автоматичний повтор.

Додаткові acceptance scenarios: sandbox з production-призначенням відхиляється; вкладений процес зі старим дозволом не запускається після restart; відсутній probe не викликає heavy bootstrap; втрачена відповідь агента відновлює той самий job; migration history без підтвердженого джерела дає явний блокер.
