# 035 — «Запуски» (Launches): технічна специфікація

**Статус:** проєкт для погодження та майбутньої реалізації.  
**Дата дослідження:** 12.10.2026.  
**База дослідження:** локальний checkout `8c395374f4082cafbb1f836ab0b2ae090a9f60f1`.  
**Межі цієї роботи:** лише документація; без реалізації, міграцій, зміни компонентів, звернень до production чи Meta API.

У документі **«Факт»** означає перевірене в коді цього checkout; **«Рішення»** — запропонований контракт нового модуля; **«Погодити»** — відсутнє продуктове або зовнішнє підтвердження. Наявність міграції у checkout не доводить її застосування на production. Зокрема, в дереві є міграції з датами пізніше дати дослідження: вони враховані як код, а не як доказ стану розгорнутої БД.

## 1. Мета, межі та основні інваріанти

Launch — окрема сутність простору, яка готує один рекламний URL, N назв кампаній, бюджети й діапазони оголошень; для методу «Каталог» додатково створює одну варіацію наявного товарного каталогу. Користувач переносить результати до Ads Manager самостійно.

- Один Launch містить декілька кампаній; кампанії не стають Tasks або окремими плитками.
- Tasks залишаються універсальними завданнями. Новий модуль не змінює їхню модель, статуси, прогрес чи вкладення.
- Методи тільки `catalog` / `other`. Обидва використовують той самий URL Generator, завжди один рекламний URL на версію запуску. «Мови» не є методом.
- Buyer — текстове значення довідника простору; assignee — учасник простору. Автоматичного зв'язку між ними немає.
- Вік, стать, Advantage+ та дата є текстовими складовими неймінгу. Soty не застосовує реальний таргетинг, не створює кампанії, не виконує запити до Meta/AIO для генерації URL.
- Прев'ю — чистий локальний розрахунок. Генерація файлів і фіксація результатів відбуваються лише після явної дії.
- Збережена версія результату незмінна. Редагування створює робочу конфігурацію, а підтвердження — наступну версію.
- Усі дані ізольовані `team_id`, права перевіряються сервером. Назви, URL, SUB і токени не потрапляють у діагностику.

Поза v1: інтеграція Ads Manager, синхронізація AIO, складний Campaign / Ad Set / Ad builder, кілька креативів, довільний текст у SUB, редактор шаблону неймінгу, автоматична генерація за розкладом, автоматичне створення Tasks/нотаток РК.

### 2.1. Відмінності від припущень початкового опису

1. **BM не виявлено** у досліджених accounts UI/contracts/migrations. Реальний зв'язок: простір → соц → РК. BM не є передумовою запусків; нову BM-сутність не додавати.
2. `teamAgentIdSuffix()` бере останні **символи**, а `normalizeTeamAgentId()` дозволяє не лише цифри. Для Launch потрібна додаткова перевірка числового ID; глобальний контракт РК не змінювати.
3. Генератор приймає **відео**, не довільний image/file (`not_a_video`). Image-креатив для «Каталог» не підтриманий поточним pipeline.
4. Повертається `sheetUrl = Drive webViewLink` Google Sheets. Це посилання Google Drive (`webViewLink`) на створену таблицю каталогу; саме його показувати й копіювати як посилання на каталог.
5. `randomLinkVariation` змінює **videoLink** (`?v=...`), не рекламний `sourceLink`. Нова варіація каталогу та випадковий параметр videoLink — різні механізми.
6. [ProductCatalogProgress.tsx](../../apps/web/src/team/product-catalog/ProductCatalogProgress.tsx) показує **оцінені таймером етапи**, не серверні відсотки. Не видавати його за доказ поступу.
7. `CreateProductCatalogDialog` тримає `processed` і ключ каталогу в React state; цього недостатньо для recovery після reload.
8. Генератор відкриває доступ `anyone reader` до sheet, відео та зображень. Якщо sourceLink містить CAPI token, він потрапить у вміст доступної за посиланням таблиці. Це реальна властивість поточного механізму, яка потребує окремого рішення (§18), а не питання лише логів.
9. У дослідженому коді не знайдено готового campaign naming generator або узгодженого маркера Advantage+. Формат `adv+` нижче є пропозицією.
10. Не виявлено загального поля timezone простору. Є передавання IANA timezone у finance API. Для v1 використовувати timezone браузера без нової timezone-підсистеми.

## 3. Сценарії

### 3.1. Створити запуск

Користувач відкриває «Запуски», натискає «Новий запуск». Форма копіює defaults простору, встановлює завтра, дає вибрати один РК, офер, Buyer і material. Новий офер/Buyer створюється всередині пошукового списку. Завантаження файлу — явна окрема операція користувача; воно може створити material до генерації Launch і не є побічним ефектом прев'ю.

Локальне прев'ю реагує на форму без RPC. «Згенерувати запуск» валідовує конфігурацію, атомарно фіксує намір і версію, обчислює результати на довіреній стороні, за потреби виконує каталог. Після готовності відкривається «Результат».

### 3.2. Повернутися після помилки або закриття

Список читається з сервера. Готовий Launch відкриває останню завершену версію. Draft відкриває налаштування. Незавершена генерація відкриває конфігурацію з відновленим станом операції та дією продовження, не запускає нову варіацію. Якщо є попередня готова версія, вона залишається доступною з явною позначкою її номера.

### 3.3. Змінити готовий запуск

«Налаштування» створює робочу копію з базової версії. Прев'ю змінюється, старий результат — ні. «Оновити результати» показує один компактний diff наслідків: назви/URL/нова варіація каталогу. Підтвердження фіксує нову версію. Cancel повертає до збереженої конфігурації. Історія дозволяє відкрити й скопіювати попередню версію; відновлення старої конфігурації також створює нову версію.

### 3.4. Співпраця

Виконавець та робочий статус редагуються без перерахунку результатів; під час активної генерації їхнє редагування також заблоковане за §12.3. Інший учасник бачить серверний стан, а при конкурентному редагуванні отримує конфлікт версії, не мовчазний overwrite. Перейменування соца/офера/файлу або перенесення РК не перераховує вже видані результати.

### 3.5. Скопіювати запуск

Користувач може виконати «Копіювати запуск» із меню плитки або відкритого запуску. Дія створює **новий Launch-чернетку з окремим ID**, відкриває його налаштування та переносить конфігурацію вибраної збереженої версії; для запуску без готових версій — збережену чернетку. Якщо є незбережені зміни, явно показати, що копіюється збережена конфігурація; не зберігати їх побічно.

Копіюються РК, офер, Buyer, посилання на той самий креатив і його alias, N/maxBudget/ручні бюджети/adsCount, age/gender/Advantage+, метод, оригінальний URL, SUB-конструктор і параметри каталогу/перезашивки. Фізичні файли та довідники не дублюються. Дату нової чернетки встановити на завтра за поточною локальною timezone; виконавця зберегти, якщо він досі активний учасник простору, інакше очистити з поясненням. Робочий статус нового запуску — `todo`.

Готові результати, generated URL, кампанії, каталог, номери варіацій, operations, історія та idempotency keys джерела **не переносяться як результати нового Launch**. Локальне прев'ю розраховується з перенесеної конфігурації. Каталог і нова варіація створюються тільки після явного «Згенерувати запуск» у копії. Зміни копії не змінюють вихідний Launch; видалені або недоступні джерела позначаються й блокують генерацію до виправлення.

Копіювання дозволене в межах того самого простору за правами `view` на джерело та `edit` на створення; сервер перевіряє їх повторно. Подвійне натискання/повтор запиту з одним requestKey створює одну копію. Нова явна дія копіювання має новий requestKey і може створити ще одну незалежну чернетку. У метаданих зберігаються nullable `copied_from_launch_id` / `copied_from_revision_id` для походження; це не спільна історія результатів.

## 4. Інтерфейс

Новий розділ у WorkspaceShell: список компактних LaunchCard, пошук за офером/соцом/alias креативу, фільтри статусу/виконавця, пагінація; один Launch = одна плитка. На плитці: офер, стан готовності, `соц-суфікс`, креатив, метод, `M45+`, `ADV+` якщо on, N кампаній, бюджети, assignee. Стан роботи і стан генерації візуально розрізняються. Меню плитки та відкритого запуску містить «Копіювати запуск» (§3.5); не створювати окремий майстер копіювання.

### Візуальна підказка для незаповнених обов'язкових полів

Поки Launch не готовий до генерації, кожне видиме обов'язкове поле без валідного значення отримує легкий помаранчевий фон/контур із семантичної ролі `warning` (soft/softer token). Після введення валідного значення цей акцент одразу прибирається. Якщо значення знову очищено або стало невалідним — акцент повертається. Це постійна спокійна підказка заповнити конфігурацію, не повідомлення про помилку: не показувати червоний error state лише через початкову порожнечу; помилка з'являється після взаємодії з невалідним значенням або спроби генерації відповідно до DESIGN.md.

Акцент визначається спільним validator-ом і охоплює required поля таблиці §5: РК, офер, Buyer, creative/launch alias, кількість кампаній, максимальний бюджет, кількість оголошень, age, gender, date та URL. У SUB-builder кожне вибране джерело має бути валідним; порожня конфігурація SUB дозволена й не підсвічується. Для методу «Каталог» обов'язкові також productCount, валідні restitch defaults/налаштування та duration, якщо вибрано custom. Умовно приховані поля не підсвічуються. Optional assignee, необрані SUB та вимкнений restitch не є порожніми помилками.

Поля з вибором сутності підсвічуються, якщо сутність не вибрана або її більше не можна використати. Input підсвічується, якщо порожній чи невалідний згідно з тим самим live validation, що блокує генерацію. Власне нормалізація пробілів Buyer/creative та інші автоперетворення спершу показуються як фактичне значення; індикатор зникає лише після того, як нормалізоване значення відповідає контракту. Не підсвічувати всю секцію або вже заповнені поля через помилку іншого поля.

Підсвічування не єдиний сигнал: обов'язковість і незавершений стан доступні через label/aria-describedby та короткий підсумок на кнопці/поруч із дією генерації (наприклад, «Заповніть обов'язкові поля» з числом пропусків). Не дублювати однакове попередження великим текстом під кожним полем. Використовувати токен, що відповідає `warning-soft`/`warning-border`, дотримуватися контрасту обох тем, reduced motion та `check-design-tokens`; без сирого кольору. Валідаційні помилки після submit лишаються окремим, сильнішим error state.

### Фільтри дати

У всіх представленнях модуля «Запуски», де є фільтр дати, використовувати той самий компактний патерн, що в Tasks: **«Календар» → «Вчора» → «Сьогодні»**, саме в такому порядку. Календар — кнопка з чинною іконкою CalendarDays, що відкриває Popover із RangeCalendar для одного дня або діапазону; «Вчора» й «Сьогодні» — видимі поруч кнопки, кожна застосовує фільтр одним натисканням. Вибраний день/діапазон відображається на календарній кнопці, активний quick filter позначається; очищення повертає всі дати.

Повторно використати [TaskDateFilterControl](../../apps/web/src/team/tasks/TaskDateFilter.tsx), який уже підтримує `inlineDays`, `showStatus` та `allowAll`, і helpers дат із [useTasks.ts](../../apps/web/src/team/tasks/useTasks.ts). За потреби винести спільний date-filter primitive, зберігши поведінку Tasks; не створювати другий календар. Статусний фільтр Launch лишається окремим контрактом. Фільтрувати за збереженою **датою запуску launchDate**, не createdAt; для готового запуску — за активною версією результату, для нового без результату — за збереженою чернеткою. Незбережені зміни не пересувають плитку у списку. «Вчора»/«Сьогодні» визначаються за локальною timezone користувача, з календарним переходом через DST; фільтр не змінює дату запуску або default «завтра». Фільтри комбінуються зі статусом/виконавцем і застосовуються сервером до пагінації.

Редактор — повна поверхня всередині простору з вкладками **«Результат» / «Налаштування»**, не ланцюг модальних форм. Налаштування згруповані:

1. Контекст: РК, офер, Buyer, креатив/alias, assignee.
2. Кампанії: N, maxBudget, adsCount, вік із зовнішнім `+`, стать, Advantage+, дата, метод.
3. Поле з підписом **«URL»** в одному рядку; нижче SUB 1/2/3 і їхні прев'ю. У користувацькому інтерфейсі не використовувати назву «AIO URL»: AIO залишається лише контекстом походження посилання в технічному описі.
4. Каталог — умовний блок із restitch/duration, кількістю товарів і станом налаштувань простору.
5. Локальне прев'ю: N, таблиця бюджет/назва/діапазон. Підсумок суми можна показати як довідковий, не замість maxBudget.

На достатній ширині налаштування й sticky-панель прев'ю видимі одночасно; на вузькому екрані — послідовно, без горизонтального скролу форми. Поля компактні, згруповані через flex-wrap відповідно до DESIGN.md. Вік приблизно на дві цифри за візуальною шириною, але без `maxLength=2`; більше число доступне для редагування й прочитання. За потреби вводиться семантичний sizing token, не raw CSS.

Результат: короткий заголовок, один URL, N назв із бюджетами, назва каталогу та наявні посилання, assignee, статус, номер версії. Не дублювати форму. У режимі перегляду весь рядок значення — доступний copy control (`Enter`/`Space`, aria-label); кожне згенероване поле також має доступний inline-режим редагування за §4.1. Під час введення/виділення тексту копіювання не спрацьовує; після успішного `clipboard.writeText` — коротке success-підсвічення токеном і toast/aria-live. При відмові clipboard — помилка й можливість виділити текст, без фальшивого «скопійовано». Довгі рядки переносяться/розгортаються, копіюється повне точне значення. Дію відкриття посилання, якщо потрібна, відокремити від копіювання. Існуючі catalog dialogs використовують окремі copy buttons: повнопольовий CopyResultField — новий тонкий UI-компонент на наявних primitives.

Усі нові підписи — через поточний i18n; українська/інші підтримані локалі без зміни канонічних згенерованих рядків.

### 4.1. Ручне редагування згенерованих результатів перед копіюванням

На вкладці «Результат» користувач може змінити **будь-яке показане згенероване значення**: рекламний URL, назви кампаній, їхні бюджети й діапазони оголошень, згенеровану назву каталогу та посилання Google Drive на каталог; також SUB або інші похідні значення, якщо вони показані окремими полями. Не потрібно повертатися до налаштувань або повторно генерувати запуск для такої правки. Службові ID/стан операції не є редагованими результатами; виконавець і робочий статус мають свої звичайні контроли.

Для кожного поля зберігається базове згенероване значення та окреме ручне override. Показане й скопійоване значення — override, якщо воно відрізняється від базового, інакше baseline. Після зміни поле одразу отримує **помаранчеве підсвічення** через семантичні `warning` tokens та текстову позначку **«Змінено вручну»**. Ознака доступна для screen reader і не передається лише кольором. Позначка залишається після копіювання та збереження; короткий зелений copy-success не стирає її. Якщо повернути точне початкове значення або виконати «Відновити згенероване», override і помаранчева позначка прибираються.

У режимі перегляду натискання на поле копіює його поточне значення, як визначено вище; контекстна дія «Редагувати» на рядку або з клавіатури переводить у звичайний Input/Textarea. У режимі редагування натискання ставить курсор, а не копіює текст. Завершення редагування повертає copy-поведінку; без зайвого модального вікна. Введення URL/назв не нормалізувати непомітно; копіювати точний текст. Порожнє значення або некоректний числовий формат позначити локально, не підміняти попереднім значенням; явно показати, яке значення буде скопійовано. Зафіксовані генератором бюджети й діапазони не переписуються через такі ручні правки.

Ручна правка **не запускає перерахунок інших полів або важкі операції**. Наприклад, зміна бюджету в результаті сама не переписує текст назви; користувач може відредагувати обидва поля. Зміна URL не оновлює вже створений каталог, а зміна показаної назви каталогу не перейменовує фізичний файл. Біля залежних результатів показати компактну ознаку розходження/підказку: «Змінено для копіювання; каталог не оновлено». Справжня зміна конфігурації й генерація нової варіації лишаються явною дією через налаштування.

Правки доступні для копіювання одразу з локальної робочої копії. Дія «Зберегти ручні зміни» фіксує їх як нову незмінну result revision із посиланням на базову, автором і часом; попередні значення зберігаються. До save відображати стан незбережених змін і попереджати при виході, не записувати секретні поля до localStorage. Не вимагати save перед копіюванням. Збережені overrides відновлюються при повторному відкритті. Сервер перевіряє `edit`, team scope та expectedVersion; користувач із `view` може читати й копіювати, але не зберігати/редагувати результати. Copy action працює з активним ручним значенням, включно з незбереженим.

Подальша автоматична генерація створює новий baseline і не переносить старі overrides мовчки: явно показати їх наявність і дозволити залишити попередню версію або підтвердити новий результат. «Копіювати запуск» переносить конфігурацію, а не ці ручні результати, відповідно до §3.5.

## 6. Бюджети й оголошення

Для `i = 1..N`: `budget[i] = Math.round(i * maxBudget / N)`.

Приклади для max=30: N=1 → `[30]`; N=2 → `[15,30]`; N=3 → `[10,20,30]`; N=4 → `[8,15,23,30]`; N=5 → `[6,12,18,24,30]`. max=70,N=5 → `[14,28,42,56,70]`. Округлення має бути ідентичне JS Math.round для додатних значень на клієнті й сервері; не використовувати banker's rounding.

Нульові/повторювані бюджети — blocking error. Нічого не підвищувати мовчки. Для автоматичного масиву в цьому домені maxBudget<N не дає N різних додатних цілих; перевіряти також фактичний масив.

**Рішення щодо ручного режиму:** дозволити редагування рядків бюджету; масив повинен бути строго зростаючим, цілочисельним, >0, <=maxBudget, останнє значення дорівнює maxBudget. Це зберігає значення поля «максимальний бюджет». Зміна N/maxBudget при overrides позначає їх як такі, що потребують узгодження; не обрізати/перераховувати непомітно. Дати явну дію «Перерахувати автоматично». До коректного масиву генерація заблокована. Defaults зберігають N/maxBudget, не індивідуальні overrides.

Для campaignIndex від 1: `start=(campaignIndex-1)*adsCount+1`, `end=campaignIndex*adsCount`. N=3,ads=3 → 1–3/4–6/7–9; ads=4 → 1–4/5–8/9–12. ads=1 → `(1-1)`, `(2-2)` тощо за фіксованим шаблоном. Нумерація починається з 1 у кожному Launch, глобальних лічильників оголошень немає. Внутрішня структура умовно 1-1-N, окремі сутності Ad/AdSet не створюються.

## 7. SUB builder

```json
{
  "schemaVersion": 1,
  "sub1": ["buyer"],
  "sub2": ["social", "adAccountSuffix", "creative"],
  "sub3": ["creative"]
}
```

Це приклад початкової конфігурації, яку можна змінити й зберегти як defaults; не hardcoded-правило для всіх запусків. Змінні мають стабільні технічні ключі, labels локалізуються. У межах одного SUB змінна може бути присутня один раз, між SUB повторення дозволені. Максимум 4 значення. Порядок масиву — порядок об'єднання через `-`; сортування за алфавітом неприпустиме.

SelectMenu/Popover із пунктами Buyer/Соц/РК/Креатив: вибрані мають індикатори ①②③④, доступне озвучення «вибрано, позиція 2». Зняття стискає порядок, повторний вибір додає в кінець. Reorder через клавіатурні «вище/нижче» і, за бажанням, drag; drag не є єдиним способом. Без поля довільного тексту. Під кожним SUB — живий результат.

Обчислення використовує alias креативу, назву соца і суфікс ID, не фізичні шляхи. Вибрана змінна без значення — помилка, не тихе пропускання. Порожній масив — **preserve**, а не команда очистити параметр: наявні входження відповідного SUB зберігаються; відсутній параметр не додається. У прев'ю для такого рядка: «Залишити значення оригінального URL», за потреби з маскованим оглядом наявності; не показувати «порожній», якщо URL вже містить SUB.

## 8. Генератор рекламного URL

### 8.1. Межа сумісності

**Погодити перед реалізацією:** фактичні AIO query keys. Пропозиція v1 — точні case-sensitive `sub1/sub2/sub3`. Не вгадувати `sub_id_1`, `SUB1`, `sub_1` або регістр. Для альтернативної схеми потрібне явне versioned mapping, перевірене на знеособленому прикладі AIO. Весь подальший алгоритм виходить із `sub1/sub2/sub3`.

Не використовувати поточний catalog `validateWebLink` як повний валідатор Launch: він видаляє всі whitespace і додає https, а це недостатньо для вимоги збереження AIO.

### 8.2. Алгоритм: оригінальний URL незмінний, змінюються тільки SUB 1/2/3

1. Зберігати `originalUrl` **точно в тому вигляді й послідовності символів, як його надав користувач**. Не trim, не нормалізувати, не додавати схему, не декодувати й не серіалізувати вихідний рядок. Зовнішні/внутрішні whitespace, control chars, credentials в authority, відсутня схема, не HTTP(S) або невалідний host можуть зробити генерацію невалідною; у такому разі зупинитися й попросити користувача виправити URL. Валідація не переписує і не замінює оригінал.
2. Структурно виділити fragment, path/authority та raw query, зберігаючи точні межі й байти компонентів. Парсер/`new URL` можна використати тільки для перевірки, **не** для серіалізації фінального URL. Макроси `{{...}}` у path/query/fragment мають лишитися точними; не переписувати scheme/authority.
3. Query представити впорядкованим списком raw-сегментів, розділених `&`; пару розділити за першим `=`. Ключем керованого параметра є точний case-sensitive raw key `sub1`, `sub2` або `sub3`. Інші ключі, включно з інакше закодованими чи іншим регістром, не трактувати як керовані SUB. Зберегти кожен сегмент, separator, дублікати, порожні частини та представлення інших параметрів; не перетворювати query на object/map.
4. Не декодувати й не перекодовувати сторонні keys/values. Розпізнавати тільки буквальні raw keys `sub1/sub2/sub3`; некоректні percent sequences у будь-якій іншій частині лишаються як є, але якщо через них URL не приймається валідатором — показати помилку без сирого URL у діагностиці.
5. Для SUB з непорожнім builder обчислити й провалідувати значення, percent-encode тільки його один раз (UTF-8). Якщо точний ключ уже є — замінити **тільки raw value після першого `=` в кожному входженні цього SUB**, не змінюючи raw key, порядок, кількість дублікатів, позиції чи інші сегменти. Якщо наявний сегмент має вигляд `subN` без `=`, перетворити його на `subN=<encoded>`. Якщо ключа немає — додати тільки новий `subN=<encoded>` у query перед fragment, зберігши весь попередній рядок; додавати відсутні керовані параметри в порядку sub1/sub2/sub3.
6. Для SUB з порожнім builder не змінювати жодного входження, включно з `subN=`, `subN`, дублікатами. Усі інші параметри, весь path/authority, fragment, порядок, `%2F`/`%2f`, `+`, `=`, макроси й кожен байт вихідного URL залишаються точно як у `originalUrl` користувача.
7. Зібрати generated URL із незмінених raw компонентів і відредагованих лише value керованих SUB; separator додавати тільки для відсутнього керованого параметра. Перевірити довжину обох URL: <=8192 для сумісності з catalog SOURCE_LINK_MAX. Зберегти оригінал дослівно, generated URL і `urlGeneratorVersion`/mapping version.
8. Кожний розрахунок стартує з `originalUrl`. Повторне застосування до generated URL не є API цього модуля. Не fetch URL і не розгортати Facebook-макроси.

Інваріант: `originalUrl` ніколи не перезаписується generated URL. У generated URL кожен фрагмент поза значеннями точних `sub1/sub2/sub3` та separator-ом для доданого відсутнього SUB дорівнює оригіналу byte-for-byte. Формулювання «змінюються тільки SUB 1/2/3» означає, що для наявних ключів міняються тільки їхні values; параметр додається лише коли відповідний builder непорожній, а ключа ще немає.

Приклад (вигадані домен/значення):

```text
original: https://example.invalid/p?pixel=123&sub1=old&sub1=older&x=a%2Fb+z&fb={{campaign.id}}#top
builder:  sub1=[buyer], buyer=patrik; sub2=[], sub3=[]
result:   https://example.invalid/p?pixel=123&sub1=patrik&sub1=patrik&x=a%2Fb+z&fb={{campaign.id}}#top  (показано збереження дублікатів; кожне значення керованого sub1 замінене)
```

На рівні технічного encoder значення `a&b+c` стало б `a%26b%2Bc`, але погоджена валідація змінних SUB (§8.3) відхиляє його до генерації; `creative=v5` не змінює наявні AIO campaign IDs. Без вибраних змінних в усіх трьох SUB generated URL byte-for-byte дорівнює originalUrl. Невідомі ключі, включно з `sub4`, незмінні.

### 8.3. Єдині правила значень SUB: читабельність і blocking validation

**Погоджене рішення:** єдина нормалізація й валідація застосовується до Buyer, назви креативу для запуску та всіх інших змінних SUB: соца й суфікса РК. Дозволені тільки латинські літери `A–Z/a–z`, цифри, `_` і `-` (`^[A-Za-z0-9_-]+$`). Пробіли автоматично замінюються на нижнє підкреслювання. Кирилиця, інші алфавіти, emoji, порожні або інші некоректні значення **блокують генерацію всього Launch** до виправлення. Правило однакове для «Каталог» та «Інше». Creative alias і Buyer перевіряються як поля конфігурації завжди; соц/суфікс перевіряються при використанні у SUB, суфікс додатково підпорядковується числовому контракту РК (§5). Всі непорожні згенеровані SUB перевіряються після об'єднання, перед вставленням у URL.

Для creative початкове значення — filename без останнього розширення. Для Buyer/соца використовуються значення вибраних записів. Для всіх змінних після trim зовнішніх пробілів кожний внутрішній пробіл Unicode категорії Zs замінюється на `_`; послідовність із кількох пробілів дає відповідну кількість `_`, існуючі `_`/`-` не стискаються. Tab/newline/control chars не є пробілами для такої заміни й відхиляються. Нормалізоване значення відразу видиме в полі та прев'ю; та сама нормалізація/валідація виконується сервером до збереження наміру генерації й side effects.

```text
Файл:                  creative test 5.mp4
Назва для запуску:     creative_test_5
SUB:                   sub3=creative_test_5

Файл:                  Відео 5.mp4
Назва в полі:          Відео_5
Стан:                  генерацію заблоковано
Підказка:              «Вкажіть назву креативу латиницею. Дозволені цифри, _ та -»
Виправлено вручну:     video_5
SUB:                   sub3=video_5
```

Файл у просторі зберігає оригінальну назву, навіть кирилицею. Нормалізація соца для SUB не перейменовує існуючий соц і не змінює його назву в кампаніях: використовувати похідне нормалізоване значення, показане в SUB-прев'ю. Якщо соц містить недозволені символи, показати конкретну помилку з дією вибрати інший РК або виправити соц через наявні механізми акаунтів; не створювати другий alias соца. Buyer нормалізується видимо при inline-create; існуючий некоректний Buyer треба замінити або явно виправити, не змінювати довідник побічно. Автоматичної транслітерації, видалення недозволених символів, другого набору правил/slug або зміни alias лише всередині URL немає. Система не підставляє вигадану назву замість помилки. Порожній alias також блокує генерацію. Підказка Buyer/соца називає проблемне поле й правило «Латиниця, цифри, _ та -». До виправлення показуються доступні частини прев'ю та пояснення біля поля; каталог/restitch не запускаються.

URL Generator все одно використовує UTF-8 percent-encoding значень параметрів за §8.2 як загальну технічну гарантію. Валідний creative alias із дозволених символів не потребує закодованої кирилиці або пробілів у URL. Buyer і всі інші змінні SUB проходять те саме обмеження до encoding; кирилицю чи спецсимволи не дозволяти обходити через percent-encoding або вже закодований ввід (`%20` у змінній є недозволеним). Чужі параметри й макроси оригінального URL не підпорядковуються цьому правилу й зберігаються за §8.2. Порожній builder лишається preserve: незмінені оригінальні SUB не нормалізувати й не блокувати лише через їхнє наявне значення. Некоректний Unicode дає validation error, не crash; повний URL після encoding обмежений 8192 без обрізання. Відображення декодованих значень зовнішнім трекером лишається предметом перевірки його контракту.

Ручне редагування готового URL за §4.1 не запускає генерацію й не кодує весь рядок повторно. Воно є позначеною ручною правкою для копіювання, не зміною валідованої конфігурації; нова генерація завжди повторно перевіряє Buyer, creative alias, вибрані змінні та всі сформовані SUB за цим правилом. Для ручного редагування окремого SUB, якщо такий control показано у результаті, застосовувати той самий нормалізатор/валідатор; некоректне значення не позначати готовим до використання.

## 9. Назви кампаній і локальне прев'ю

```text
[<social>-<rkSuffix>-<creative><catalogSuffix>] <offer> $<budget> <genderLower><age>+<advMarker> <DD/MM> #<index>(<start>-<end>)
catalogSuffix = method == catalog ? "-c" : ""
advMarker = advantagePlus ? " adv+" : ""
```

Маркер Advantage+ — **запропоноване рішення**, потребує погодження. При off базові приклади відтворюються точно; при on: `[g1-892-v5-c] ProCaps TR $10 m45+ adv+ 13/10 #1(1-3)`. `all35+` є звичайним значенням неймінгу. Офер/alias не транслітеруються, не розбираються за `_`/дефісом, не перетворюються на V1.

Для прикладу N=3,max=30,ads=3,date=2026-10-13,Advantage+=off:

```text
[g1-892-v5-c] ProCaps TR $10 m45+ 13/10 #1(1-3)
[g1-892-v5-c] ProCaps TR $20 m45+ 13/10 #2(4-6)
[g1-892-v5-c] ProCaps TR $30 m45+ 13/10 #3(7-9)
```

Чистий `deriveLaunchPreview(config, resolvedSnapshots)` повертає budgets, ranges, campaignNames, subValues, validation і dependency signatures. Він не має доступу до network/storage/agent. Full URL можна обчислити локально, але не виводити постійно під формою. Якщо конфігурація неповна, показувати готові частини без удаваного фінального рядка з `undefined`.

Зберігати `namingTemplateVersion=1`, а не повний DSL. Шаблон — функція з версією, щоб майбутня зміна не переінакшила історичний результат. Збереження сервером повторює обчислення й перевіряє snapshots: браузер не може підмінити бюджет/ідентичність іншого простору. Для довжини назви не вигадувати підтверджений ліміт Meta: у v1 є власні ліміти вхідних текстів; зовнішню сумісність перевірити окремо.

## 10. Інтеграція каталогів і перезашивки

### 10.1. Повторне використання

Винести orchestration із `CreateProductCatalogDialog` у придатний для повторного виклику сервіс; діалог і Launch adapter мають користуватися одним pipeline. Рядки, XLSX, pools, sharing, upload/conversion, finalize залишаються наявними. `catalog-sync` — індексація матеріалів, не генератор товарних каталогів; не плутати ці сервіси.

Для кожної підтвердженої catalog-generating версії:

1. Перевірити матеріал, `view/edit/process/upload` відповідно до конкретних side effects, storage readiness, catalog settings/pools, тарифний доступ. Без restitch локальний агент для обчислення назв/URL не потрібен; restitch потребує підключення й capability.
2. Зафіксувати original/generated URL і конфігурацію до side effects. Підготувати ключі етапів.
3. Якщо restitch on: використати наявні space defaults, а за їх відсутності автоматично отримати фінальне зображення з останнього кадру вибраного відео без додаткового налаштування або збереження → `prepareRestitchScreens` або legacy `ensureRestitchImages` → `ensureRestitchedFolder` → `teamApi.startProcess` із `toolId='restitch'`, RESTITCH_CONTRACT_VERSION, keep_both → `startTeamAgentProcess` → підтверджений finalized material.
4. Записати restitch operationId/resultMaterialId у серверному стані Launch generation. Успішний результат повторно використовувати при retry каталогу, якщо input signature і material version не змінилися.
5. Викликати наявний createProductCatalog із `videoMaterialId` **оригінального** відео, `sourceLink=generatedAdvertisingUrl`, productCount, `restitchOperationId` якщо є, `replacesMaterialId=null` і стабільним idempotencyKey етапу. Це створює нову варіацію поруч, а не замінює стару.
6. Прив'язати catalog record/materialId, variant, фактичну name, sheetUrl, параметри/settings snapshot та operationId до версії Launch. Не робити ще одну варіацію на кожну кампанію: N кампаній ділять один каталог.
7. Атомарно завершити версію й указати active result. Якщо каталожний етап не завершено, стан partial: текстові результати доступні, але весь запуск не позначений «Готовий».

Фактична назва каталогу — `<physicalVideoStem>_v<variant>_catalog` з [tail.ts](../../apps/web/src/team/materials/tail.ts) / server productCatalogName. Alias креативу Launch впливає на SUB/неймінг, але не перейменовує material або каталог. Приклад `ProCaps_TR_v5_...` не є існуючим правилом і не вводиться окремо.

### 10.2. Точні одиниці restitch

Це тривалість фінального зображення в наявному restitch pipeline, не довільна «довжина рекламного ролика». `FinalImageDurationMode` з [types.ts](../../packages/shared/src/types.ts): 30–40, 40–50, 50–60 **хвилин**, custom через [parseMinutesInput](../../apps/web/src/components/ImageEmbeddingSection.tsx). UI приймає лише додатні цілі хвилини, множить на 60; існуюча верхня межа — `99*60*60 + 59*60 + 59` секунд (359999; найбільше допустиме ціле введення — 5999 хвилин). Інші restitch налаштування, початкові зображення/їхні мілісекунди, pools і fit modes наслідуються з наявних defaults, не дублюються новим набором полів. Відсутність defaults не блокує запуск: автоматичний режим бере фінальне зображення з вибраного відео та застосовує вибрану тривалість без окремого збереження налаштувань.

Перед запуском зберігати snapshot defaults та обраних ресурсів/версій; випадкову тривалість і вибір зображень не перебирати під час replay уже успішного етапу. Runtime має лишитися під PowerGovernor: [spawn.ts](../../apps/agent/src/power/spawn.ts), scaleTimeout, resumeForTermination. Новий FFmpeg runner не потрібен.

### 10.3. Посилання на каталог, доступ і updater

`sheetUrl` — це посилання Google Drive (`webViewLink`) на фактично створену таблицю каталогу. У Launch Result показувати назву каталогу й це посилання; кнопка копіювання копіює точний `sheetUrl`. Не потрібні окремі поля URL/формату каталогу чи окремий endpoint для визначення посилання: його джерело — результат наявного Google Drive generator.

`randomLinkVariation` залишити за чинним контрактом генератора (default true) і зафіксувати в snapshot; це варіації посилання на відео всередині таблиці каталогу, не додаткові рекламні URL. Наявний updater у [worker.ts](../../supabase/functions/catalog-updater/worker.ts) може змінювати каталог. Launch не вмикає його автоматично. Після публікації linked catalog підтримує явне ручне оновлення та обраний користувачем розклад через чинний updater. Оновлення змінює вміст того самого Google Sheet, зберігаючи його ID і URL; snapshots конфігурації, назв кампаній, SUB та початкових налаштувань каталогу в історії Launch лишаються незмінними. До завершення початкової генерації candidate не потрапляє в updater. Recreate/rename/trash та підміна файлу залишаються захищеними. Зовнішнє редагування Google Drive неможливо заборонити повністю: показувати missing/changed, зберігати snapshot і не вважати ресурс незмінним лише через наявність історії БД.

URL доступні тільки авторизованому detail-read за правами, не list/card/realtime/audit projection. Не класти original URL у localStorage/IndexedDB або workspaceOperationJournal. Draft автоматично зберігається у захищеному серверному сховищі після короткої паузи в редагуванні; до підтвердження сервера нові зміни лишаються в RAM. Не використовувати plaintext payload hashing у логах; request digest/signatures серверні, недоступні аналітиці. Потребу field-level encryption узгодити в security gate (§18), не стверджувати, що вона вже реалізована для Launch URL.

Видалення: Launch у v1 архівується через `delete` permission; історія зберігається. Архівація Launch ніколи не каскадує на Google Sheet/catalog record, перезашите відео чи інші Drive materials: вони залишаються у просторі та в історії каталогу. Архівація заблокована під час активної generation до cancel/settlement. Перед архівацією Launch із готовим каталогом у будь-якій збереженій revision показати попередження «Каталог і перезашите відео залишаться у просторі» (називати відео лише коли воно є). Прапорець «Не показувати знову» присутній і **за замовчуванням вимкнений**; зберігати його як персональну перевагу поточного учасника в межах простору, не глобально. Записувати preference тільки якщо користувач підтвердив архівацію з прапорцем увімкненим; натискання «Скасувати» її не змінює. Коли preference вже збережена, попередження можна пропустити для наступних видалень у цьому просторі цього користувача. API/DB archive не видаляє й не змінює Drive outputs навіть коли попередження приховане. Від'єднання креативу не видаляє файл із Drive. Archived offer/Buyer не пропонується новим запускам, але snapshot продовжує відображатися. Видалення/перенесення джерел не каскадує Launch revisions: nullable references або soft-deletion/guard із незмінними snapshots. Фізичне очищення історії та retention — окрема погоджена політика. Видалення простору й авторизаційна недоступність підпорядковуються чинним правилам Soty.

### 12.2. Майбутній API-контракт

Назви методів нижче запропоновані, не вже наявні endpoint.

- `listLaunches(teamId, cursor, filters)` — картки без URL/секретів, stable pagination; date filter `all` або включний date-only діапазон `from/to`, що застосовується до launchDate за §4 до пагінації.
- `getLaunch(teamId, launchId, revisionId?)` — detail + робоча конфігурація + поточна generation; access check на кожне читання.
- `saveLaunchDraft({teamId,launchId?,expectedVersion,requestKey,config})` — явна дія; повертає id/version, без каталогу.
- `generateLaunch({teamId,launchId,expectedVersion,baseRevisionId,requestKey})` — сервер читає draft, перевіряє джерела, фіксує revision і generation; повертає generationId/revisionId/state.
- `getLaunchGeneration`, `resumeLaunchGeneration`, `cancelLaunchGeneration` — reconcile/claim поточних етапів; resume не створює нової revision.
- `saveLaunchResultOverrides({teamId,launchId,baselineRevisionId,expectedVersion,requestKey,overrides})` — створює нову manual result revision за §4.1, без catalog/restitch або зміни конфігурації; повторний requestKey повертає той самий результат.
- `updateLaunchMetadata({expectedVersion,assigneeId?,workStatus?})` — без генерації.
- `copyLaunch({teamId,sourceLaunchId,sourceRevisionId?,expectedSourceVersion,requestKey})` — атомарно створює незалежну чернетку за §3.5, повертає новий launchId/version; без важких операцій. Replay повертає ту саму копію; stale source version дає conflict.
- `listLaunchRevisions`, `archiveLaunch` — історія/архів, без видалення Drive матеріалів. Для Launch із каталогом UI спершу показує попередження за §11; suppress preference оновлюється атомарно/в одній транзакції з успішним archive лише за явного checkbox consent.
- `list/create/archiveLaunchOffer`, аналогічно Buyer; create повертає існуючий запис при гонці normalized_key.
- `get/setLaunchDefaults({expectedRevision,config,subConfig})` — лише whitelist дефолтів, без URL/РК/material/date/results/assignee.

RPC фіксації generation атомарний: перевірка expectedVersion і requestKey → resolve sources → revision + N campaign rows + generation → commit. Для `other` можна в цій транзакції завершити текстовий результат. Для catalog файли виконуються після commit з checkpoint. Жодна транзакція БД не тримається відкритою під час FFmpeg/Drive.

Права v1: view — читання; edit — створити/редагувати/призначити/згенерувати текст; upload — завантажити файл; process — перезашивка; manage_metadata — довідники/defaults/catalog settings; delete — archive. Catalog generation додатково перевіряє реальні права на sharing/write у чинному pipeline. Якщо роль не має manage_metadata, inline-create прихований із поясненням, існуючі довідники доступні. Перевірка членства/простору/тарифу виконується також у service-role RPC перед side effects, а не лише в браузері.

Realtime надсилає лише invalidation/IDs/state; після reconnect робиться bounded refetch. Наявний useTeamRealtime не підписаний автоматично на нові таблиці — додати Launch invalidation seam. Дані попереднього team/actor не повинні застосуватися після перемикання простору або logout.

### 12.3. Прогрес генерації та скасування

Прогрес починається тільки після натискання «Згенерувати запуск». До цього діє лише локальне прев'ю (§9), без стану «виконується». Після прийняття запиту показується підтверджений стан/етап поточної generation, отриманий від сервера або дочірньої team operation; завершені кроки позначаються виконаними, активний крок — у роботі, наступні — очікують. Не оцінювати відсоток за таймером і не показувати крок завершеним на підставі відправленого запиту.

Для методу «Каталог» показувати лише застосовні етапи в реальному порядку: перевірка та збереження конфігурації; за ввімкненої перезашивки — підготовка ресурсів, передавання відео агенту, фактичний прогрес/стадії restitch із team operation, фіналізація готового відео; генерація рядків каталогу; завантаження й реєстрація каталогу; збереження результату. Якщо перезашивки немає — її етапів немає. Прогрес перезашивки показувати з реального чинного agent SSE та authoritative team operation snapshots через Realtime; нового recurring client polling не додавати. Поточний ProductCatalogProgress із таймерними оцінками не є джерелом «точного прогресу»; для генератора каталогів додати server-side підтверджені стадії або показувати останній підтверджений етап без вигаданих відсотків.

Для методу «Інше» немає restitch/catalog кроків: показати прийняття запиту → перевірку/збереження конфігурації → формування URL і кампаній → фіксацію результату → готово. Якщо етап настільки короткий, що проміжні стани не встигають відмалюватися, показати стан «Готуємо запуск…», а потім готовий результат; штучно затримувати відповідь лише заради анімації не потрібно.

Від моменту прийняття generation до її terminal state **усі параметри цієї конфігурації заблоковані**: поля, defaults, URL/SUB, assignee/status edits у тій самій поверхні й дії, що змінюють inputs. Read-only перегляд попередньої revision дозволений. Блокування є в UI й повторно забезпечується сервером через generation lock/version, а не лише disabled controls. Інші Launch у просторі лишаються доступними.

Показувати явну дію «Скасувати». Вона запитує cancel для parent generation і всіх активних дочірніх restitch/catalog operations через їхні чинні cancel APIs; UI лишається locked до підтвердженого terminal `canceled` або чесного `interrupted/reconciling`. Підтвердження cancel чекає межі, на якій сервер знає, чи дочірній результат уже створено. Після підтвердженого скасування не публікувати candidate revision як активний результат, не прив'язувати новий каталог, не переносити часткові назви/URL у готовий результат. Відкрити попередню успішну revision; якщо це перша генерація — залишити незмінну збережену конфігурацію/чернетку й показати стан до запуску. Розблокувати налаштування тільки після цього.

Якщо restitch/catalog уже створив проміжний Drive material, спершу скасувати/узгодити дочірню операцію, потім видалити тільки доведено належний цьому generation непублікований артефакт чинним trash/rollback шляхом. Не видаляти shared source, успішний попередній каталог або артефакт із невизначеним ownership. Якщо зовнішній side effect не вдалося безпечно відкотити, позначити generation `canceled_with_cleanup_pending` (новий parent enum; child team_operations enum не змінюється через це), продовжити idempotent cleanup у фоні та не показувати «як нічого не було» до завершення cleanup. Це обмеження чесно відображає, що Drive/локальний процес не підтримує спільну транзакцію з БД.

Sharing також є side effect: зберігати попередній стан і ID permission, доданого цією generation. Відкочувати лише доведено власний permission без інших consumers; коли це не можна довести, лишати cleanup_pending з явним поясненням, а не знімати спільний доступ.

Подвійний cancel/reload/retry мають бути idempotent. Cancel проти одночасного success розв'язується compare-and-swap: якщо сервер уже commit-нув результат до прийняття cancel, показати готовий результат; якщо cancel прийнято першим — fenced executor не може його опублікувати. Невизначений outcome не оголошується ні скасованим, ні успішним; спершу reconcile. Невдала generation лишає попередній результат доступним, а конфігурацію — для виправлення/повтору.

## 13. Ідемпотентність, тривалі операції й recovery

Розрізняти:

- **workStatus** — ручний todo/in_progress/done;
- **generation.state** — proposed `accepted/running/waiting_dependency/partial/succeeded/failed/cancel_requested/canceled/canceled_with_cleanup_pending/interrupted` (parent states; окремі від чинного child enum);
- **step state** — адаптація до чинних `team_operations` pending/running/succeeded/failed/canceled, без глобального перейменування їх enum;
- **availability** — чи доступний сьогодні збережений material або посилання на каталог. Ready revision може мати втрачений зовнішній ресурс.

Клієнт створює requestKey один раз на явне підтвердження й тримає його під час retry; сервер зберігає до IO. Той самий ключ + той самий payload digest → попередня generation/result; той самий ключ + інший payload → conflict. Різні ключі для одного Launch із тією самою expectedVersion не створюють дві активні generation: унікальність/lock і optimistic version check. Кнопка disabled — допоміжний UX, не гарантія.

Послідовність етапів: validate → snapshot_saved → text_derived → restitch_requested/running/finalized (optional) → catalog_requested/registered (optional) → result_committed → result_visible. Ключ етапу стабільний для generation/stage/attempt; transport retry використовує той самий ключ, нова спроба після доведеного terminal failure — новий attempt із посиланням на попередній.

**Потрібне розширення чинного catalog idempotency.** У перевіреному handler `nextVariant` викликається до `startOperation`, а replay шукає каталог за щойно обчисленим variant. Після першого успіху max variant уже змінився; наявність idempotencyKey сама по собі не доводить коректне повернення попереднього результату. Preview `max+1` також не є reservation при конкурентних запусках.

Перед реалізацією Launch adapter необхідно:

1. Атомарно резервувати variant за `(teamId,videoMaterialId,generationStepKey)` та повертати ту саму reservation при replay; serialize allocation/unique constraint. Пропуски номерів після failure допустимі, дублікати — ні.
2. Шукати завершений result за operationId/requestKey/resultMaterialId, не за новим max+1.
3. Зберігати зв'язок output ↔ step до того, як браузер отримав відповідь. Збій після Drive create, але до finalize/link, має reconcile за доведеним provider intent/ID. Наявний handler не дає доказу exactly-once при crash у цьому вікні: потрібна persisted intent/reservation і recovery через існуючий operation pipeline.
4. Поки outcome невідомий, не робити blind повторний create. Показати interrupted/reconciling і завершити пошук/cleanup; лише після доказу відсутності придатного результату retry створює наступний attempt.
5. Серверні claims/lease/fencing не дозволяють двом вкладкам вести один етап. Прострочений executor не комітить результат після takeover. Нову локальну перезашивку не стартувати лише тому, що стара вкладка втратила heartbeat: спочатку reconcile operation/agent status.

Reload/GET ніколи не означає нову варіацію; UI приєднується до відомого статусу. Продовження прийнятого незавершеного intent не є новою генерацією, але потреба в локальному агенті показується як waiting_dependency. Без агента не обіцяти server-side FFmpeg. Закриття вкладки не скасовує вже прийнятий серверний етап. Cancel — явна дія, propagation до чинної операції; налаштування locked до terminal/reconcile; late success вирішується compare-and-swap. Непубліковані outputs очищуються лише за доведеного ownership, див. §12.3.

Реальний progress брати з operation/agent, якщо підтриманий; інакше показувати назву останнього підтвердженого етапу та indeterminate indicator. Таймерний ProductCatalogProgress можна використовувати тільки як очікувану послідовність, не числовий доказ. Таймаути враховують throttling, offline/backoff і чергу.

## 14. Редагування, залежності та історія

Сигнатури будуються з канонічних versioned inputs. Порівняння має йти за **отриманими залежними значеннями**, а не просто фактом зміни поля; внутрішні signatures не передавати в аналітику.

| Вік, стать, Advantage+, дата, офер                | Назви                                          | Ні                                          | Ні                                                                 |
| N, maxBudget, overrides                           | Назви й бюджети; діапазони для N               | Ні                                          | Ні; productCount незалежний                                        |
| adsCount                                          | Назви й діапазони                              | Ні                                          | Ні                                                                 |
| Buyer                                             | Ні                                             | Якщо builder містить buyer і вихід змінився | Нова catalog variation лише якщо URL змінився; успішне відео reuse |
| РК/назва соца                                     | Назви                                          | Якщо відповідні SUB реально змінилися       | Лише при зміні URL                                                 |
| creative alias                                    | Назви                                          | Якщо SUB використовує creative              | Лише при зміні URL; фізичний файл не перезашивати                  |
| materialId або driveVersion                       | Alias за вибором користувача; назви за потреби | За фактичними SUB                           | Нові матеріали каталогу; restitch за новим source signature        |
| originalUrl / subConfig                           | Ні                                             | Перерахунок із original                     | Нова variation, якщо generated URL відрізняється                   |
| other → catalog                                   | Додається -c                                   | Ні                                          | Створити каталог після підтвердження                               |

| restitchEnabled/duration/resolved images/defaults | Ні                                             | Ні                                          | Restitch і нова variation; при off — каталог з оригінальним відео  |
| productCount/catalog settings snapshot            | Ні                                             | Ні                                          | Нова variation; restitch не повторювати, якщо його inputs ті самі  |
| assignee/workStatus                               | Ні                                             | Ні                                          | Лише metadata/audit, без result revision                           |

URL-signature: original bytes + SUB order/mapping + значення використаних змінних + URL generator version. Name-signature: усі фактичні input неймінгу + template version. Restitch-signature: original materialId/version + resolved restitch settings/pools/selections + contract version. Catalog-signature: generated URL, оригінал/підготовлене відео/version, productCount, settings/pool snapshot, randomLinkVariation, catalog template version. Невідома driveVersion означає revalidate source, а не необмежений cache hit.

Підтвердження оновлення показує, що старі посилання й каталоги залишаться у попередній версії. Для змін лише неймінгу створити новий текстовий snapshot і reuse catalog reference. При catalog update створити **нову** варіацію (`replaces=null`), не викликати destructive recreate існуючої: чинний recreate може прибрати попередній файл. До завершення нової версії activeRevision залишається попередньою успішною. Неуспішні candidate revisions видимі в історії спроб.

Зовнішня зміна джерела/довідника відображається як «джерело змінилося»; оновлення draft із поточних значень — явна дія. Безпосередньо перед snapshot-save сервер повторно перевіряє source versions; конфлікт просить переглянути прев'ю, а не генерує несподівану назву.

## 15. Defaults простору

Дії «Зберегти для офера» та «Зберегти як загальні» зберігають усі значення форми: баєра, кількості, бюджети й режим, мінімальний вік, стать, Advantage+, дату й timezone, originalUrl, SUB, параметри каталогу й примітки. Лише РК та креатив (materialId/alias) обираються окремо; офер є ключем профілю. Результати, overrides, assignee та службові стани не є параметрами цієї форми. Запис захищений manage_metadata, scope version та idempotency key. Age не має штучного початкового значення.

На створенні нового Launch — разова копія defaults, потім незалежний draft. Зміна defaults не модифікує вже відкриту форму або попередні Launch. Deleted/archived Buyer default дає порожнє поле з поясненням. Помилка читання defaults не вважається їх відсутністю: показати retry і не підмінити власні значення мовчки. Початкові приклади patrik/3/30/3/M/catalog/Advantage+=on/restitch=on — продуктова стартова пропозиція, а не вже існуючі налаштування кожного простору. restitch on без defaults не запускає випадкову конфігурацію, а показує посилання на чинні налаштування.

## 16. Помилки, безпека та діагностика

### 16.1. Обробка

| Ситуація                                                 | Результат і відновлення                                                                           |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Некоректні поля, дубльовані/нульові бюджети              | Відмова до side effects; локальні field errors, server повторює перевірку                         |
| РК без придатного числового ID/без доступного соца       | Blocking validation, повний ID показується для виправлення; не підставляти випадковий suffix      |
| Material missing/trashed/changed                         | Збережена історія читається; нова генерація заблокована до заміни/revalidation                    |
| Catalog settings/pools відсутні                          | Конкретний prerequisite і SpaceSettingsLink; не створювати порожню таблицю                        |
| Image-креатив + catalog                                  | Явно непідтриманий тип, запропонувати video або «Інше»                                            |
| Agent offline/old, відсутні screens                      | waiting_dependency/rejected із наявним нормалізованим кодом; не повторювати завершені етапи       |
| Drive quota/revoked OAuth/sharing denied                 | Код/stage/retryability; відновити storage/access, потім retry того самого intent                  |
| Network timeout після submit                             | Прочитати generation за requestKey; невідомий outcome не означає «не створено»                    |
| Restitch success, catalog failed                         | Partial із готовими текстами; retry тільки catalog із тим самим придатним restitch output         |
| Catalog success, відповідь або прив'язка Launch втрачена | Reconcile output за operationId, bind його; не створювати ще одну variation                       |
| Конкурентні edits/defaults/membership change             | Conflict/permission denied; зберегти локальний draft, не overwrite; session-scope reset           |
| Clipboard denied                                         | Помилка копіювання, повний текст доступний для ручного виділення                                  |
| Каталог змінився поза Soty                               | Availability warning і перевірка, snapshot не переписувати; claim про byte-immutability не робити |

Ужити існуючі codes там, де їхня семантика збігається. Нові кандидати (`LAUNCH_VERSION_CONFLICT`, `LAUNCH_URL_INVALID`, `LAUNCH_BUDGET_INVALID`, `LAUNCH_RESULT_UNCERTAIN`) до реалізації додати у закриті списки, Edge mappings, [types.ts](../../packages/shared/src/types.ts) і [code-map.ts](../../scripts/analytics/code-map.ts). Не додавати довільні exception.message у payload.

### 16.2. Аналітика як критерій готовності

Виконувати [031-platform-autoanalytics/spec.md](../031-platform-autoanalytics/spec.md). Використати [analytics/events.ts](../../apps/web/src/analytics/events.ts), [service.ts](../../apps/web/src/analytics/service.ts), [guard-contract.ts](../../apps/web/src/analytics/guard-contract.ts), [team/analytics.ts](../../packages/shared/src/team/analytics.ts), чинний journal forwarding і read-only CLI.

До початку реалізації визначити typed lifecycle для наміру створення/редагування, file selection/upload, генерації, retry, cancel, перегляду результату, ручного редагування/збереження/відновлення згенерованих полів, копіювання значень, копіювання Launch у нову чернетку, defaults save. Для копіювання Launch окремо довести прийняття наміру, створення нової чернетки та її видимість, без конфігурації/URL у payload. Кореляція: flowId → launchId/revisionId (непрямі ресурсні IDs за поточним контрактом) → generation/run → attempt → parent/child team operation/restitch/catalog. Початковий input failure також має flow, навіть без збереженого Launch.

Очікувані докази: intent received, validation rejected/accepted, request sent/accepted, snapshot committed, dependency waiting, source downloaded, restitch finalized, catalog registered, result committed, result rendered, copy succeeded/failed. Рендер доводить видимість у Soty, clipboard success — запис clipboard. Жоден із них не доводить вставлення в Ads Manager або реальний запуск реклами; ця межа принципово неспостережувана без Meta integration.

Поля діагностики тільки allowlist: stage, outcome, stable code, retryable, coarse counts/durations, method, capability/build/platform, operation IDs, timestamps. **Заборонено:** original/generated URL або їхній query, токени, SUB values, назви офера/Buyer/соца/креативу/кампаній, filenames/raw paths/provider payloads, clipboard text. Для ручних правок збирати лише факт дії/тип поля/ознаку override; значення та diff не надсилати. Audit зберігає тип змінених полів і IDs, не секретні diff значення. Realtime/list/index/search/log middleware також не повинні ненавмисно отримати URL.

Розширити [coverage-registry.ts](../../scripts/analytics/coverage-registry.ts), [code-map.ts](../../scripts/analytics/code-map.ts), [investigate.ts](../../scripts/analytics/investigate.ts), [queries.ts](../../scripts/analytics/queries.ts): `inspect <flow|run|attempt>` / `investigate <email|id>` повинні пояснювати останній доведений етап Launch і зв'язок із restitch/catalog; `audit` — відсутні terminal/visible events, delayed delivery, orphan child operations, unknown codes. Не писати новий dashboard або ad-hoc SQL замість CLI. Перевірити весь шлях producer → guard → storage → CLI; emitted event сам по собі не є покриттям.

Тестувати втрату terminal event при authoritative success, delayed/out-of-order/duplicate події, вимкнену аналітику, старий agent producer та втрату client visibility. CLI має показувати unknown/insufficient/unsupported_by_producer, не нуль успішних проблем. Background wait/backoff/throttle не класифікувати як зависання лише за фіксованим коротким таймаутом.

## 20. Уточнення за результатами аналізу задач

Ці правила доповнюють §3, §12–14 і §16 та обов’язкові для реалізації:

1. **Recovery без браузера.** Launch due recovery/cleanup самостійно пробуджує hosted worker через SQL dispatcher і endpoint wiring; scheduled catalog jobs не є передумовою. Bounded claims/backoff/fencing й доступність scheduler перевіряються окремо. Failed stage повторюється лише після explicit resume; автоматичне reconcile прийнятого intent не створює нової generation.
2. **Source expectation.** Разом із draft зберігається expectedSourceSnapshot із джерел, використаних у preview. Generate порівнює його із server-resolved sources до side effects; rename/version/link mismatch повертає SOURCE_CHANGED навіть без зміни Launch version. UI явно оновлює sources і preview до повторного підтвердження. Replay прийнятого intent не перераховує snapshot із нових live values.
3. **Copy timezone.** copyLaunch отримує поточний IANA timezone браузера. Сервер обчислює tomorrow календарно при першому успішному commit; replay після півночі повертає первісну дату й ID. Пояс історичного Launch не використовується як поточний.
4. **Browser persistence.** Незбережені конфігурації й ручні outputs — RAM-only; заборона поширюється на localStorage/sessionStorage/IndexedDB/Cache API/operation journal та service-worker cache protected detail. Reload відновлює підтверджену сервером чернетку за її ID; до підтвердження останніх змін вихід попереджає про втрату. Logout/scope switch очищає RAM.
5. **Розходження результатів.** Після ручної правки URL каталог показує «Змінено для копіювання; каталог не оновлено». Залежні name/budget/range/SUB поля мають відповідну підказку; save/reopen зберігає її семантику, reset відповідного override прибирає. Жодних side effects від підказки.
6. **Restore.** «Відновити конфігурацію» бере config historical revision у робочу копію Settings, включно зі старою датою та config budgets, без result overrides й outputs. Dirty input потребує явного save/discard/cancel. Sources revalidate; save draft не перемикає active result. Після explicit Generate створюється нова revision звичайним pipeline. Metadata assignee/workStatus не відновлюються зі старої revision. Права edit/lock/conflict чинні.

### Уточнення повзунка тривалості (2026-10-16)

- Точний час: одна кругла ручка без заливки зліва. Кнопка називає наступну дію — «Випадковий діапазон».
- Діапазон: незалежні цілі хвилини 1–60; перетягування середини зберігає ширину, біля межі зупиняється весь діапазон. Перетягування ручки змінює тільки відповідну межу.
- Перехід до діапазону розводить ручки на ±5 хв від точного часу з обрізанням біля 1/60; зворотний перехід зводить їх до середини. Reduced motion вимикає анімацію.
- Рухи оновлюють лише локальний компонент; редактор і збереження отримують підсумок жесту. Клавіатура: стрілки, PageUp/Down, Home/End.
- Обидві межі зберігаються у finalDurationRangeSeconds та враховуються при визначенні змін медіа. Сервер один раз вибирає тривалість у цих межах у durable preparation, повтор використовує той самий вибір.
- Діагностика: чинний lifecycle запуску (intent → accepted → restitch preparation/processing → terminal → visible); помилкові межі відхиляються як INVALID_INPUT. Незбережені рухи курсора навмисно не збираються. Доказ результату — збережена ревізія та preparation, а не pointer telemetry. Регресії перевіряють drag/resize, крайні значення, round trip меж та invalidation медіа.

- Перемикач режиму стоїть над шкалою; коли плашка хвилин наближається, кнопка ковзає в протилежний кут через transform за --motion-fast. Позиція враховує реальну ширину тексту та контейнера; у середині діапазону не перемикається без зіткнення. Reduced motion прибирає перехід.

### Межі автоматичного бюджету (2026-10-16)

- Заголовок бюджетної групи: «Встановіть бюджет кампанії» для N=1, «Встановіть бюджет кампаній» для N>1. В автоматичному режимі є два поля: «Мінімальний», потім «Максимальний».
- Нові запуски мають minBudget=10, maxBudget=30. Для N>1 бюджет i дорівнює round(minBudget + i*(maxBudget-minBudget)/(N-1)), i=0…N-1. Для однієї кампанії використовується максимум. Показані суми й генерація використовують ту саму чисту функцію.
- Позитивні цілі значення до 999999; min≤max; чинна вимога строго зростаючих бюджетів лишається. Якщо цілих значень у межах недостатньо для N кампаній, генерація блокується LAUNCH_BUDGET_INVALID. Зміна будь-якого поля одразу оновлює прев’ю.
- Старі конфігурації без minBudget зберігають попередній розподіл max*i/N. Draft/defaults/revision зберігають minBudget за його наявності. Збережений результат історичного запуску не перераховується.
- Діагностика використовує чинний lifecycle team.launches та закритий код LAUNCH_BUDGET_INVALID; невідправлені зміни полів не збираються. Регресії перевіряють preview→server parity, bounds validation, одиночну кампанію, legacy і round trip збереження.

### Вибір дати запуску (2026-10-16)

Праворуч у рядку аудиторії дата показується текстом «Дата запуску: DD.MM.YY». Під нею — «Сьогодні», «Завтра» та іконка календаря. Скорочення обчислюються в timezone запуску на момент кліку, календарна арифметика враховує DST та перехід місяця/року. Календар використовує спільний компонент і стек popover, після вибору закривається; заблокований редактор не допускає змін. Вибір одразу змінює конфігурацію й прев’ю, зберігається як чинний ISO YYYY-MM-DD. Діагностичний lifecycle запуску та INVALID_INPUT для невалідної дати незмінні; незбережені натискання окремо не збираються. Регресії перевіряють timezone, DST, Today/Tomorrow, вибір у календарі та disabled.

### Сумісність назв SUB (2026-10-16)

Літеральні query keys sub1/sub_1, sub2/sub_2, sub3/sub_3 означають відповідні спільні SUB-слоти. Попередження про відсутні слоти й фінальна підстановка використовують одну відповідність; якщо присутні обидві форми або дублікати, оновлюються всі відповідники. Написання ключів, порядок, невибрані слоти, сторонні параметри, рекламні макроси й fragment зберігаються byte-for-byte; відсутні ключі не додаються. Регістр та percent-encoded keys не нормалізуються. Параметри всередині fragment не вважаються query. Перевірки використовують тільки синтетичні URL; реальні токени/адреси не додаються до тестів або діагностики. Чинні коди LAUNCH_URL_INVALID/LAUNCH_SUB_INVALID і lifecycle запуску лишаються, незбережені URL не збираються.

### Автозбереження параметрів (2026-10-16)

Після першого редагування новий редактор створює захищену серверну чернетку та підмінює new її ID без перезапуску сесії. Після 500 мс без редагування зберігається найновіший snapshot конфігурації та джерел. Поля лишаються доступними під час запиту; наступний snapshot записується після підтвердження попередньої версії. Відповідь на старий snapshot не замінює новіший ввід, навіть коли вперше з’являється ID.

Використовується чинний save_launch_draft з ACL, expectedVersion та requestKey. Невідомий результат/тимчасова помилка повторює ідентичний intent з bounded backoff; конфлікт версій зупиняє автозапис і показує помилку. Після втрати доступу/зміни scope пізні відповіді не застосовуються. Запуски, архівація та інші мутації не змагаються з автозаписом; до підтвердження browser unload лишає чинне попередження. Ручні result overrides зберігаються чинною окремою дією/working-copy transaction; їхні незбережені правки блокують автозапис конфігурації, щоб не розвести базові версії.

Показуються стани «Збереження…», «Є незбережені зміни», «Чернетку збережено». Повний URL/aliases не записуються у browser storage/cache/journal. Reload читає захищений detail, а не локальний кеш. Діагностика: save_draft з flow_id=requestKey та workflow_id за наявності, success лише після підтвердження запису, closed failure codes і недоставлена browser telemetry залишаються невідомими. Джерело істини — збережена серверна версія, а не індикатор. Регресії: debounce, нові правки під час запиту, перший ID, retry з тим самим ключем, конфлікт, unmount/scope, browser storage privacy та refresh у beta.

### Dictionary management

Offer and buyer selectors expose a manage action to members with `manage_metadata`.
The nested shared dialog searches active entries, renames with the same normalization
as creation, and soft-deletes entries. A selected entry requires a replacement in
the current draft before deletion. Generated revision snapshots are never rewritten.
Undo restores the same ID; duplicate normalized names are rejected. Writes compare

### Уточнення: швидке створення та відновлення перезашивки (2026-10-16)

### 2026-10-17 — Видиме очікування перед генерацією

Коли генерацію тимчасово блокує автозбереження, перевірка джерел, завантаження креативу або збереження вибору, кнопка показує спінер, а поряд є живий підпис фактичної причини. Відкладена відповідь автозбереження має зберігати індикатор та блокування генерації, дозволяти подальше введення, а після підтвердження останніх змін — прибирати індикатор. Діагностика використовує наявні кореляції `save_draft` та підтверджені версії; спінер не є доказом збереження, вміст URL не збирається.

### 2026-10-17 — Стабільний прогрес генерації

Звичайна інвалідація кешу каталогу не є втратою Realtime-з'єднання й не перемикає комірки запуску в попередження. Відсутність нового підтвердження залишає останню відому заливку; реальна помилка відображається одразу. Старі версії generation не замінюють нові, виміряна заливка в межах спроби не відкочується через пропущений або старіший зразок, нова спроба починає власний облік. Стани не оцінюються таймером. Комірки невідомої тривалості мають спокійний фон без пульсації та без удаваних 100%. Модальне вікно зберігає розмір, має внутрішній скрол і стабільне місце для статусу та дій; справжні помилки не обрізаються. Перевірки: повторні інвалідації кешу, справжній розрив зв'язку, збій, запізнілий snapshot, скидання між спробами. Діагностика й кореляції лишаються на чинних generation та operation receipts; колір і розмір UI не є доказом завершення роботи.

### 2026-10-17 — Повторна генерація після зміни вхідних даних

Зміна режиму, центру або будь-якої межі активного діапазону тривалості забороняє повторне використання старого відео та каталогу. Обидві серверні перевірки використовують однакову проєкцію активних полів, узгоджену з browser/Edge impact; неактивні поля часу не спричиняють зайвої обробки. Нова генерація фіксує новий process key і нову тривалість у межах вибраного діапазону; повтор запиту повертає ту саму підготовку.

Дозвіл повторного використання перевіряє походження відео: його фактичну операцію й ревізію, яка підготувала її вхідні дані. Позначки останньої ревізії недостатньо — історичний результат, помилково використаний зі старою тривалістю, має бути перероблений при наступній генерації навіть без додаткової зміни форми. Історичні результати залишаються незмінними.

Приймальна матриця охоплює креатив, байти й ідентичність файлу, зображення та defaults перезашивки, час, URL, кількість товарів, ціну, картинку й текст каталогу, назви та бюджети. URL і параметри каталогу оновлюють каталог зі збереженням придатного відео; зміни назв і бюджетів використовують чинні медіа. Retry прийнятої операції зберігає її зафіксовані дані, а нові зміни вимагають нової генерації; конфлікт не можна тихо проігнорувати.

Діагностична проєкція та read-only CLI повертають `reuse_evidence`: opaque ID операції відео, generation, яка його обробила, та попередньої ревізії використаного каталогу. Це доказ походження збереженого результату, а не доказ його перегляду користувачем. Для старої схеми, пошкодженого доказу або втраченої підготовки причина відсутності обробки залишається невідомою. Немає збору конфігурації, URL, назв чи вмісту медіа. Регресії перевіряють весь шлях від SQL receipts до CLI, стару схему, некоректні значення та збереження приватності.

Перевірка можливості повторного використання залишається на етапі підготовки. Відмова від старого каталогу не створює запису про його реєстрацію й не переводить прогрес уперед перед поверненням до створення нового каталогу. Executor/lease fence перевіряється до перевірки придатності результату.

### 2026-10-17 — Стабільний статус редагування

Редагування має один постійний рядок статусу під панеллю вкладок: очікування автозбереження й активний запис використовують однакове коротке повідомлення; підтверджений запис показує «Чернетку збережено» або «Зміни збережено». Статус залишається видимим при прокрутці. Помилки й конфлікти не оголошуються успішним збереженням. Перевірка джерел і завантаження креативу використовують цей самий рядок; кнопка генерації зберігає підпис і має доступний зв'язок зі статусом причини блокування.

Пояснення копіювання знаходиться біля відповідної дії у підказці. Поки зміни не підтверджені, копіювання недоступне; повтор уже прийнятого запиту копіювання зберігає власну ідентичність. Звичайне редагування не додає абзаців над формою або рядків до панелі дій. Підказка SUB-параметрів займає зарезервовану висоту найдовшого локалізованого повідомлення для поточної ширини. Валідаційні помилки лишаються доступними.

Acceptance: одна DOM-комірка статусу до редагування, під час debounce, запису та після підтвердження; незмінна кількість елементів над формою й у панелі дій; введення не блокується; копіювання розблоковується після підтвердження останньої зміни; відсутність/наявність SUB-параметрів не змінює місце підказки. Аналітика використовує чинні `save_draft`, `save_overrides`, `copy` та version-conflict receipts. Вигляд статусу не є окремим сигналом збереження; незбережені зміни в пам'яті й час читання повідомлення залишаються неспостережуваними.

### 2026-10-17 — Компактне підтвердження оновлення

Підтвердження має короткий заголовок «Оновити запуск?», список лише зачеплених результатів з іконками та одну виділену дію «Оновити запуск». «До редагування» повертає без генерації. Історія пояснена однією другорядною приміткою; попередження про незбережені ручні правки показується лише за їх наявності. Якщо змінюється тільки відео, повідомлення про незмінні результати не показується. Блок переносить вміст за доступною шириною без анімації розмірів.

Acceptance: правильний список наслідків, повернення без запиту генерації, блокування повторного підтвердження та збереження ручних правок при невдалому запуску перевірені UI-регресіями. Чинні generate/cancel lifecycle та кореляції залишаються джерелом діагностики; перегляд підтвердження не є доказом початку або завершення обробки. Нові дані користувача не збираються.

### 2026-10-25 — Оновлення робочого каталогу із запуску

### Явний стан помилки генерації

Повтор генерації/непідтвердженого запиту розташований усередині прогресу одразу праворуч від скасування, з чинними умовами доступності та тими самими request keys. Помилка має червону рамку, іконку й Alert над статичними етапами. Підтверджений failed/partial/interrupted або failed child показує «Генерацію зупинено»; помилка відповіді без terminal receipt — «Помилка — перевірте стан», із явним попередженням, що операція може виконуватися. Втрата зв'язку/тиша без помилки — warning «Статус не підтверджено». Останній підтверджений етап вторинний, помилковий етап червоний, індикатор активної роботи відсутній до нових підтверджень.

Діагностика й мутації використовують наявні launch correlation/stage/error codes та read-only reconciliation. Візуальне оформлення не змінює authoritative state і не створює фальшивого terminal event. Acceptance: unconfirmed reply ніколи не названа зупинкою; confirmed failure очевидний без читання повного пояснення; retry відтворює той самий намір; reconnect повертає активний стан лише за чинних receipts.

Каталог із перезашивкою та `catalogName` у SUB звіряє `sourceLink` із захищеним `launchSubBinding` поточного child intent і точним `namePlan`, а не з початковим URL ревізії. До реєстрації child ревізія залишається незмінною; attach переводить binding у published snapshot лише за існуючим publication fence. Missing binding і початковий URL після binding відхиляються. Регресія `launch-state` проходить реальний SQL від restitch receipt до link/register/attach/publish та перевіряє read-only `getLaunchEvidence`: committed SUB, успіх і відсутність URL у діагностиці.

### Повне відновлення профілю й явне застосування (2026-10-25)

Після вибору офера з відмінним збереженим профілем показати внутрішнє підтвердження «Застосувати збережені налаштування?» з «Так, застосувати» / «Ні». Профіль офера має пріоритет над загальним. «Ні» залишає поточні дані; «Так» відновлює всі параметри, включно з мінімальним віком, датою, URL та примітками, залишаючи поточний РК і креатив. Автозбережений ID нової чернетки не змінює поведінку. Відкриття існуючого запуску чи realtime refresh не підміняє його форму. Відповіді попереднього офера не можуть застосуватися до нового. Порожні опційні поля очищають попередні значення. Старий профіль не відновлює даних, яких ніколи не містив; його можна перезберегти.

Вибір закриває список оферів до показу підтвердження. Повернення фокуса після «Так» або «Ні» не відкриває список; явний клік, введення й клавіатурна навігація доступні. Приймання: round-trip повної форми через обидва RPC scopes, нова чернетка після autosave, мінімальний вік 52, No без apply/save, obsolete reads, nested focus restoration та незмінні РК/креатив.

Діагностика: чинні launch_defaults_read/save/apply з flow/attempt/scope; apply success лише після React commit відповідної форми, save після підтвердження та feedback. No і сам фокус не створюють apply; без terminal доставка unknown. URL, примітки, вік та інші значення не входять у telemetry, invalidation або browser storage. Захищений профіль і version receipt — fallback для втраченого save reply; tests/analytics-launch-defaults.test.ts перевіряє producer → sanitizer → persistence → CLI. Beta має вимкнену доставку analytics, тому live UI та автоматизована діагностика є окремими доказами.

Міграція 453 розширює лише наявні профілі та валідацію. Rollback UI не видаляє збережені нові поля; перед відновленням старої SQL-валідації залишити їх захищеними, не обрізати конфігурацію і не дозволяти старому клієнту мовчки перезаписати повний профіль.
