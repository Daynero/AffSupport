# Checklist: гроші та оплачений доступ після запуску тарифів

**Purpose**: зібрати рішення, без яких можна випадково дати неоплачений доступ або забрати оплачений.
**Created**: 2026-11-01
**Feature**: [034 — тарифи простору](../spec.md)
**Audience**: власник продукту та розробник перед комерційним запуском.
**Depth**: поглиблений розбір переходу, грошей, прав, місць, відновлення та релізу.
**Basis**: читання поточного робочого дерева на базі `b0d42f54`, включно з пізнішими міграціями.

**Актуально після доручення власника:** продуктових питань до нього немає. Рутинні рішення
прийняті в розділі «Комерційний запуск: рішення без додаткового опитування» у
[специфікації](../spec.md). Реалізація й перевірка захистів — робота розробника, T045–T051.

Складено за `speckit-checklist`. Нижче збережено 48 внутрішніх пунктів аудиту для трасування.
Позначка `[x]` означає, що правило визначене в специфікації, **не** що захист уже реалізований,
пройшов тест або потрапив у production. Це не анкета власнику. Відтворені прогалини нижче
залишаються чинними до окремого доказу виправлення.

Production-стан тарифів, оплат і членства тут не перевірявся. Відомий `free` у профілі користувача
не визначає тариф його простору. Зокрема, роль і підстава доступу Санчоса ще не встановлені.
Production-операції та релізні перевірки не виконувалися. Локально реалізовано редагований
бонус першого періоду; це не виправляє перелічені нижче прогалини доступу.

## Повнота переходу на платний доступ

- [x] CHK001 **P0 — Коли закінчується безкоштовний перехід?** Чи визначені дата вимкнення старого правила, перелік просторів, які ним користуються, та заборона поширювати виняток на нові простори після початку продажів? Чи задокументовано, що запрошення адміна Soty за чинною логікою відкриває простір без оплати? [Completeness, Spec US2 / FR-002 / FR-012, Gap]
- [x] CHK002 **P0 — Хто має право на постійний безкоштовний простір?** Чи визначено, що внутрішній простір адміністратора призначений для внутрішньої роботи, хто може переводити клієнта в такий простір, і як обліковуються подаровані доступи? Чи розділені адмін Soty та звичайна роль «адмін простору», щоб остання не давала тарифних пільг? [Clarity, Spec FR-002 / FR-004, Gap]
- [x] CHK003 **P0 — Що саме отримає кожна наявна команда?** Чи передбачено перед переходом перелік «простір → реальний власник → учасники/запрошення → підстава доступу → оплачений строк і місця → рішення після переходу», включно із Санчосом? Чи визначено, що особистий `free` і відсутність запису про платіж не доводять відсутності оплати за команду? [Completeness, Spec US2 / FR-001, Gap]
- [x] CHK004 **P0 — Чи можна закрити боржника, поки старе правило ще працює?** Чи узгоджені «Закрити простір зараз» та пріоритет legacy/internal, хто отримує попередження перед вимкненням правила й що відбудеться, якщо адміна-учасника видалять або глобальне правило випадково ввімкнуть знову? [Consistency, Spec US2.2 / US3.3 / FR-015, Conflict]

### Google: яка саме квота витрачається

За [офіційною документацією Google](https://support.google.com/cloud/answer/15549945?hl=en):
у режимі **Testing** дозволені до 100 test users; доданий до проєкту test user займає квоту.
Для неперевірених sensitive/restricted scopes існує також **OAuth user cap** за весь час життя
проєкту, який не можна скинути. Це різні правила; вважати видалення локального credential
або передачу простору поверненням Google-місця не можна.

Той самий документ зазначає строк згоди/refresh token у Testing — 7 днів, крім identity-only
scopes. Отже, повторне підтвердження **того самого** схваленого Google-акаунта потрібне й
не повинно продаватися як нове підключення. Простий вхід у Soty нині запитує лише
`openid email profile`; він відокремлений від згоди на Drive.

Передача ролі або запрошення учня самі по собі не додають test user у Google Cloud.
Якщо проєкт справді в Testing, акаунт поза Google allowlist не отримає Drive-згоду.
Якщо це Published/External/Unverified, такого allowlist-захисту немає — див.
[Google OAuth app states](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview).
Відмова Soty на callback не гарантує збереження квоти: згоду в Google користувач уже міг надати.
`login_hint`, текст у UI або прихована кнопка не є захистом Google-квоти.
