# Проблеми для розбору після релізу

Дата початку: 2026-11-05. Цей документ — окремий перелік робіт після поточного
релізу. Він не змінює його склад і не авторизує production-зміни.
Усі виправлення нижче відкриті. Аналіз коду й baseline-тести виконано в розділі 6;
реалізацію та приймання виправлень ще не проводили.

## План реалізації всього переліку

Детальний [план реалізації](CATALOG_IMPLEMENTATION_PLAN.md) визначає спільні

[Чекліст із 60 задач](CATALOG_IMPLEMENTATION_TASKS.md) — основне місце обліку
виконання, залежностей і доказів. Цей документ зберігає інциденти, аудит та

## 1. Копіювання посилання на вже створений каталог

Повідомлення Руслана близько 13:18 за Києвом: посилання на вже створений каталог
не копіюється; на скриншоті «Сервер відповів несподівано. Спробуйте ще раз».
Також повідомив про погану роботу інших вкладок. Посилання він уже копіював
вручну — пропозиція ручного копіювання не була новим вирішенням проблеми.

Підтверджено read-only CLI для облікового запису Руслана Кужельнова:

- 12:52:53 каталог зареєстровано; це не доказ працездатності подальшого копіювання.
- 13:17:59 і 13:18:25 список із шести каталогів відобразився, тривалість
  відповідних операцій 127 і 163 мс.
- 13:18:33–39 оновлення профілю успішні, 102–104 мс.
- У перевіреній діагностиці за день немає втрат зв’язку з агентом.

Ці факти не доводять відсутність часткового або короткого збою; повне падіння
сервера не встановлене. Причина невдалого копіювання невідома. Не встановлено,
яка саме кнопка/поверхня показала повідомлення зі скриншота.

Прогалини коду:

- `apps/web/src/team/product-catalog/ProductCatalogMenuDialog.tsx`: запис у
  clipboard, помилка показується toast, окремого діагностичного lifecycle немає.
- `apps/web/src/team/library/CopyDriveLinkButton.tsx`: API отримання посилання/
  доступу та clipboard заховані за спільним catch; точна причина втрачається.
- `apps/web/src/api/team.ts`, `throwRpc`: нерозпізнана RPC-помилка переходить
  у `INVALID_RESPONSE`; той самий код застосовується при відмові перевірки payload.
  Текст повідомлення сам по собі не встановлює джерело збою.

Роботи:

- [ ] Знайти всі поверхні копіювання каталогу, відтворити фактичний шлях Руслана.
- [ ] Покрити натискання, отримання URL, перевірку/надання доступу, clipboard,
      успіх, відмову, переривання та повторну спробу корельованими сигналами.
- [ ] Розділити безпечними закритими кодами transport/API, невідому серверну
      помилку, неправильний payload та відмову clipboard. Не збирати URL, контент,
      credentials або сирі provider payloads.
- [ ] При наявному URL та відмові clipboard показувати доступне поле для ручного
      копіювання. Не заявляти успіх до виконання clipboard promise.
- [ ] Простежити аналогічну втрату причин у суміжних вкладках/спільному API seam;
      не приписувати всі скарги одній причині без доказів.
- [ ] Перевірити шлях producer → ingestion → CLI diagnosis, включно з відсутніми
      та затриманими сигналами; додати змістовні регресії й capability inventory.

Критерій: `investigate`/`inspect` пояснюють, яка дія і на якому етапі зупинилася;
невідома причина залишається явною. Окремо перевірено практичний fallback.
Додавання аналітики саме по собі не вважається виправленням першопричини.

## 3. Випадковий вибір та повтор проблемної картинки

Перевірена реалізація updater:

- `private.draw_restitch_screens_for` у
  `supabase/migrations/20261029100000_restitch_sources.sql`: випадково по одній
  картинці на ввімкнений слот start/end (`order by random() limit 1`).
- `supabase/functions/drive-ops/updater-restitch.ts`: новий claim викликає draw;
  виключення починаються з порожнього списку. Одна повторна вибірка з виключенням
  можлива при відмові видачі grant, але не після локального download failure.
- Агент обробляє переданий набір; невдала передача завершує цю спробу, іншу
  картинку автоматично не підбирає.

Отже, нова вибірка не гарантує інший файл; пул з одного файла завжди поверне його.
Пам’яті невдалих завантажень між такими спробами немає. Це можливий сценарій
Руслана, а не підтвердження, що він двічі отримав один файл. Поведінку інших
шляхів (Launch, recovery/replay) потрібно перевірити окремо: не узагальнювати
правило нового updater claim на будь-яку кнопку «Повторити».

Роботи:

- [ ] Простежити фактичний шлях обох operation Руслана та семантику повтору.
- [ ] Забезпечити діагностичне порівняння вибраних opaque IDs між спробами.
- [ ] Визначити політику bounded повторного вибору для доведено недоступного
      файла; не виключати файли масово через спільний мережевий/authorization збій.
- [ ] Перед будь-яким replay звіряти authoritative terminal та execution fence;
      не запускати невизначену операцію повторно.
- [ ] Покрити пул з одного файла, кілька файлів, повтор того самого вибору,
      недоступний файл, спільний збій передачі та вичерпання fallback.

### Узгоджена поведінка відновлення (вимога власника)

Натискання «Перезашити» має доводити поточну спробу до результату, автоматично
усуваючи проблему окремої картинки заміною на іншу придатну. Користувач не має
повторно натискати кнопку, щоб випадково отримати робочий файл. Заборонено
зациклюватися на останній або вже відхиленій картинці.

- [ ] У межах поточної спроби вести набір відхилених кандидатів окремо для
      відповідних слотів; не обирати їх повторно, включно з останнім кандидатом.
- [ ] Якщо картинка недоступна, пошкоджена, не підтримується або не проходить
      перевірку, автоматично взяти іншу з дозволеного пулу й продовжити цю спробу.
      Перевіряти картинки до запуску основної обробки; не повторювати вже прийняту
      обробку відео заради заміни джерела.
- [ ] Перебір має бути скінченним, з явним лімітом і без прихованого нескінченного
      циклу. Вичерпання ліміту перевірки не називати доказом, що весь пул пошкоджений.
- [ ] Для тимчасового збою передачі дозволити обмежене відновлення. Спільний
      збій мережі, авторизації або диска відрізняти від дефекту окремого файла:
      заміна картинки не повинна маскувати таку причину або запускати масовий перебір.
- [ ] Якщо немає жодної придатної картинки, завершити спробу зрозумілою помилкою:
      що саме не вдалося, для якої позиції та що користувач може зробити далі
      (додати/замінити картинки в налаштуваннях перезашивки). Не показувати загальне
      «сервер відповів несподівано» замість відомої причини.
- [ ] Розрізняти порожній пул, усі перевірені картинки недоступні/непридатні,
      немає прав, збій з’єднання та неможливість запису на диск. При невідомій
      причині прямо повідомляти про невдале отримання, не стверджувати пошкодження.
- [ ] Нове натискання після невдачі не має сліпо відтворювати старий вибір.
      Визначити обмежений строк/область пам’яті відмов; зміна версії джерела або
      налаштувань має дозволяти перевірку виправленого файла. Не робити постійного
      blacklist на основі тимчасової помилки.
- [ ] Показувати короткий стан відновлення під час заміни. Аналітика має
      пояснювати кількість перевірених/відхилених/замінених кандидатів, причини,
      остаточний результат і його доставку без збору контенту та URL.

Приймання: один проблемний файл серед робочих автоматично обходиться в межах
одного натискання; останній проблемний кандидат не повторюється нескінченно;
пул лише з непридатних файлів дає конкретне повідомлення й наступний крок;
спільний збій зупиняється з відповідною причиною; cancel та execution fences
залишаються дієвими. Усі сценарії перевірити наскрізно до CLI diagnosis.

## 4. `investigate`/`inspect` не піднімають доведені terminal із журналу

Для двох operation вище `journal` повертає failed `process_terminal`, однак
`investigate` показав лише execution reservations і unknown execution/delivery,
без цих failures у findings/errors. `inspect` першої operation також повернув
лише `execution_reserved`, terminal null. Це окрема діагностична прогалина.

- [ ] З’єднати native journal terminal з operation у `investigate` та `inspect`.
- [ ] Перевірити класифікацію capability: inspect потрапив у `team.tariff_recovery`.
- [ ] Додати регресію: reservation + native failed terminal дає доведену помилку
      з кодом і evidence, а не лише unknown. Відсутню доставку залишати unknown.
- [ ] Покрити затримку, дублікати, відсутність terminal та конфліктні докази.

## 5. Каталог: завантаження та отримання посилання з двох поверхонь

Додаткове повідомлення власника 2026-11-05:

> Не можливо скачати каталог ні з провідника ні з менеджера. З менеджера
> каталог в азерів при отриманні посилання через поширити або отримати
> посилання падає помилка і посилання не дає.

Це повідомлений користувацький збій, ще не відтворений і не прив’язаний до
конкретного operation/attempt. Формулювання «в азерів» збережено як отримано;
конкретний простір/каталог не встановлено. Не вважати його доказом формату,
провайдера, причини або зв’язку з перезашивкою.

Охоплення проблеми ширше за clipboard: посилання взагалі не повертається,
також не працює завантаження готового каталогу.

- [ ] Відтворити завантаження одного й того самого готового каталогу з провідника
      та менеджера; перевірити обидві поверхні незалежно.
- [ ] Відтворити «Поширити» та «Отримати посилання» з менеджера; з’ясувати,
      чи це спільний API/дозвіл/тип матеріалу, чи окремі несправності.
- [ ] Перевірити обробку реального типу каталогу, provider file identity,
      download/export, доступ і response guards. Не припускати конкретний формат.
- [ ] Зафіксувати безпечні stage/error codes та кореляцію кожної дії, включно
      з відмовою до отримання URL; не зводити все до clipboard failure.
- [ ] Додати регресії для завантаження з обох поверхонь і обох способів отримання
      посилання, з реальним контрактом каталогу та відмовами залежностей.
- [ ] Перевірити user-visible результат: файл справді завантажився, посилання
      справді доступне користувачу; окремий server success цього не доводить.

Критерій: готовий каталог можна завантажити з провідника й менеджера;
«Поширити» та «Отримати посилання» повертають придатне посилання за наявності
прав. При відмові користувач бачить конкретну причину/наступний крок, агент
отримує її через CLI. Зіставити з пунктом 1, але не об’єднувати першопричини
без доказів. Реалізацію залишити після поточного релізу.

#### CM01 — база для відтворення

- [ ] Зафіксувати післярелізний SHA, web/agent builds, час UTC/Київ, можливості
      версій, роль/дозволи і спосіб доступу. Зіставити зі скаргою, не лише ім’ям.
- [ ] Через read-only CLI знайти catalog/operation/attempt і актуальні докази.
      Якщо проєкції бракує — додати вузький дозволений CLI-запит через код і тести.
- [ ] У локальній beta підготувати створений Soty XLSX, старий каталог,
      каталог із native Sheets тільки там, де цей режим дозволений, та дублікати назв.
- [ ] У тестах змоделювати null size, відсутній webViewLink, видалений/переміщений
      файл, відкликаний доступ, відсутню/прострочену передачу, обрив відповіді після commit.

Приймання: кожний доведений дефект має мінімальний failing regression і
безпечний fixture; жодні дані користувача не копіюються в тестові артефакти.

#### CM02 — завантаження (пункти 5, F03–F04)

- [ ] Простежити material → grant → provider bytes/export → browser/agent →
      отриманий файл. Зберігати назву, розширення й правильний формат результату.
- [ ] Для підтверджено підтримуваних типів обрати коректний download/export;
      відсутність розміру не маскувати загальним «сервер відповів несподівано».
- [ ] Визначити окремо download_requested, handoff, provider transfer і local
      saved; браузерне збереження, яке технічно не спостерігається, залишати unknown.
- [ ] Покрити малий файл, шлях через агент, агент offline, 403/404, прострочений
      grant, обрив потоку, неправильний MIME, недоступний запис на диск, cancel.

Приймання: у beta з обох поверхонь завантажений файл відкривається та має
очікувані байти/формат. Втрата відповіді після handoff не записується як saved.

#### CM03 — посилання та поширення (пункти 1, 5; F01–F02, F04)

- [ ] З’ясувати первинну відмову share handler і перевірки payload для реального
      контракту; додати окремі коди відсутньої адреси, доступу й перевірки публічності.
- [ ] Відокремити «посилання отримано», «доступ дозволено», «скопійовано».
      Публічний доступ змінювати лише згідно з дозволами й погодженим сценарієм.
- [ ] Блокувати дубль натискання під час запиту, зберігати ідентичність
      невизначеної спроби та звіряти результат перед повтором.
- [ ] Показувати отриманий URL у стійкому доступному полі з повторним Copy/Open,
      якщо clipboard відмовив; довгі адреси не губляться після зникнення toast.

Приймання: усі entry points ведуть до однакового результату за однакових прав;
подвійне натискання не породжує дубль роботи; кожна відмова видима користувачу й CLI.

#### CM04 — відновлення перезашивки (пункти 2–3)

- [ ] Реалізувати погоджену вище заміну непридатної картинки в межах одного
      натискання, bounded перебір без повернення до відхиленого кандидата.
- [ ] Розрізняти зламаний файл і загальну несправність залежності; не прибирати
      весь пул через мережу/авторизацію. Визначити строки й умови скидання відмов.
- [ ] Провести fallback до запуску основної обробки, зберегти cancel, lease,
      reservation і upload fences. Перевірити updater, ручний запуск та recovery.
- [ ] Вичерпаний пул, ліміт перевірок і тимчасовий збій мають різні зрозумілі
      повідомлення з доступною наступною дією, без нескінченного «підготовка».

Приймання: робоча друга картинка автоматично доводить спробу до результату;
єдиний поганий файл не зациклюється; всі погані дають пояснення; невідомий
terminal не дозволяє повторне виконання відео.

#### CM05 — діагностика як частина виправлень (пункт 4; F01–F03)

- [ ] Увімкнути file-attempt producer для менеджера через правильний контекст
      storage; додати кореляцію для share, run/cancel/retry, partial bulk і fallback.
- [ ] З’єднати journal process_terminal із catalog/recovery operation, включно
      з parent/child. Усунути випадок Руслана: журнал failed, а inspect лише reservation.
- [ ] Передавати безпечну первинну причину transfer та effective settings/version,
      opaque candidate IDs і причини заміни. Створити code-map для нових кодів.
- [ ] Розрізнити current snapshot і історичну спробу; CLI catalog зараз читає
      поточну проєкцію без переданого period у getCatalogUpdateDiagnosis. Позначати
      часові межі, ліміт, fresh-through та неможливість історичної реконструкції явно.
- [ ] Розібрати timeout audit без послаблення захисту production: обмежені запити,
      частковий результат із unavailable замість втрати всього звіту.

Приймання: producer → guard → зберігання → inspect/investigate/audit перевірені
для success, partial, failure, cancel, missing/delayed terminal та delivery.
Критична помилка не зникає лише тому, що browser event не надійшов.

#### CM06 — контракти та неповні дані (F05–F06)

- [ ] При невалідному рядку повертати явний partial/contract error і безпечний
      лічильник відхилень. Придатні рядки лишати видимими; порожній успішний список
      відрізняти від повністю непридатної відповіді.
- [ ] Строго перевіряти count/boolean відповідей run/retry/cancel. Розділити
      invalid response, no-op, accepted та confirmed terminal.
- [ ] Профіль, runtime та розклад звіряти за версією/attempt, не лише одночасністю
      двох запитів. Відсутній профіль показувати як невідомий із відновленням.

Приймання: malformed payload не показує «вже запущено» або успішно порожній список;
змішані старі/нові контракти дають пояснення, а не тихе зникнення каталогів.

#### CM07 — масові збереження й розклад (F07–F08)

- [ ] Спільна семантика з одиночним редактором: accepted, rejected, conflict,
      unknown → bounded readback. Retry лише після встановлення результату.
- [ ] Показувати окремі outcomes кожного каталогу; повтор не торкається вже
      підтверджених змін і не перезаписує свіжі правки іншого користувача.
- [ ] Додати до bulk час, день і timezone разом з інтервалом як атомарну зміну;
      «залишити кожному своє» не стирає ці значення. Зберегти ліміт чотирьох writes.
- [ ] Перевірити DST, різні зони, прострочений next run, старий інтервал без
      calendar anchor, undo, втрату мережі після commit і частковий конфлікт.

Приймання: одиночне й масове налаштування дають однаковий ефективний розклад;
unknown не стає failed/success без доказу, результати batch не губляться.

#### CM08 — запуск, зупинка, повтор (F06)

- [ ] Показувати фактичну кількість прийнятих запусків; count=0 пояснювати

- [ ] Після втраченої відповіді звіряти поточну спробу перед новим запуском.
      Об’єднати захист від повторного натискання для рядка, history та selection.
- [ ] Пояснювати stop requested/confirmed/already terminal. Стоп поточної роботи
      й вимкнення розкладу — окремі дії з чіткими наслідками.

Приймання: double click, дві вкладки, cancel одночасно з success і retry за
старим profile не створюють дубль виконання або вигаданий успіх.

#### CM09 — часткове видалення (F09)

- [ ] Невідомі записи звіряти перед повтором; ключі не змінювати сліпо.

- [ ] Перевірити каталог під час оновлення, захищені outputs і зміну дозволів.

Приймання: при success A / failure B / not-started C UI відображає саме ці
три результати; повтор не видаляє A вдруге й не приховує помилку B.

- [ ] Не блокувати readback безкінечним очікуванням Promise. Повтор читання
      не повинен повторювати mutation або губити невизначений результат запису.

Приймання: history та збереження виходять із pending при timeout, дають Retry;

Приймання: нова спроба не успадковує 94% попередньої; partial з готовою таблицею

Опцію можна реалізувати спочатку для одного відео, з контрактом, що підтримує
набір варіацій. Обидві нові можливості потребують окремої специфікації змін
shared/DB/server/agent/web і сумісності перед реалізацією після релізу.

## Загальні правила роботи після релізу

Пріоритети виправлень визначає черга CM01–CM14 вище. Нові можливості CM15–CM16
описані в розділах 7–8 й додаються після стабілізації відповідних сценаріїв.

1. Зафіксувати версію/commit і повторити read-only діагностику; не покладатися
   на тимчасові файли `/tmp` як довготривалий доказ.
2. Відновити наскрізне пояснення відомих failures у CLI (пункт 4).
3. Відтворити передачу картинки й копіювання; виправляти підтверджені причини.
4. Покрити вибір/повтори, безпечний fallback і відсутні сигнали.
5. Оновити coverage inventory відповідно до 031-platform-autoanalytics;
   виконати релевантні тести та `npm run verify` перед комітом.
6. Після окремого релізу виправлень перевірити `investigate --as-of …` та
   `audit --as-of …`; підтвердити практичний результат користувача окремо
   від серверного receipt. Не закривати проблему лише через відсутність подій.

Джерела розслідування: штатні read-only analytics commands `errors`, `users`,
`diagnose`, `investigate`, `journey`, `journal`, `inspect`; скриншоти й уточнення
власника. Продакшн під час цього розбору не змінювали.
